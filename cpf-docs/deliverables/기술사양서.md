## 26. 사양 적용 범위와 Owner 판정

CPF 사양은 기능 이름보다 **상태를 소유하는 Module**을 먼저 정한다. Public API를 호출하는 Consumer가 여러 개여도 Current State, Version, Idempotency Ledger, Attempt, Audit를 갱신하는 Owner는 하나여야 한다.

| 영역 | Owner 판단 기준 | Consumer가 직접 하면 안 되는 일 | 복구 기준 |
|---|---|---|---|
| 업무 Domain | 업무 Current/History와 업무 상태 전이를 소유 | 타 Domain Table 직접 DML | Owner Query/Command와 Audit로 상태 확정 |
| Platform Runtime | Runtime desired/observed, health, apply state를 소유 | Frontend가 상태를 추정해 확정 | Operation ID·Version·ACK/NACK 대사 |
| Batch | Job Definition, Execution, Step, Lease/Fencing을 소유 | Scheduler/Worker가 메타 원장을 우회 갱신 | Spring Batch Metadata + CPF Execution 원장 대사 |
| BZA | 조직·직원·사용자·Role·Permission·Approval 정책을 소유 | 업무 Domain 상태를 BZA가 대신 소유 | as-of/Version/Audit 기준으로 재조회 |
| Gateway | Route/Binding/Server Group/Apply/LKG를 소유 | Service Registry 등록만으로 외부 공개 | Validate→Approve→Publish→ACK/NACK→LKG |

Owner가 불명확하면 구현을 추가하지 않고 `재확인 필요`로 두며, 먼저 API/SPI/Internal 경계를 결정한다.

## 27. Public API·SPI·Internal 계약

### 27.1 Public API

Public API는 Consumer가 Compile 또는 HTTP/Message 계약으로 의존하는 면이다. 변경 시 다음을 함께 검토한다.

- Operation ID와 URI/Method 또는 Java Signature.
- Request/Response/Error Schema와 필수·선택 필드.
- Version, Idempotency, Timeout, Retry, Unknown Result 의미.
- 인증 주체와 Permission/Data Scope/Masking.
- Local과 Remote 호출의 의미 동등성.
- OpenAPI/Generated Client/Guide/Test의 동시 변경.

### 27.2 SPI

SPI는 Provider 교체 지점이다. Provider SDK의 타입을 Public API에 노출하지 않고, Provider별 예외는 CPF 오류·Attempt·Health 계약으로 정규화한다. Provider 교체 시 Consumer 코드를 바꾸지 않는 것을 목표로 하되, 실제 Provider가 제공하지 않는 보장은 문서에서 만들지 않는다.

### 27.3 Internal

Internal 구현은 외부 Consumer의 Compile 계약이 아니다. 문서에 Internal Class를 쓸 때는 Source Evidence 목적임을 표시하고 고객 코드에서 직접 참조하는 예제로 제시하지 않는다.

## 28. HTTP Command 상세 계약

상태 변경 HTTP Command는 다음 순서를 기준으로 한다.

```text
Authenticate
 -> Authorize(Menu/API/Button + Data Scope)
 -> Validate request/schema/range
 -> Resolve Idempotency Key + canonical Request Hash
 -> Check Expected Version/CAS
 -> Record Operation/Attempt as needed
 -> Execute Owner transaction
 -> Persist Audit/Outbox in the same owner boundary where required
 -> Commit
 -> Return deterministic result or UNKNOWN_RESULT semantics
```

| 조건 | 응답/상태 의미 | Client 조치 |
|---|---|---|
| Validation 실패 | 요청 미수행 | 입력 수정 후 새 요청 |
| Permission 실패 | 미수행 | 권한/Scope 확인, 우회 금지 |
| Idempotency 동일 Key·동일 Hash | 기존 결과 재사용 또는 동일 Operation 상태 반환 | Key를 바꾸지 않음 |
| 동일 Key·다른 Hash | Conflict | 새 업무 요청인지 판정 후 새 Key |
| Expected Version 불일치 | Conflict/409 | 최신 상태 재조회 후 재판정 |
| Commit 이전 확정 실패 | FAILED 가능 | Side Effect 미발생 Evidence가 있을 때만 bounded retry |
| Commit 이후 응답 유실 | UNKNOWN_RESULT 가능 | Operation/Owner 상태 조회·Reconcile |
| 일부 Target만 적용 | PARTIAL | Target별 observed/ACK를 대사하고 재적용 또는 Rollback |

## 29. Query·Paging·Export 사양

Query는 업무 상태를 바꾸지 않는다. 검색조건, 기준시각, 정렬 Allowlist, Page/Size 상한, Masking 적용 후 반환을 계약으로 둔다. Export는 Browser Memory에서 전체 데이터를 조립하지 않고 Export Job/Artifact로 분리할 수 있으며, Permission·사유·만료·다운로드 Audit를 별도 관리한다.

ADM의 실제 63개 화면별 입력·기본값·표 컬럼·Button 조건은 `cpf-docs/deliverables/evidence/doc-r18/ADM_COMPONENT_CONTRACT_CATALOG.csv`를 Source Trace 원장으로 사용한다. 이 원장은 `expectedOperationIds`를 화면 Button으로 간주하지 않고 Vue Component의 실제 입력/조치와 분리해 기록한다.

## 30. Error·Result 상태 사양

| 분류 | 대표 상태 | Retry 판단 | 운영 종결 기준 |
|---|---|---|---|
| 입력/정책 | VALIDATION/REJECTED | 입력 또는 정책 변경 후 새 요청 | Owner 상태 미변경 확인 |
| 인증/인가 | UNAUTHORIZED/FORBIDDEN | 권한 복구 전 재시도 금지 | Session/Grant 정상화 |
| 동시성 | CONFLICT | 최신 Version 재조회 후 판단 | 새 Expected Version으로 의도 재확정 |
| 외부 의존 | FAILED/RETRY | Side Effect 경계에 따라 결정 | Attempt와 Target 상태 일치 |
| 응답 유실 | UNKNOWN_RESULT | Blind retry 금지 | Owner/외부 원장 Reconcile |
| 다중 Target | PARTIAL/NACK/DRIFT | Target별 결정 | observedVersion/ACK가 desired와 일치하거나 LKG 복귀 |
| 복구 완료 | RECONCILED/ROLLED_BACK | 추가 재시도 없음 | Audit와 최종 상태 일치 |

상태명은 기능별 실제 Enum/DB 값을 우선한다. 위 분류는 서로 다른 기능의 운영 의미를 비교하기 위한 상위 사양이다.

## 31. Idempotency·Operation·Attempt 상세 사양

Idempotency Ledger는 적어도 Key Scope, Request Hash, Owner Operation, 처리 상태, 결과 Snapshot 또는 Result Reference, 생성/만료 시각을 식별할 수 있어야 한다. 외부 Side Effect는 같은 Idempotency Key만으로 충분하지 않을 수 있으므로 Attempt ID와 Target Tracking ID를 별도로 유지한다.

Operation ID는 사용자 요청의 추적 축이고 Attempt ID는 실제 시도 축이다. 한 Operation에 여러 Attempt가 있을 수 있으나, 응답 유실 후 새 Operation으로 재실행하면 중복 Side Effect를 만들 수 있으므로 상태 조회를 먼저 수행한다.

## 32. Timeout Budget 사양

| Budget | 적용 위치 | 초과 시 기록할 값 |
|---|---|---|
| Client Deadline | Browser/Caller 전체 요청 | Operation ID, elapsed, last known state |
| Queue/Claim | Worker가 작업을 소유하기 전 | queue/lease owner, age |
| Connect | 외부 연결 수립 | target, address/pin, attempt |
| Response/Read | 요청 송신 이후 응답 | target, attempt, timeout stage |
| Retry Backoff | 다음 Attempt 전 | attempt no, nextAt |
| Reconcile Deadline | UNKNOWN 상태 대사 | probe 결과, decision |

하위 Timeout의 합과 Retry Backoff는 상위 Deadline을 넘지 않도록 설계한다. 실제 Starter/Module Default는 `PROPERTY_LEAF_CATALOG.csv`의 Source 확인값을 따른다.

## 33. Messaging Envelope·Reliability 사양

Message/Event는 Event ID, Key, Schema Version, Producer, Correlation/Transaction, Payload Hash를 식별할 수 있어야 한다. Producer는 업무 Commit과 Publish 사이의 유실을 Outbox로 닫고, Consumer는 중복 수신을 Inbox/Idempotency로 닫는다.

```text
Business Transaction
 -> Outbox READY
 -> Publisher claim/lease
 -> Broker publish attempt
 -> ACK or UNKNOWN
 -> Consumer receive
 -> Inbox duplicate guard
 -> Consumer business commit
 -> ACK
 -> Retry/DLQ/Reconcile
```

Broker별 연결 세부는 Provider Starter가 담당하지만 Outbox/Inbox/DLQ/Replay/UNKNOWN 의미는 Consumer에 동일하게 보인다. 현재 Source 확인 leaf는 `cpf.messaging.reliability.*`와 Broker Provider별 설정을 `PROPERTY_LEAF_CATALOG.csv`에 기록한다.

## 34. External Integration 사양

HTTP/TCP/SFTP/Webhook/ISO8583 연계는 다음 공통 정보를 갖는다.

- Target/Endpoint와 Environment.
- Request/Operation/Attempt/External Tracking ID.
- Connect/Response/Overall Timeout.
- Retry 가능 조건과 Idempotency 근거.
- Request/Response Hash 또는 Masked Evidence.
- 응답 유실 시 Status Query/Reconcile 경로.
- Compensation 또는 Manual Decision 조건.
- Secret/TLS/Host/CIDR Allowlist와 SSRF 방어.

HTTP Client의 현재 공통 Runtime 설정은 `cpf.service-call.*`, `cpf.http-client.*`, `cpf.services.*`를 사용하며 Catalog의 논리 Capability Namespace와 구분한다.

## 35. File·Attachment·Archive 사양

Upload/Import는 파일명만 신뢰하지 않고 Size, Format, Checksum, Template/Schema Version을 검증한다. 대용량 처리는 Streaming, bounded buffer, Temp Artifact, cancellation, disk capacity, partial cleanup을 고려한다.

File Job은 `RECEIVED → VALIDATED/READY_TO_APPLY → APPLY/FAILED/PARTIAL_FAILED/UNKNOWN_RESULT → Rollback/Resolution`과 같이 실제 Owner 상태를 기준으로 조작하며, `UNKNOWN_RESULT`는 외부/DB Evidence로 `SIDE_EFFECT_NOT_APPLIED`, `SIDE_EFFECT_APPLIED`, `SIDE_EFFECT_COMPENSATED` 중 실제 구현이 허용하는 결과를 확정한다.

## 36. Batch 상세 사양

### 36.1 Job Definition

Job ID, Definition Version, Executor Type, Trigger, Typed Parameter, Resource Policy, Recovery Policy, Alert Policy, Dependency, Checksum, Row Version을 함께 관리한다. Published/Retired Version을 임의 수정하지 않고 새 Version 또는 허용된 상태 전이를 사용한다.

### 36.2 Execution

Execution은 Job Parameter Snapshot, Spring Batch JobInstance/JobExecution/StepExecution, Worker/Server Instance, Transaction ID를 연결한다. 기술 상태 `COMPLETED`만으로 업무 대사 완료를 의미하지 않는다.

### 36.3 Scheduler·Lease

Schedule Preview, Business Calendar, Misfire, Leader/Lease, 중복 억제를 분리한다. Lock/Lease 강제 해제는 실제 실행이 살아 있으면 중복 수행을 만들 수 있으므로 Fencing Token과 Heartbeat를 확인한다.

### 36.4 Center-Cut

Job 단위 대량 재처리보다 Execution/Target/Result 단위 상태를 사용한다. 현재 ADM Component 계약은 FAILED Execution 재처리와 UNKNOWN Execution 대사를 분리하고 Job 전체 blind retry를 허용하지 않는다.

## 37. ADM·BZA 사양

### 37.1 ADM

현재 Route Registry는 63개 Route를 갖고 각 Route에 Menu ID, Risk, Feature Flag, expectedOperationIds, Component가 연결된다. Router는 Server Session에서 Route 접근권한과 Feature 활성 상태를 다시 계산한다. Query Parameter를 Permission 근거로 사용하지 않는다.

위험 조치는 화면별 실제 Permission과 Server API 검증을 모두 통과해야 하며, Reason/Expected Version/Approval/Idempotency 요구 여부는 실제 Component/API 계약을 따른다.

### 37.2 BZA

현재 BZA Route 계약은 26개 Route를 갖는다. 조직/직원/배치/역할/권한/결재/세션/감사/첨부/다운로드를 Menu Code와 Operation ID로 연결한다. BZA가 업무 Domain의 Current State를 대신 소유하지 않는다.

## 38. Gateway Route·Publish 사양

Gateway Binding은 Service Registry 존재만으로 외부 공개되지 않는다. 현재 UI/Control Plane은 **Default Deny**를 전제로 Draft→Validate→Approve/활성화→Instance Apply ACK를 확인한다.

Route 사양에는 Host/Path/Method/API Version/Route Version/Service/Server Group/Ingress·Target Protocol/Timeout/Retry/Idempotent/Gateway Allowed/Direct Allowed/TLS/AuthN/AuthZ/Header/Rate Limit/Health Policy를 포함한다. Apply 후 `expectedVersion != appliedVersion` 또는 실패 상태는 Drift로 운영한다.

## 39. Security·Session·Secret 사양

- Browser privileged console은 Server Session/CSRF/Trusted Origin 경계에서 동작한다.
- Resource Server는 enabled일 때 issuer-uri와 jwk-set-uri 중 정확히 하나를 요구한다.
- Service Identity는 service-id, key-id, 충분한 Secret 길이와 TTL 상한을 검증한다.
- Secret Starter는 승인된 고객 SecretProvider가 없으면 Runtime을 거부한다.
- 화면/로그/Evidence는 Raw Secret을 보존하지 않고 Reference/Metadata를 사용한다.
- Break-glass는 좁은 Scope, 제한 TTL, 사후 Review와 Audit를 갖는다.

## 40. Configuration·Runtime Control 사양

Catalog Namespace는 기능 선택을 위한 논리 이름이고 실제 Runtime Key Prefix와 같다고 가정하지 않는다. `STARTER_RUNTIME_CONFIG_SURFACE.csv`는 39 Starter 각각을 `DIRECT_LEAF`, `DIRECT_LEAF_DIFFERENT_PREFIX`, `CONSUMER_OF_CORE_DB`, `NO_DIRECT_RUNTIME_LEAF` 등의 형태로 구분한다.

Dynamic Runtime 변경은 desired Version/Checksum/Target Snapshot, Approval, Apply Attempt, ACK/NACK, observed Version, Rollback/LKG를 연결한다. 응답 유실은 Operation ID로 상태를 조회하며 새 Operation을 만드는 것보다 기존 상태 대사를 우선한다.

## 44. 검증 사양과 Evidence 등급

정적 Source 대조, Unit/Contract Test, Runtime Integration, Browser E2E, DB3, Multi-process/Fault/Restore Drill은 서로 다른 Evidence다. 한 종류의 PASS를 다른 종류의 성공으로 승격하지 않는다.

현재 문서 패키지의 정적 Evidence는 135 EDU, 39 Starter, 63 ADM Component, 26 BZA Route, 243 Runtime leaf, Tool/Gate 원장을 포함한다. Java/Gradle 전체 Runtime, Browser E2E, DB3 Live Lifecycle, Broker/Multi-process, DR Drill은 이 문서 작성 세션에서 실행하지 않았으므로 `미검증`으로 유지한다.

## 46. 변경 검토 완료 조건

기술사양 변경은 다음 질문에 답이 있을 때만 문서상 `완료`로 판정한다.

1. 상태 Owner와 실제 Consumer는 누구인가.
2. Public API/SPI/Internal 경계가 바뀌는가.
3. 정상 입력·기본값·상태 전이는 무엇인가.
4. 동시성·멱등·Timeout·응답 유실 시 상태는 무엇인가.
5. 부분 실패와 UNKNOWN_RESULT를 누가 어떻게 대사하는가.
6. Permission·Scope·Masking·Reason·Approval·Audit가 어디에서 강제되는가.
7. DB/Message/Config/Frontend/Batch/Gateway 호환 영향이 있는가.
8. 어떤 Test를 실제 실행했고 어떤 Test가 미검증인가.
9. Guide/Design/Evidence가 Source와 양방향으로 갱신됐는가.
