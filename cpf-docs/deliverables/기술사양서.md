## 1. 기술 Stack과 기준

Stack Version은 `gradle/cpf-stack.properties`, 제품/Component Version은 `gradle/cpf-platform.properties`, Module·Profile·Capability는 `settings.gradle`이 정본이다. Artifact Manifest와 Runtime Version Endpoint가 같은 Source SHA를 반환해야 한다.

| 영역 | 기술 기준 |
|---|---|
| Language/Runtime | Java Toolchain과 JVM Option은 Stack 정본 |
| Framework | Spring Boot·Spring Framework·Spring Batch·Spring Security |
| Build | Gradle Wrapper·BOM·Publication·Offline/Remote Mode |
| API | REST·OpenAPI·Generated Client·표준 Error |
| Data | JDBC/MyBatis·MariaDB/PostgreSQL/Oracle |
| Messaging | Kafka·RabbitMQ·JMS·IBM MQ |
| Cache | Caffeine·Valkey·durable invalidation |
| Frontend | Vue·TypeScript·Generated Client·Playwright |
| Operations | ADM/BZA/Gateway·Log/Metric/Trace·Support Bundle |

## 2. Public API·SPI·Internal

Public API는 고객 업무와 Consumer가 사용하는 안정 계약이다. SPI는 Starter/Provider가 구현한다. Internal은 Store·SDK·Generated 내부 구현이다.

Public 계약 변경 시 Source·Binary·Serialization·Error·OpenAPI·Generated Client·DB/Message Schema·Sample·문서 호환을 검토한다. Default Method는 Token·Evidence·상태 검증을 우회하지 않는다.

## 3. 표준 Context·Header

| 항목 | 의미 | 규칙 |
|---|---|---|
| Transaction ID | 하나의 업무 요청 | 모든 Segment에 전파 |
| Trace ID | 분산 Trace | W3C 또는 정본 형식 |
| Business ID | 고객 업무 식별자 | Masking·길이 제한 |
| Operation ID | 부작용 요청/결과 | 응답 유실 조회 Key |
| Idempotency Key | 중복 요청 Key | Owner 범위, Payload Hash와 결합 |
| Expected Version | 동시성 | 상태 변경에 사용 |
| Actor/Service Identity | 요청 주체 | 사용자·서비스 구분 |
| Reason | 운영 변경 근거 | 공백 금지·길이 제한 |
| Approval Request ID | 위험 조치 승인 | Snapshot·Expiry 검증 |

## 4. 표준 Result·Error

Result는 상태, 업무 결과, Version, Operation/Attempt, Replay 여부, Target 결과를 포함한다. Error는 Code, Message, HTTP/Protocol 의미, Retryable, Validation Field, Operation ID를 제공한다.

- `400`: 형식·범위·교차 Field Validation.
- `401`: 인증 실패.
- `403`: Permission/Data Scope.
- `404`: Owner 대상 없음.
- `409`: Version·Idempotency Hash·상태 충돌.
- `422`: 업무 규칙 거부.
- `429`: Rate/Bulkhead.
- `5xx`: Provider/Owner 장애. Dispatch 이후 결과 불명은 별도 상태로 보존한다.

## 5. Idempotency·Operation·Attempt

Idempotency Ledger는 Owner, Key, Request Hash, 상태, Result Snapshot, Created/Expires를 갖는다. Operation은 요청 단위, Attempt는 실제 Target 실행 단위다. Replay는 같은 Key/Hash일 때 기존 Result를 반환한다. 다른 Hash는 Conflict다.

여러 Target은 Aggregate와 Target Result를 모두 저장한다. Aggregate만 저장해 Partial 정보를 잃지 않는다.

## 6. Local·Remote Contract

Local Adapter와 Remote Adapter는 같은 Port·DTO·Validation·Error·Idempotency·Permission·Audit 의미를 사용한다. Remote는 Service Identity, Serialization, Timeout, Trace, Attempt, UNKNOWN_RESULT를 추가한다. Contract Fixture를 두 구현에 공통 실행한다.

## 7. Data·Transaction 계약

업무 Row·History·Audit·Outbox가 같은 DB에 있으면 같은 Transaction Manager를 사용한다. Optimistic Version Update는 `WHERE id=? AND version=?`와 영향 건수 1을 사용한다. 외부 Target·Broker 결과를 Local Transaction에 포함한다고 가정하지 않는다.

## 8. Messaging 계약

Message Envelope에는 Message ID, Event Type, Schema Version, Business Key, Occurred At, Producer, Trace/Transaction, Payload Hash를 포함한다. Producer는 Outbox, Consumer는 Inbox/Attempt, Poison은 DLQ를 사용한다.

AsyncAPI Catalog는 `cpf-tools/contracts/asyncapi`에 두고 실제 Producer/Consumer와 Schema Version을 대조한다.

## 9. File·Attachment 계약

Metadata에는 Artifact ID, File Name, Size, MIME, Checksum, Storage Key, Scan 상태, Retention, Owner, Version을 포함한다. Upload는 Temp→Checksum/MIME/Scan→Commit, Download는 Permission/Data Scope/Masking/Reason/Audit를 사용한다.

## 10. HTTP·TCP·전문 계약

HTTP는 Target, Timeout Budget, Authentication, Retry Predicate, Circuit, Idempotency, Attempt를 명시한다. TCP는 Frame 경계, Charset, Correlation, TLS, Pool을 명시한다. Fixed-length와 ISO8583은 Versioned Layout/Packager와 Golden Bytes를 사용한다.

## 11. Cache·Valkey 계약

`cpf.data.cache.valkey` Prefix의 주요 Default는 enabled=false, key-prefix=`cpf:`, invalidation-channel=`cpf.cache.invalidate`, default-ttl=10m, required=true, tls=false, maximum-payload-bytes=1048576, scan-count=500이다.

Key Prefix는 1~120 Token, Channel은 1~180 Token, Payload는 1~64 MiB, Scan Count는 10~10000이다. Durable Coordinator의 reconcile batch size는 1~10000, max batches는 1~1000이다.

## 12. Common Template·Calendar 계약

Template Lifecycle은 DRAFT/APPROVED/RETIRED, Key는 Template Code·Channel·Version, 동시성은 expectedRevision이다. 변경은 Audit와 durable refresh Event를 같은 Transaction에 둔다.

Calendar는 Calendar ID·Institution·Business Date·Business Day·Day Type·Version을 갖고 UPSERT/DELETE와 기준일 계산을 제공한다. Outbox 실패 시 변경 Transaction을 Rollback한다.

## 13. Batch 기술 계약

Spring Batch Metadata와 CPF Control Ledger를 연결한다. JobParameter는 Instance 식별, Execution은 Attempt, StepExecution은 Count/Exit, ExecutionContext는 Checkpoint를 소유한다.

Center-Cut Action Request는 `reason`, `approvalRequestId`, `idempotencyKey`를 필수로 한다. 화면 Operation은 `admCenterCutReprocessFailedExecution`, `admCenterCutReconcileUnknownExecution`이며 Execution-scope만 허용한다.

## 14. ADM·BZA 기술 계약

ADM Route Registry는 Route 62개와 Route–Operation 405개를 소유한다. Route 항목은 routeId, path, menuId, label, group, component, ownerModule, riskLevel, featureFlag, expectedOperationIds다.

BZA는 Route 26개, Route–Operation 78개를 제공한다. Directory와 Permission은 기준일, 결재는 Versioned Policy와 Participant Snapshot을 사용한다.

## 15. MFA·Notification 계약

ADM Login DTO는 operatorId, password, otpCode를 사용한다. MFA TOTP는 RFC 6238, HMAC-SHA1, 30초, 숫자 6자리, ±1 Window, constant-time 비교다. Secret char/byte 배열은 사용 후 지운다.

Notification Provider 미설정 시 `UnavailableNotificationSender`는 성공을 반환하지 않고 `PROVIDER_NOT_CONFIGURED`를 기록한다. Receiver는 Masking한다.

## 16. Gateway 기술 계약

Route Binding은 Route ID/Version, Predicate, Rewrite, Target Group, Security, Timeout, Retry/Circuit/Bulkhead, Idempotency, Publish 상태를 갖는다. HMAC Canonicalization, Body SHA-256, Timestamp, Nonce, Audience, SSRF/TLS를 검증한다. Publish는 Validate→Approval→ACK/NACK/UNKNOWN→LKG/rollback이다.

## 21. Health·Log·Metric·Trace

Liveness는 Process, Readiness는 필수 Dependency와 수행 가능성, Version은 Source SHA·Artifact·Profile·Capability를 반환한다. Log/Trace는 Transaction·Operation·Attempt·Target을 연결한다. Metric은 Throughput·Latency·Error·Lag·Pool·Capacity를 제공한다.

## 22. Artifact·DB·Release 사양

Release Bundle은 Artifact·BOM·Manifest·Checksum·SBOM·Provenance·DB Vendor Pack·Config Template·Frontend Client를 포함한다. DB Pack은 source/install/migration/rollback/runtime/verify Chain을 갖는다. Release Gate는 Fresh Consumer, 3 Vendor, OpenAPI/Client, Browser, Supply Chain, Rollback을 포함한다.

## 23. 계약 변경 Gate

1. Source Owner와 Public/API/SPI/Internal 범위를 확인한다.
2. 모든 Consumer·Adapter·Generated Client를 찾는다.
3. DTO/Schema·DB·Message·Config 호환을 판정한다.
4. Local/Remote·3 Vendor·Frontend·Batch·ADM/BZA/Gateway를 회귀한다.
5. 오류·응답 유실·부분 실패·Rollback Test를 실행한다.
6. 공식 매뉴얼과 Evidence Matrix를 같은 SHA로 갱신한다.
