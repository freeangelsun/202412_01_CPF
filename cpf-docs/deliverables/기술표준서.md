## 1. 기본 원칙

1. 실제 Owner와 Consumer가 없는 추상화는 공개 기능으로 판정하지 않는다.
2. Source·SQL·API·Config·Frontend·Script·Test·문서는 같은 상태와 이름을 사용한다.
3. 선택 기술은 Core/Common에 강제 전이하지 않는다.
4. 실패를 숨기지 않고 Retryable, Final, Partial, Unknown으로 분류한다.
5. 직접 실행하지 않은 시험은 `미검증`으로 기록한다.
6. 업무 원장은 업무 Domain이 소유한다.
7. Secret·Token·Password·Private Key는 Repository와 Evidence에 저장하지 않는다.

## 2. Java·Package 표준

- Java Toolchain은 Root Stack 정본을 따른다.
- Public API·SPI는 Provider SDK Type을 노출하지 않는다.
- `internal` Package는 다른 Gradle 프로젝트에서 참조하지 않는다.
- DTO와 Domain Model을 혼용하지 않는다.
- 시간은 `Instant` 또는 명시된 Zone 정책을 사용한다.
- 금액은 `BigDecimal`과 Currency/Scale 계약을 사용한다.
- 식별자는 임의 문자열보다 Value Object를 우선한다.
- Nullable 반환은 계약에 명시하고 가능한 경우 명시적 Result/Optional을 사용한다.

## 3. 의존성 표준

### Core

허용:

```text
JDK·Jakarta 최소 API
Provider-neutral API/SPI
순수 Java 최소 구현
```

이관 대상:

```text
MyBatis/JDBC 조립
AspectJ Runtime
WebMVC/Servlet Runtime
OpenAPI UI
OTel SDK/Exporter
HTTP Provider Runtime
Validation Provider
Compress Runtime
SFTP Runtime
Broker Reliability JDBC
```

### Common

업무 공통만 유지한다. Redis·Valkey·Caffeine·MyBatis·POI·Validation Provider는 Leaf Starter로 이동한다.

### Starter

- `api`는 Consumer가 컴파일에 필요할 때만 사용한다.
- Provider SDK는 가능한 한 `implementation`으로 숨긴다.
- Optional Provider가 없을 때 Class Loading 실패가 없어야 한다.
- AutoConfiguration은 조건과 Backoff를 Test로 검증한다.

## 4. 코딩 표준

### Command

```java
public record OperationCommand(
        String operationId,
        String idempotencyKey,
        long expectedVersion,
        String reason,
        String approvalId) {}
```

- Command는 상태 변경 의도와 동시성·감사 문맥을 포함한다.
- Controller에서 업무 Transaction을 조립하지 않는다.
- 재시도할 때 Command Identity를 유지한다.

### Result

```java
public record OperationResult(
        String operationId,
        OperationState state,
        String resultCode,
        String reconcileKey) {}
```

- Boolean 성공/실패만 반환하지 않는다.
- `UNKNOWN_RESULT`와 `PARTIAL_SUCCESS`를 표현한다.

### 예외

- 예외 Message에 Secret·개인정보·SQL 원문을 넣지 않는다.
- 외부 Provider 예외를 Public API에 그대로 노출하지 않는다.
- Error Code, Failure Class, Retry Hint, Correlation을 매핑한다.

## 5. Transaction·동시성

- 업무 상태 변경은 Local Transaction으로 묶는다.
- 낙관적 충돌은 `expectedVersion` 불일치로 판정한다.
- Distributed Lock만으로 정확성을 보장하지 않는다.
- Lease 소유자는 Fencing Token을 쓰기 시점에 검증한다.
- Retry는 Deadline과 Attempt Budget을 초과하지 않는다.

## 6. 멱등성·UNKNOWN_RESULT

### 멱등성

- 같은 업무 효과는 같은 Idempotency Key를 사용한다.
- 요청 Hash가 다른데 Key가 같으면 Conflict로 거부한다.
- 이전 성공 결과는 원 결과를 재사용한다.
- Logical Delete 후 Key 재사용 정책을 명시한다.

### 결과 불명

1. Provider Write 또는 DB Commit 가능성을 확인한다.
2. 업무 원장·Outbox·Inbox·Receipt·Target 상태를 조회한다.
3. 대사 결과를 `SUCCEEDED`, `FAILED_FINAL`, `PARTIAL_SUCCESS` 중 하나로 확정한다.
4. 수동 판정은 Reason·승인·Evidence를 남긴다.

## 7. Messaging 표준

- Domain은 Provider SDK 대신 CPF Messaging Port를 사용한다.
- Message Schema와 Version을 명시한다.
- Consumer는 중복·순서 변경·재전달을 가정한다.
- Retry/DLQ/DLT 정책은 횟수뿐 아니라 시간 예산과 Poison 판정을 포함한다.
- Replay는 Dry Run, 대상 건수, 승인, 감사가 필요하다.
- Kafka·RabbitMQ·JMS·IBM MQ를 같은 추상화로 숨기되 Provider 고유 운영 항목은 Extension으로 노출한다.

## 8. REST·TCP·File 표준

### REST

- Connect/Read/Write Timeout을 구분한다.
- Retry 가능한 Method와 업무 멱등성을 함께 검증한다.
- HTTP 2xx라도 업무 Result Code를 확인한다.

### TCP

- Fragmentation과 Coalescing을 기본 Fault로 시험한다.
- Frame Limit, Queue Limit, Connection Pool Limit을 설정한다.
- Correlation 없는 동시 요청은 금지하거나 단일 비행으로 제한한다.

### File/SFTP

- 임시 파일 → Checksum → Atomic Rename 순서를 사용한다.
- Transfer Ledger로 Partial Transfer와 Resume를 판정한다.
- 파일명·경로 Traversal·Symlink를 검증한다.

## 9. Security 표준

- 인증과 권한을 분리한다.
- Permission, Data Scope, Masking, Reason, Approval, Audit를 각각 검증한다.
- Service Identity는 사용자 Session과 분리한다.
- Secret Provider가 없거나 필수 Secret이 유효하지 않으면 Prod 계열 기동을 거부한다.
- Credential Rotation 중 Old/New 중첩 구간과 Rollback을 정의한다.

## 11. DB·SQL 표준

- Logical Model과 Canonical Metadata를 먼저 변경한다.
- Vendor SQL 직접 수정은 생성 원본과 Generator 변경을 동반한다.
- DDL은 재적용·Checksum Conflict·Drift를 판정할 수 있어야 한다.
- Rollback Script가 불가능하면 Forward Recovery 절차와 영향 범위를 제공한다.
- 데이터 보정은 Dry Run·대상 건수·Chunk·Commit·Resume·Audit를 제공한다.

## 12. Frontend 표준

- Route·Permission·Operation Contract를 생성 정본과 대조한다.
- 버튼 활성 조건은 상태·권한·Expected Version·Approval을 반영한다.
- 응답 유실 시 성공 Toast를 임의 표시하지 않고 Operation 상태를 재조회한다.
- 위험 조치는 Reason과 재확인·승인 정보를 표시한다.
- 표·상세·Form은 Masking과 Data Scope를 유지한다.

## 14. Starter 제거 시험

각 Optional Starter는 다음을 확인한다.

1. 의존성 제거 후 Compile 성공
2. 관련 Property가 없어도 기동 성공
3. 관련 Bean·Route·Migration이 남지 않음
4. JAR/WAR·POM·SBOM에 Provider SDK가 없음
5. 다른 Capability가 회귀하지 않음

## 15. Build·Publication

- `LOCAL_DEV`, `REMOTE`, `OFFLINE` 모드를 분리한다.
- 동일 Version의 Artifact Content가 모드별로 달라지지 않아야 한다.
- Sources·JavaDoc·POM·SBOM·Checksum을 함께 검증한다.
- Aggregate Starter는 전이 Dependency 외 Content가 없어야 한다.
- Release Manifest는 `resolvedStarters`, Profile Version, Provider Binding, Source SHA를 포함한다.

## 16. Review 표준

Review는 다음을 질문한다.

- 실제 Consumer가 있는가?
- 정상 경로 외 오류·경계·부분 실패가 구현됐는가?
- 응답 유실 후 중복 효과를 막는가?
- 다중 인스턴스에서 이전 Owner 쓰기가 차단되는가?
- Secret·권한·감사·Masking이 유지되는가?
- 3개 DB Vendor와 Upgrade·Rollback이 일치하는가?
- Generator·Guide·Artifact가 함께 변경됐는가?
