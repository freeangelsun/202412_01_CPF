## 1. 표준 적용 우선순위

실제 Source·SQL·API·Config·Frontend·Script·Test가 문서와 과거 보고보다 우선한다. Public 계약 변경은 Owner와 Consumer를 함께 검토한다. 선택 Provider의 기술 표준은 SPI 경계를 넘지 않는다.

## 2. Java·Package·Module

- Package는 `api`, `application`, `domain`, `persistence`, `integration`, `config` 책임을 분리한다.
- Public Type은 불변 DTO/Value Object를 우선한다.
- Null·Optional·Exception 의미를 명확히 한다.
- Clock·ID·Random·External Client는 Test 가능한 Port로 주입한다.
- Static mutable state와 Process Memory 정본을 만들지 않는다.
- Provider SDK Type을 Public API에 노출하지 않는다.
- Owner Module 밖 Persistence 직접 접근을 금지한다.

## 3. API·DTO·Validation

- Query와 Command Endpoint를 분리한다.
- 입력 Field에 형식·길이·범위·교차 검증을 둔다.
- 상태 변경은 Expected Version·Idempotency Key·Reason을 사용한다.
- Error Code·HTTP Status·Retryable 의미를 일관되게 한다.
- 목록은 Paging·Sort whitelist·Data Scope를 사용한다.
- 원문·Download는 별도 Permission·Reason·Audit를 사용한다.
- OpenAPI Operation ID는 전역 중복이 없어야 한다.

### 3.1 API Review 표

| 항목 | 표준 |
|---|---|
| Resource/Action | 조회와 상태변경을 분리하고 업무 의미를 이름에 표현 |
| Operation ID | OpenAPI·Client·Permission·Audit에서 유일 |
| DTO | Provider SDK Type 금지, 형식·길이·범위·교차 Validation |
| Paging | 최대 Size·안정 Sort·Cursor/Offset 의미 고정 |
| Error | Validation·Forbidden·Conflict·Not Found·Timeout·Unknown 분리 |
| Header/Context | Transaction·Trace·Idempotency·Identity·Deadline 연결 |
| Version | 상태 변경의 Expected Version/Revision 사용 |
| Response | 상태·Version·Operation·Replay/Partial 표시 |
| Compatibility | Required Field/Enum/상태 변경 시 Consumer 영향 기록 |

### 3.2 Validation 순서

형식→필수→길이/범위→Enum→교차 Field→Reference→권한→현재 상태→Version→Idempotency 순으로 검증한다. Secret/개인정보 값은 오류 Message에 포함하지 않는다.

## 4. Transaction·동시성

- 업무 Row·History·Audit·Outbox의 Transaction Manager를 명시한다.
- Optimistic Update는 Version 조건과 영향 건수 1을 검증한다.
- Deadlock/Serialization 실패 Retry는 상한과 Idempotency를 사용한다.
- 외부 부작용을 DB Transaction 성공으로 추정하지 않는다.
- Lease는 Expiry·Owner·Fencing Token을 사용한다.
- CAS 실패를 마지막 Write Wins로 덮지 않는다.

### 4.1 동시성 도구 선택

| 상황 | 도구 | 금지 Pattern |
|---|---|---|
| 단일 Row 상태 변경 | Optimistic Version CAS | Last-write-wins |
| 순번/Lease/단일 Owner | DB Lock·Lease·Fencing | Process Memory Lock |
| 중복 요청 | Idempotency Ledger | 요청마다 새 Key 강제 |
| 여러 Row Snapshot | 조건 Hash·기준시각 | 실행 중 대상 무제한 변경 |
| 외부 부작용 | Attempt·UNKNOWN·Reconcile | Local Transaction으로 가정 |
| Message 전달 | Outbox/Inbox | DB Commit 전 Broker Publish |

Transaction 범위를 넓혀 장시간 Lock을 만들지 않고, 외부 호출을 DB Transaction 안에 넣을 경우 Timeout·Lock 영향과 결과 불명을 명시적으로 설계한다.

## 5. Idempotency·UNKNOWN_RESULT

- Key 범위와 만료를 Owner가 정한다.
- Request Hash와 Result Snapshot을 저장한다.
- 같은 Key/다른 Payload는 Conflict다.
- Dispatch 전 실패와 Dispatch 후 결과 불명을 구분한다.
- UNKNOWN은 Target/Owner 원장으로 대사한다.
- 원본 Attempt를 수정·삭제하지 않는다.
- 성공 Target을 중복 재실행하지 않는다.

## 6. Messaging

- Event Envelope와 Schema Version을 사용한다.
- Producer는 Outbox, Consumer는 Inbox/Attempt를 사용한다.
- ACK 전에 업무 결과를 저장한다.
- Poison·DLQ·Backout을 무한 Retry하지 않는다.
- Kafka/RabbitMQ/JMS/IBM MQ Provider 차이를 업무 DTO에 노출하지 않는다.
- AsyncAPI Catalog와 Producer/Consumer를 대조한다.

## 7. HTTP·TCP·Codec·File

- HTTP Timeout Budget과 Retry Predicate를 명시한다.
- TCP Frame 경계·Charset·Correlation을 명시한다.
- Fixed-length는 Byte Length와 Layout Version을 사용한다.
- ISO8583은 MTI·Bitmap·STAN/RRN·MAC 규칙을 Version으로 관리한다.
- File은 Temp·Checksum·Scan·Atomic Rename·Retention을 사용한다.
- SFTP Host Key 검증을 끄지 않는다.

## 8. Security·Secret·Masking

- 사용자·서비스·운영자 Identity를 분리한다.
- Permission은 Menu·Button·API·Data Scope에서 적용한다.
- MFA Secret·Password·Token을 Log/DTO에 반환하지 않는다.
- TOTP는 형식·Window·constant-time 비교를 사용한다.
- Secret Rotation은 Consumer 전환과 Rollback을 포함한다.
- Raw Contact·개인정보 Download는 별도 Audit를 사용한다.
- Break-glass는 Scope·Expiry·Review·Close가 필수다.

### 8.1 Security Coding Gate

- 인증 Identity와 요청 Body의 Actor/Requester가 일치한다.
- UI 숨김 외에 Controller/Application/Repository Data Scope를 적용한다.
- Permission은 Resource·Action·Scope·조건을 표현한다.
- Masking 해제와 원문 Download에는 별도 Permission·Reason·Audit를 사용한다.
- Secret은 `String` 장기 보관·Log·Exception·Bundle에 남기지 않는다.
- Key/Certificate는 Version·Provider·Rotation·Grace·Consumer Probe를 관리한다.
- MFA는 Secret Reference·OTP 형식·Clock Skew·Replay/Session을 검증한다.
- Gateway는 HMAC·Body Hash·Nonce·Audience·SSRF·TLS를 함께 검토한다.
- Break-glass는 Scope·Expiry·Action Audit·사후 Review·Close를 강제한다.

## 9. Logging·Metric·Trace·Audit

- Log에 Transaction/Trace/Operation/Attempt/Target을 넣는다.
- Error는 Code와 원인 Domain을 기록한다.
- Metric Label에 업무 ID·사용자 ID를 넣지 않는다.
- Trace Header와 Service Identity를 함께 전파한다.
- Audit는 Before/After·Actor·Reason·Approval을 갖는다.
- Audit 저장 실패를 무시하지 않는다.
- Support Bundle은 allowlist와 Masking을 사용한다.

## 10. SQL·DB

- SQL은 Owner Resource Catalog에 둔다.
- `SELECT *`와 무제한 Query를 금지한다.
- Sort/Filter Column과 Index를 함께 검토한다.
- MariaDB·PostgreSQL·Oracle 논리 결과를 같게 한다.
- Migration은 source/install/upgrade/rollback/verify Chain을 유지한다.
- Generated/Vendor SQL 일부만 수정하지 않는다.
- Seed와 Test Data를 구분한다.

## 11. Cache

- Key에 Tenant·Namespace를 포함한다.
- TTL·Payload·SCAN 범위를 검증한다.
- Fast Signal을 정본으로 사용하지 않는다.
- Durable Event 저장→Apply→Checkpoint 순서를 유지한다.
- Namespace Evict는 제한된 SCAN과 Lock/Fencing을 사용한다.
- Process Kill·Signal Loss Reconcile Test를 둔다.

## 12. Batch

- JobParameter Dictionary와 Identifying 여부를 문서화한다.
- Reader Sort Key와 Checkpoint를 일치시킨다.
- Writer는 Chunk Transaction 또는 Idempotency를 사용한다.
- Stop/Restart/Abandon/Reprocess 의미를 섞지 않는다.
- Partition은 Lease·Fencing을 사용한다.
- Center-Cut은 Execution-scope 조치만 허용한다.
- Agent 응답 유실을 성공으로 기록하지 않는다.

## 13. Frontend·ADM/BZA

- Generated Client만 사용하고 Raw URL 호출을 만들지 않는다.
- Route Registry와 expectedOperationIds를 정본으로 사용한다.
- Loading·Empty·Error·UNKNOWN·PARTIAL 상태를 분리한다.
- Button은 상태·Permission·Version·Approval 조건을 반영한다.
- 화면 성공 표시는 Owner 재조회와 Audit를 기준으로 한다.
- Browser E2E에 권한·Timeout·응답 유실·부분 적용을 포함한다.

## 14. Gateway

- Route Definition과 Applied State를 분리한다.
- HMAC Canonicalization·Nonce·Audience·Body Hash를 고정한다.
- SSRF와 TLS Negative Test를 둔다.
- Retry는 Idempotency 가능한 오류에만 적용한다.
- Publish는 Validate·Approve·ACK/NACK·LKG를 사용한다.
- Drift와 Partial Apply를 Target별로 복구한다.

## 15. Test

| Test | 필수 범위 |
|---|---|
| Unit | 상태 규칙·Validation·Hash·Codec·Policy |
| Contract | Public Port·Local/Remote·OpenAPI·Generated Client |
| Integration | DB·Broker·Cache·Secret·Object·External Adapter |
| Concurrency | Version·Idempotency·Lease·Fencing·Duplicate |
| Fault | Timeout·Response loss·Process kill·Partial apply |
| Browser | Field·Button·Permission·Error·Recovery |
| Vendor | MariaDB·PostgreSQL·Oracle Fresh/Upgrade/Rollback |
| Release | Fresh Consumer·Publication·SBOM·Provenance |

### 15.1 기능별 Test Pyramid

| Test | 검증 |
|---|---|
| Domain Unit | 상태전이·계산·Validation·결정표 |
| Application | 권한·Version·Idempotency·Transaction·Audit |
| Persistence | Query·Index·CAS·Migration·Vendor SQL |
| Contract | Local/Remote·OpenAPI·Generated Client·Message Schema |
| Integration | DB·Broker·File·HTTP/TCP·Secret/Cache Provider |
| Browser | Route·Field·Button 조건·403/409/Timeout/Unknown |
| Fault | Response Loss·Process Kill·Partial Target·Audit/Outbox 실패 |
| Recovery | Restart·Reprocess·Reconcile·Rollback·Restore |
| Compatibility | Fresh Consumer·N/N-1·3 DB Vendor·Artifact Mode |
| Security | AuthN/Z·Scope·Masking·MFA·HMAC·SSRF·TLS |

Test 이름과 Evidence는 Requirement/Scenario·Source SHA·Owner/Consumer와 연결한다. Mock만으로 외부 Runtime·Process Kill·다중 Instance 결과를 대체하지 않는다.

## 16. Build·Publication·Supply Chain

- Gradle Wrapper와 Stack/BOM Version을 고정한다.
- Remote/Offline Repository Mode를 검증한다.
- Artifact Checksum·Signature·SBOM·Provenance를 생성한다.
- Fresh Consumer에서 Public Artifact만으로 Build한다.
- 선택하지 않은 Provider Dependency가 포함되지 않는지 검사한다.
- Release와 Rollback Artifact를 함께 보존한다.

## 17. Code Review

Reviewer는 Owner·Consumer·호출 경로·계약·DB/Message/Config·OpenAPI/Frontend·Batch·ADM/BZA·Sample·문서를 확인한다. “내 소유 파일만 수정했다”는 이유로 간접 호출 영향과 회귀를 생략하지 않는다.

타 Owner 수정이 필요하면 exact path와 Root Cause를 Integration Owner에게 요청한다.

### 17.1 Review 질문

1. 이 변경의 State/Contract Owner와 모든 직접·간접 Consumer는 누구인가?
2. Public API/SPI·DTO·Schema·Message·Config·Generated Client가 바뀌는가?
3. 정상 경로 외에 중복·Version 충돌·Timeout·응답 유실·부분 실패가 있는가?
4. Retry가 허용되는 조건과 대사 Key는 무엇인가?
5. 업무 Row·Audit·Outbox/Ledger가 같은 Transaction에 참여해야 하는가?
6. 권한·Data Scope·Masking·Reason·Approval이 어디에서 강제되는가?
7. MariaDB·PostgreSQL·Oracle·Migration·Rollback·Verify가 일치하는가?
8. ADM/BZA/Gateway/Batch 화면과 Operation이 같이 바뀌는가?
9. Fault/Recovery/Compatibility Test가 실제 실패 조건을 재현하는가?
10. 운영 인계·Runbook·문서·Evidence가 같은 SHA를 가리키는가?

## 18. 금지 Pattern

- Owner DB 직접 수정.
- Raw URL·수기 Generated DTO.
- Version 없는 상태 덮어쓰기.
- Timeout 후 Blind Retry.
- `SELECT *`·Wildcard 전체 삭제.
- Secret/PII Log.
- Audit best effort.
- Job-scope Center-Cut 일괄 재처리.
- Fast Signal 정본화.
- 화면 숨김만으로 권한 처리.
- Provider SDK Public 노출.
- Test하지 않은 결과를 성공으로 기록.

## 19. 문서 표준

기능 장은 업무 결과, 선택 기준, 역할·권한, 결정값, 결과물, 단계, 입력/Default/범위, 정상 판정, 오류/동시성/응답 유실/부분 실패, 복구, 관측/Audit, EDU, 고객 변경/CPF 보호, 운영 인계를 포함한다.

목차 번호는 문서 전체에서 단조 증가하며 같은 설명을 여러 장에 복제하지 않는다. Route/Property/API 목록만으로 완료 처리하지 않는다.

## 20. Definition of Done

1. Source·SQL·API·Config·Frontend·Test·문서가 같은 계약이다.
2. 실제 Consumer가 연결됐다.
3. 정상·오류·경계·동시성·응답 유실·부분 실패·복구 Test가 있다.
4. Permission·Masking·Reason·Approval·Audit가 있다.
5. 3 DB Vendor와 Local/Remote 영향을 판정했다.
6. ADM/BZA/Gateway/Batch 운영 절차가 있다.
7. Migration·Upgrade·Rollback·Backup 영향이 있다.
8. Evidence와 기준 SHA를 남겼다.

## 21. Reviewer 질문집

- 이 기능으로 고객이 무엇을 끝낼 수 있는가?
- 누가 상태를 소유하고 누가 소비하는가?
- 중복·동시성·Timeout·응답 유실 때 상태는 무엇인가?
- 성공을 어떤 원장·화면·Audit로 판정하는가?
- 일부 Target만 성공하면 어떻게 복구하는가?
- Provider/DB Vendor/Topology를 바꿔도 계약이 유지되는가?
- 운영자가 Source 없이 Runbook을 실행할 수 있는가?
- Rollback 뒤에도 데이터와 Consumer가 호환되는가?
