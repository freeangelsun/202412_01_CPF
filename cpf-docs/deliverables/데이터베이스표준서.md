## 1. 기본 원칙

- 논리 Table·Column·상태·Constraint를 Canonical Model로 정의한다.
- Vendor Script는 문법이 달라도 업무 의미가 같다.
- Table과 Query의 Owner·Consumer를 기록한다.
- Current Row·History·Ledger·Audit를 목적별로 분리한다.
- Migration은 Fresh Install·Upgrade·Verify·Rollback/Forward Recovery를 가진다.

## 2. Naming

| 대상 | 규칙 | 예 |
|---|---|---|
| Table | System Prefix + 업무 명사 | `PAY_METHOD` |
| PK | Table + `_ID` 또는 업무 Key | `METHOD_ID` |
| Index | `IX_<TABLE>_<PURPOSE>` | `IX_PAY_METHOD_CUST_STATUS` |
| Unique | `UK_<TABLE>_<PURPOSE>` | `UK_PAY_IDEMPOTENCY_KEY` |
| Check | `CK_<TABLE>_<PURPOSE>` | `CK_PAY_METHOD_STATUS` |
| FK | `FK_<CHILD>_<PARENT>` | 명시적 Owner 경계 안에서 사용 |

## 3. 공통 Column

- ID.
- Status.
- Version.
- Created/Updated UTC.
- Actor 또는 Created By.
- Deleted/Effective Date는 업무 정책에 따라.
- Secret·PII는 분류·암호화·Masking 정책.

## 4. 상태·History

Current Row를 수정할 때 History와 Audit를 같은 Transaction에 기록한다. 물리 삭제가 감사·복구 요구와 충돌하면 상태 전이와 Retention Job을 사용한다.

## 5. Idempotency·Attempt

Idempotency Table은 Key, Request Hash, Owner Operation, Result Snapshot, Expiry를 저장한다. Attempt Table은 Target, Attempt No, Payload Hash, Dispatch, Response, Result 상태를 저장한다.

원본 Attempt를 수정해 성공으로 바꾸지 않고 후속 Reconciliation Decision을 연결한다.

## 6. Outbox·Inbox

- Outbox: Event ID·Type·Key·Schema·Payload·Status·Attempt.
- Inbox: Event ID·Consumer ID·Status·Result.
- DLQ: 원본 Event·오류·Attempt·Replay Approval.
- Checkpoint: Consumer·Last Event·Version.

## 7. Paging·Cursor

Sort Key는 유일하고 변경되지 않아야 한다. Timestamp만 사용하지 않고 Tie-breaker ID를 추가한다. Vendor별 문법이 달라도 동일 Sort와 Boundary를 사용한다.

## 8. MariaDB

- `datetime(6)` 또는 제품 정본 형식.
- `varchar` Charset·Collation 명시.
- DDL Transaction 특성을 고려한 Migration.
- `limit` Paging과 Cursor Query 검증.

## 9. PostgreSQL

- `timestamp with time zone` 사용 의미를 명확히 한다.
- `jsonb`는 Schema·Index·크기 정책이 있을 때 사용한다.
- Transactional DDL과 Lock 영향을 검토한다.
- `fetch first` 또는 `limit` 정본 Query를 관리한다.

## 10. Oracle

- Identifier 길이·Type Mapping.
- `timestamp with time zone` 또는 승인된 UTC 저장 규칙.
- Sequence·Identity 정책.
- DDL Commit 특성과 Rollback 제한.
- Paging과 Batch Bind 검증.

## 11. Migration Lifecycle

1. Baseline·Backup.
2. Precondition.
3. Schema 변경.
4. Data Backfill.
5. Constraint·Index.
6. Verify.
7. Application Canary.
8. Drift Check.
9. Rollback 또는 Forward Recovery.

## 12. Expand·Migrate·Contract

Mixed Version 배포에서는 새 Column·Table을 먼저 추가하고 양쪽 Version이 읽을 수 있게 한다. Data Migration 뒤 Consumer 전환을 확인하고 마지막에 Legacy를 제거한다.

## 13. Drift

- Schema Object.
- Column Type·Nullability.
- Constraint·Index.
- Migration History·Checksum.
- Seed·Reference Data.
- Query ID·Resource Hash.

Drift를 운영 DB에서 직접 고치지 않고 정본 Script와 비교한다.

## 14. Backup·Restore

Backup에는 업무 Row뿐 아니라 Batch Metadata, Outbox·Inbox·Attempt·Audit·Approval·Object Metadata를 포함한다. Restore 뒤 Row Count·금액·Hash·Foreign Key·Event Checkpoint를 대사한다.

## 15. DB 장애 Runbook

### Deadlock

- Victim Transaction과 Query ID 확인.
- Retryable 여부와 한도.
- Lock 순서·Index·Batch Size 보정.
- 중복 부작용·Idempotency 대사.

### Connection Pool 고갈

- Active·Idle·Wait·Leak.
- Slow Query·외부 호출 포함 Transaction.
- 신규 Traffic 제한.
- Pool 복구 뒤 Timeout Operation 대사.

### Partial Migration

- 적용 Object·History·Checksum 확인.
- 추가 DDL 금지.
- Forward Recovery 또는 Restore 선택.
- Application Version과 호환성 확인.

### Replica Lag·Failover

- Read-after-write 요구와 Routing.
- Promotion 시점.
- Outbox·Batch·Lease 상태.
- Failback Drift.

## 부록 B. Migration Lifecycle

1. Expand: 새 Column/Table/Index를 기존 Version과 호환되게 추가한다.
2. Backfill: Bounded Batch로 채우고 Checkpoint·건수·오류를 기록한다.
3. Dual Read 검증: 새/구 Path 결과를 비교하되 정본은 하나만 유지한다.
4. Switch: Consumer를 새 계약으로 전환하고 Metric·Audit로 확인한다.
5. Contract: 구 Column/Index 제거는 호환 Window 뒤 별도 Version으로 수행한다.
6. Rollback 불가 DDL이면 Forward Recovery Script와 Backup Restore 조건을 사전에 승인한다.
