## 1. 지원 Vendor와 정본

CPF는 MariaDB·PostgreSQL·Oracle Vendor Pack을 유지한다. Canonical Model과 Query Contract가 논리 정본이며 Vendor SQL은 구문 차이를 구현한다.

각 Vendor는 `source`, `install`, `migration`, `rollback`, `runtime`, `verify`, `pack.json`을 갖는다.

## 2. Schema·Table Ownership

Table은 단일 Owner Module이 소유한다. 다른 Module은 Public API/Port를 통해 접근한다. 공통 Schema라고 해서 모든 Module이 직접 Write하지 않는다. Cross-schema Query가 필요하면 Read Model·Event·API를 설계한다.

## 3. Naming

- Table/Column/Index/Constraint/Sequence 이름은 프로젝트 Naming Rule을 따른다.
- PK, FK, UK, IX 목적을 이름에 드러낸다.
- 상태 Column은 코드 의미와 Check Constraint/Reference를 맞춘다.
- Timestamp는 기준 Timezone과 정밀도를 명시한다.
- Reserved Word와 Vendor별 Case Folding을 피한다.
- Boolean 표현과 Y/N 사용을 Schema 단위로 일관되게 한다.

### 3.1 Naming 기록표

| Object | 원칙 | Review |
|---|---|---|
| Schema | Module/업무 Owner가 드러나는 이름 | 공유 Write Owner가 생기지 않는가 |
| Table | Entity/Ledger/History/Attempt 의미 | 상태·보존·Purge 책임이 명확한가 |
| PK | 기술 PK와 업무 Key 분리 | 외부 노출·Migration 영향 |
| FK | Owner 내부 참조 중심 | Cross-schema 결합 여부 |
| UK | 업무 중복 규칙 표현 | Null/Collation/Vendor 의미 |
| Index | Filter·Join·Sort·Cursor 순서 | Write 비용·중복 Index |
| Constraint | 상태·범위·참조 무결성 | Error Mapping 가능성 |
| Sequence | 용도·Cache·증가·DR | 다중 Instance·Gap 의미 |
| Migration | Version·Owner·목적 | 순서·Checksum·Rollback |

식별자 길이는 3 Vendor 제한을 함께 고려하고 축약어 사전을 문서화한다.

## 4. 공통 Column

| Column 성격 | 목적 |
|---|---|
| 식별자 | 업무/기술 PK, 외부 식별자 분리 |
| Version/Revision | Optimistic Lock·Policy CAS |
| 상태 | Lifecycle·처리 결과 |
| 생성/수정 시각·주체 | 운영·Audit 연결 |
| Transaction/Operation | Log·Audit·대사 연결 |
| Idempotency/Request Hash | 중복·Replay·Conflict |
| Soft Delete/Use | 이력·참조 보호 |
| Tenant/Data Scope | 격리·권한 Query |

### 4.1 논리 Table 예시

```sql
CREATE TABLE pay_method (
    method_id            VARCHAR(64)  NOT NULL,
    customer_id          VARCHAR(64)  NOT NULL,
    status_code          VARCHAR(32)  NOT NULL,
    row_version          BIGINT       NOT NULL,
    last_operation_id    VARCHAR(128) NOT NULL,
    created_at           TIMESTAMP    NOT NULL,
    created_by           VARCHAR(64)  NOT NULL,
    updated_at           TIMESTAMP    NOT NULL,
    updated_by           VARCHAR(64)  NOT NULL,
    PRIMARY KEY (method_id)
);
```

예시는 논리 Column 의미를 설명하며 실제 Vendor DDL·이름·Type은 Generator와 Vendor Pack을 따른다. 상태 변경 Query는 `row_version` CAS와 영향 건수 검증을 사용한다.

## 5. Index·Query

Index는 실제 Filter·Join·Sort·Cursor에 맞춘다. Leading Column과 Selectivity를 검토한다. 대량 목록은 안정 Sort Key를 사용한다. Pagination Query는 Vendor별 구문이 달라도 같은 순서와 Cursor 의미를 반환한다.

Query에는 최대 기간·Page Size·Sort whitelist를 둔다. 운영 조회가 업무 Write Lock을 오래 점유하지 않게 한다.

### 5.1 Query 설계 절차

1. 검색 Field·필수 조건·최대 기간·Sort를 API/화면과 함께 정한다.
2. 데이터 분포와 Selectivity를 확인한다.
3. Equality→Range→Sort/Cursor 순으로 Index 후보를 만든다.
4. Covering 여부와 Write/Storage 비용을 평가한다.
5. MariaDB·PostgreSQL·Oracle 실행계획을 비교한다.
6. 첫 Page·중간 Cursor·마지막 Page·동일 Sort 값·대량 Offset을 Test한다.
7. Masking/Data Scope 조건이 Index를 무력화하지 않는지 확인한다.
8. Query Timeout과 최대 Row를 정하고 ADM Export는 별도 Job으로 분리한다.

### 5.2 Cursor 계약

Cursor는 정렬 Key 전체와 방향·조건 Hash를 포함한다. 조건이 바뀐 Cursor를 재사용하지 않는다. 동일 Timestamp가 가능한 경우 PK를 보조 Sort로 사용한다.

## 6. Optimistic Lock·CAS

Update/Delete/Approve/Retire는 `WHERE id=? AND version=?` 또는 Revision 조건과 영향 건수 1을 사용한다. 0건이면 Not Found와 Version Conflict를 구분하기 위해 최신 Row를 조회한다. 충돌 시 마지막 Write Wins로 덮지 않는다.

## 7. Idempotency Ledger

| Column | 의미 |
|---|---|
| owner_scope | Key 충돌 범위 |
| idempotency_key | 요청 중복 Key |
| request_hash | Payload 동일성 |
| status | REQUESTED/RUNNING/SUCCEEDED/FAILED/UNKNOWN |
| result_snapshot | Replay 결과 |
| operation_id | 운영 조회 Key |
| created_at/expires_at | 보존·Purge |
| version | 동시성 |

Unique는 Owner Scope + Key를 사용한다. 같은 Key/다른 Hash는 Conflict다.

### 7.1 처리 Algorithm

1. Owner Scope·Idempotency Key로 Ledger를 조회/생성한다.
2. 신규면 Request Hash·REQUESTED·Operation ID를 저장한다.
3. 기존 Key면 Request Hash를 비교한다.
4. Hash가 다르면 Conflict다.
5. SUCCEEDED/FAILED 확정 결과면 Result Snapshot을 Replay한다.
6. RUNNING/UNKNOWN이면 Operation 상태를 반환하고 중복 실행하지 않는다.
7. 업무 Transaction 결과와 Ledger 상태/Result를 함께 확정한다.
8. Retention/Purge는 업무 재시도 Window와 감사 기준 뒤에 수행한다.

### 7.2 Index/Constraint

Owner Scope + Idempotency Key Unique, Operation ID 조회 Index, Status+Updated At 운영 Index, Expires At Purge Index를 논리 기준으로 검토한다.

## 8. Outbox·Inbox·Attempt

Outbox는 Event Key·Schema·Payload Hash·Publish 상태·Attempt를, Inbox는 Consumer·Message ID·처리 상태·Result를 소유한다. 외부 HTTP/Gateway/Agent Attempt는 Target·Dispatch·Response·Result 상태를 기록한다. 원본 Row를 삭제하거나 결과를 덮지 않고 Attempt를 추가한다.

## 9. Cache Invalidation Ledger

3 Vendor에 Cache Invalidation Source/Install/Migration/Runtime/Verify/Rollback을 유지한다.

권장 논리 Column:

- `event_id`: 단조 증가 Event.
- `event_key`: 요청 중복/추적 Key.
- `tenant_id`, `namespace`, `cache_key`.
- `version`, `reason`, `requested_by`, `created_at`.
- Consumer Checkpoint Table: `consumer_id`, `last_event_id`, `updated_at`, `version`.

Coordinator는 Event Append→Cache Apply→Checkpoint 순서다. Process Kill 후 checkpoint 이후 Event를 다시 읽는다.

### 9.1 Event/Checkpoint Transaction

Event Key는 중복 요청을 식별하고 Event ID는 Consumer 순서를 제공한다. Consumer별 Checkpoint는 마지막 적용 Event ID를 저장한다. Cache 적용이 실패하면 Checkpoint를 전진하지 않는다. Fast Signal 실패는 Ledger Event를 삭제하거나 성공으로 치환하지 않는다.

### 9.2 Process Kill Recovery

1. Consumer ID의 Checkpoint를 읽는다.
2. 더 큰 Event ID를 Batch Size만큼 조회한다.
3. Key 또는 Namespace Evict를 적용한다.
4. 적용 성공 뒤 Checkpoint를 해당 Event ID로 갱신한다.
5. Max Batches까지 반복하고 남은 Lag를 Metric/ADM에 표시한다.
6. 동일 Event Replay가 Cache 결과를 훼손하지 않는지 확인한다.

## 10. Common Calendar·Template

Calendar SQL은 find/range/insert/update/delete와 Version 조건을 제공한다. 변경 Row·Audit·durable refresh outbox를 같은 `cmnTransactionManager`에 둔다.

Template SQL은 insert draft, approve, retire, supersede, active/version/audit query를 제공한다. Lifecycle과 expectedRevision CAS를 적용한다.

## 11. Generated Domain 표준 Schema

Generator는 업무 Table과 Idempotency Ledger, History/Audit/Outbox 선택을 생성한다. 고객은 Field와 업무 상태를 바꾸되 Version·Audit·Idempotency·Migration 구조를 제거하지 않는다.

Business Table에는 PK, 업무 Key, 상태, Version, Created/Updated, Transaction/Operation, Soft Delete/Use를 업무 요구에 맞게 둔다.

## 12. Batch Metadata·업무 대사

Spring Batch Metadata를 직접 임의 수정하지 않는다. JobInstance·Execution·StepExecution·ExecutionContext와 업무 결과 Table을 대사한다. Ghost Recovery는 Process·Heartbeat·Lease가 확인된 뒤 표준 Operation으로 상태를 전이한다.

## 13. BZA·Approval Schema

조직·발령·사용자·Role·Permission에는 유효기간·상태·Version을 둔다. Approval Policy는 Code+Version, Step/Target, 유효기간을 갖는다. Approval Document는 Policy/Participant Snapshot, Payload Hash, Idempotency Key, History를 보존한다.

## 14. Gateway Schema

Server Group·Member·Binding·Security·Publish/LKG·Attempt/Idempotency·Connection Test를 분리한다. Definition Version과 Target Applied State를 같은 Column으로 덮지 않는다. Target별 ACK/NACK/UNKNOWN과 Checksum을 저장한다.

## 15. Migration Chain

Canonical Model/Query → Generator/Template → Source SQL → Fresh Install → Seed → Upgrade Migration → Runtime Query → Verify → Rollback/Forward Recovery → 3 Vendor Test → Repository/Service/API/Frontend/Batch/ADM 문서 순서로 갱신한다.

### 15.1 파일별 책임

| 경로 | 책임 |
|---|---|
| `source` | 현재 Schema 전체의 정본 DDL |
| `install` | 빈 Schema 설치 순서 |
| `migration` | 이전 Version→현재 Version 변경 |
| `rollback` | 허용된 역변경 또는 복구 보조 |
| `runtime` | Runtime Query/Procedure/운영 SQL |
| `verify` | Object·Constraint·Data·Version 검증 |
| `pack.json` | 파일 순서·Checksum·Compatibility |

### 15.2 변경 연쇄

Canonical Model과 Query Contract를 먼저 바꾼 뒤 Generator/Template, 3 Vendor Source/Install/Migration/Rollback/Runtime/Verify, Seed, Repository/Service, API/OpenAPI/Client, Frontend/Batch/ADM/BZA, Test·Drift·문서를 한 Change Set으로 검토한다.

## 16. Fresh Install

빈 Schema에서 Install 순서를 실행하고 Table·Index·Constraint·Sequence·Seed·Schema Version을 검증한다. Runtime 계정으로 CRUD·Lock·Paging·Audit·Outbox/Inbox·Cache Ledger를 실행한다. 이전 Test Data가 없는지 확인한다.

## 17. Upgrade

현재 Version과 Migration Chain을 계산하고 Backup·Restore를 확인한다. 격리 Schema에서 DDL Lock·Data 변환·Application 호환을 검증한다. 적용 후 Verify와 Drift를 실행한다. 중간 실패 시 자동 계속하지 않는다.

### 17.1 Upgrade Runbook

1. 현재 Schema/Application/Artifact Version과 Drift를 기록한다.
2. Migration 대상·예상 시간·Lock·Data 변환·Disk 증가를 계산한다.
3. Backup과 격리 Restore를 확인한다.
4. N/N-1 Application Compatibility와 배포 순서를 확인한다.
5. Maintenance/Traffic/Batch/Scheduler 계획을 승인한다.
6. Migration 파일 Checksum과 실행 계정을 확인한다.
7. 단계별 실행 결과와 영향 건수를 기록한다.
8. Verify·Runtime CRUD·업무 Smoke·성능을 확인한다.
9. 실패 시 Rollback 가능 지점 또는 Forward Recovery를 선택한다.
10. Schema Version·Application Target·Drift·Backup 복구점을 인계한다.

## 18. Rollback·Forward Recovery

Transactional DDL 지원 여부와 Data 변환 가역성을 판정한다. Rollback Script는 정확한 Migration Version을 대상으로 한다. 비가역 변경은 Forward Recovery와 LKG Application 호환을 설계한다. Wildcard Drop이나 전체 Schema Reset을 운영 복구로 사용하지 않는다.

### 18.1 결정표

| 변경 | Rollback 가능성 | 권장 복구 |
|---|---|---|
| 신규 Nullable Column/Index | 비교적 높음 | 구 App 호환 확인 후 제거/유지 |
| Column Rename/Type 변경 | Data/구 App 의존 | Expand-Migrate-Contract |
| 대량 Data 변환 | 복구 비용 큼 | Backup/PITR 또는 Forward Fix |
| Constraint 강화 | 기존 Data 영향 | 사전 정리 후 적용, 실패 Row 보존 |
| Table 분할/병합 | 양방향 동기화 필요 | 단계적 Dual-read/write 후 전환 |
| Encryption 변경 | Key/Version 의존 | Dual-read·재암호화·검증 |

Rollback Script가 존재한다는 이유만으로 실행하지 않는다. 현재 Data와 구 Application의 읽기/쓰기 가능성을 먼저 확인한다.

## 19. Backup·Restore·DR

Backup Manifest에 DB Version·SCN/LSN/시각·Checksum·Encryption·연관 Object/File·Artifact Version을 기록한다. Restore 후 Row Count·업무 합계·Audit·Outbox/Inbox·Attachment Hash·Approval Snapshot·Gateway LKG를 대사한다.

## 20. Drift

정본 SQL/Pack Manifest와 실제 Schema의 Table·Column·Type·Default·Constraint·Index·Sequence·Version을 비교한다. Manual DDL은 Drift로 기록하고 정본 Migration으로 흡수한다. Drift를 “현재 운영값”으로 방치하지 않는다.

## 21. 성능·용량·Retention

대량 Table의 증가율·Row Size·Index Size·Partition/Purge·Backup Window를 기록한다. Idempotency·Outbox/Inbox·Audit·Attempt·Log Metadata는 업무·감사 보존 기준에 따라 Archive/Purge한다. Purge 자체도 Batch·Audit·대사 대상이다.

## 22. 보안·권한

Schema Owner, Migration, Runtime, Read-only, Backup 계정을 분리한다. 개인정보 Column은 암호화/Masking/접근 Audit를 적용한다. Secret을 SQL Script에 넣지 않는다. 운영 Query는 Data Scope와 Row Limit을 사용한다.

## 23. Vendor 동등성

| 항목 | 확인 |
|---|---|
| Type | 숫자·문자·Timestamp·LOB 의미 |
| Identity/Sequence | 생성·동시성·Rollback |
| Paging | Offset/Cursor Sort 결과 |
| Upsert | 중복·Version·영향 건수 |
| Lock | Nowait/Skip locked/Timeout |
| JSON | 저장·Index·비교 의미 |
| DDL Transaction | 실패·Rollback 전략 |
| Case/Collation | Code·검색·Unique |
| Timestamp | Timezone·정밀도 |
| Error Mapping | Constraint·Deadlock·Timeout |

### 23.1 동등성 Test Set

- 동일 Seed에서 Query 결과 Row·정렬·Cursor 일치.
- Version CAS 성공/충돌 영향 건수 일치.
- Unique/FK/Check/Not-null 오류가 표준 Error로 매핑.
- Deadlock·Lock Timeout·Nowait/Skip-locked 의미 일치.
- Timestamp/Timezone·소수점·문자/Collation 결과 일치.
- JSON/LOB Size·Encoding·Index Query 일치.
- Fresh Install·N-1 Upgrade·Rollback/Forward Recovery·Restore 일치.
- Idempotency·Outbox/Inbox·Cache Ledger·Batch Metadata 동작 일치.

Vendor별 성능 수치는 다를 수 있지만 업무 결과와 상태·오류 의미는 같아야 한다.

## 24. DB Review Checklist

1. Owner와 Consumer가 명확한가?
2. Query·Index·Paging이 일치하는가?
3. Version·Idempotency·Audit·Outbox가 필요한가?
4. 3 Vendor SQL과 Verify가 있는가?
5. Fresh·Upgrade·Rollback·Restore 경로가 있는가?
6. 부분 Migration과 Drift 복구가 있는가?
7. Security·Retention·Capacity가 정의됐는가?
8. API·Generated Client·Frontend·Batch Consumer가 함께 갱신됐는가?
