## 1. 공식 지원 Vendor

| Vendor | Pack Path | Lifecycle |
|---|---|---|
| Oracle | `cpf-tools/db/vendor/oracle` | install → migration → verify → rollback → reapply |
| PostgreSQL | `cpf-tools/db/vendor/postgresql` | install → migration → verify → rollback → reapply |
| MariaDB | `cpf-tools/db/vendor/mariadb` | install → migration → verify → rollback → reapply |

## 2. Naming 표준

- Table: 업무 또는 플랫폼 Owner Prefix + 단수 명사
- PK: `<entity>_id` 또는 정본이 정의한 식별자
- FK: 참조 Entity PK 이름과 일치
- 상태: `status_code`
- 낙관적 Version: `version_no`
- 생성/수정 시각: UTC Timestamp와 명시적 Timezone 변환
- 생성/수정 Actor: `created_by`, `updated_by`
- Soft Delete가 필요한 경우 `deleted_at`, `deleted_by`, `delete_reason`

Oracle 식별자 길이 제약을 고려해 세 Vendor에서 동일한 논리 이름을 사용한다.

## 3. 공통 Column

| Column | Type 목적 | 필수 조건 |
|---|---|---|
| ID | 불변 식별자 | PK, Not Null |
| STATUS_CODE | 상태 전이 | Check/Reference 검증 |
| VERSION_NO | 동시성 | Update 시 +1 |
| CREATED_AT/BY | 생성 감사 | Insert 시 필수 |
| UPDATED_AT/BY | 변경 감사 | Update 시 필수 |
| IDEMPOTENCY_KEY | 중복 방지 | 업무 범위 Unique |
| CORRELATION_ID | 추적 | 외부/비동기 흐름 |
| LEASE_UNTIL | Worker 소유 | Claim 대상에 적용 |
| FENCING_TOKEN | Stale Writer 차단 | Lease 갱신 시 증가 |

## 4. 상태·이력 Table

업무 원장과 실행 이력을 분리한다. Outbox, Inbox, Notification, File Transfer, Runtime Change, Batch Execution은 Current State와 Attempt/Audit History를 보존한다. `UNKNOWN` Row를 성공 Row로 덮어쓰지 않고 Reconcile 결과와 근거를 추가한다.

## 5. Index 표준

- PK/Unique: 업무 불변 식별자와 멱등성 Key
- Search: 실제 ADM/API 검색 조건 순서
- Worker Claim: `status_code`, `next_attempt_at`, `lease_until`
- Trace: `transaction_id`, `trace_id`, `correlation_id`
- Audit: `occurred_at`, `actor_id`, `resource_type`
- 대량 Partition Key가 있는 경우 Leading Column과 조회 패턴을 맞춘다.

Index 추가 전 세 Vendor 실행계획과 쓰기 비용을 검토한다.

## 6. Lock·동시성

- 온라인 상태 변경은 `WHERE id=? AND version_no=?`를 사용한다.
- Queue Worker는 Skip Locked 또는 Vendor 동등 전략과 Lease를 함께 사용한다.
- DB Lock만으로 장시간 외부 호출을 보호하지 않는다.
- Lease 만료 후 Reclaim 시 Fencing Token이 이전 Worker의 Update를 거부해야 한다.
- Scheduler/Batch는 동일 Trigger·Execution에 대한 Unique Constraint를 둔다.

## 7. Migration 구성

각 DB 보유 기능은 다음 구조를 갖는다.

```text
<owner>/src/main/resources/db/
  mariadb/migration/
  mariadb/rollback/
  postgresql/migration/
  postgresql/rollback/
  oracle/migration/
  oracle/rollback/
```

파일은 순번, 목적, Forward/Rollback 대응을 유지한다. 적용 순서와 Checksum은 DB Pack Manifest에서 관리한다.

## 8. Fresh·Upgrade·Rollback 절차

1. Empty Schema인지 확인하고 Object Count를 기록한다.
2. Install Pack을 적용한다.
3. Verify Query로 객체·Column·Index·Seed를 확인한다.
4. Upgrade Migration을 적용한다.
5. 업무 Read/Write Smoke Test를 수행한다.
6. Backup Manifest를 확인한다.
7. 승인된 환경에서 Rollback 또는 Forward Recovery를 수행한다.
8. Reapply와 Drift Scan을 실행한다.
9. Before/After Object Count와 Checksum을 Evidence로 보존한다.

## 9. Query 표준

- SQL Parameter는 Bind Variable을 사용한다.
- Query ID와 Owner를 명시한다.
- Update/Delete는 영향 Row Count를 검증한다.
- Pagination은 안정적인 정렬 Key를 가진다.
- Cursor/Chunk 조회는 재시작 Key를 보존한다.
- 개인정보 Column은 최소 조회하고 Export 시 Masking한다.
- Vendor 함수는 전용 Catalog로 캡슐화한다.

## 10. Backup·Restore

Backup은 DB 파일만이 아니라 Schema Version, Migration Checksum, Artifact Version, Config Hash, Secret Reference와 함께 Manifest를 만든다. Restore 후 Readiness, Row Count, Sequence/Identity, Scheduler Lock, Outbox/Inbox 상태, Audit 연속성을 확인한다.

## 11. Drift 판정

Drift는 기대 Manifest와 실제 Object/Column/Index/Constraint/Checksum 차이다. 미승인 Drift가 발견되면 배포를 중단하고 임의 DDL로 수정하지 않는다. 원인 Commit, Owner, 영향, 복구 Script와 재검증 결과를 기록한다.

## 12. 성능·용량

- 대량 Table은 보존 기간과 Purge/Archive 절차를 정한다.
- Outbox/DLQ/Audit는 상태·시간 기준 Index와 Partition 전략을 적용한다.
- Connection Pool 변경은 Runtime Control Preview와 Capacity Metric을 확인한다.
- 실행계획은 대표 정상·최대 건수·경계 조건에서 비교한다.
- Batch Commit Interval은 재처리 비용과 Lock 시간을 함께 고려한다.

## 13. 검증 명령

```powershell
./gradlew.bat checkQa39DbParity --no-daemon
./cpf-tools/scripts/invoke-cpf-qa34-db-runtime-matrix.ps1 -Root . `
  -MariaDbProfile <profile> -PostgreSqlProfile <profile> -OracleProfile <profile> `
  -MariaDbUpgradeProfile <profile> -PostgreSqlUpgradeProfile <profile> -OracleUpgradeProfile <profile> `

```

운영 데이터가 있는 환경에서는 `-AllowDestructiveRollback`을 사용하지 않는다.
