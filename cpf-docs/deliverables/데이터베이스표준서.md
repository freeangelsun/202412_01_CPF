## 1. Vendor와 Lifecycle

| Vendor | Pack | Lifecycle |
|---|---|---|
| Oracle | `cpf-tools/db/vendor/oracle` | install → migration → verify → rollback/forward → reapply |
| PostgreSQL | `cpf-tools/db/vendor/postgresql` | install → migration → verify → rollback/forward → reapply |
| MariaDB | `cpf-tools/db/vendor/mariadb` | install → migration → verify → rollback/forward → reapply |

## 2. Ownership

Table·View·Sequence·Query·Migration은 단일 Owner를 가진다. 다른 Domain은 Owner Public Contract로 접근하고 DB Object를 직접 참조하지 않는다.

## 3. Naming

- Table: Owner Prefix + 명확한 단수 명사
- PK/FK: 동일 논리 식별자
- 상태: `status_code`
- Version: `version_no`
- 생성/수정: `created_at/by`, `updated_at/by`
- Soft Delete: `deleted_at/by`, `delete_reason`
- Idempotency: `idempotency_key`
- Correlation: `transaction_id`, `correlation_id`
- Worker: `lease_until`, `fencing_token`, `claim_owner`

Oracle 식별자 길이를 포함해 세 Vendor에서 논리 이름을 유지한다.

## 4. 공통 Column

| 목적 | 필수 조건 |
|---|---|
| 불변 ID | PK·Not Null |
| 상태 | 허용 값과 전이 검증 |
| Version | 조건 Update와 증가 |
| Audit | UTC 시각·Actor |
| Idempotency | 업무 범위 Unique |
| Correlation | Transaction/Trace 연결 |
| Lease/Fencing | 다중 Worker Stale Writer 차단 |
| Error | Code·Message·Last Attempt |
| Checksum | File·Payload·Config 무결성 |

## 5. 상태와 이력

Current State와 Attempt/Audit History를 분리한다. UNKNOWN을 SUCCESS로 덮어쓰지 않고 Resolution History와 Evidence Reference를 추가한다.

Outbox, Inbox, Notification, File Transfer, Runtime Change, Batch Execution은 Attempt·Lease·Next Retry·Last Error를 보존한다.

## 6. Index

- PK/Unique: ID·Idempotency·Trigger/Execution 중복 차단
- 검색: 실제 API/ADM 조건 순서
- Worker Claim: Status·Next Attempt·Lease Until
- Trace: Transaction·Trace·Correlation
- Audit: Occurred At·Actor·Resource
- Batch/대량: Partition Key·Stable Cursor

Index 추가 전 세 Vendor 실행계획과 쓰기 비용을 검토한다.

## 7. Lock·동시성

온라인 Update는 `WHERE id=? AND version_no=?`를 사용한다. Worker Claim은 Vendor 동등 Skip Locked/Lease 전략과 Fencing Token을 함께 사용한다. 외부 호출 동안 DB Lock을 유지하지 않는다.

## 8. Query

- Bind Variable
- 명시 Column
- 안정적 Order와 Pagination/Cursor
- 영향 Row Count 검증
- 최소 개인정보 조회와 Masking
- Vendor 함수는 Catalog로 캡슐화
- 대량 조회는 Streaming과 Bounded Memory
- Query ID·Owner·Timeout·Expected Rows 기록

## 9. Migration Chain

Canonical Model → Generator/Template → Vendor SQL/Mapper → Fresh Install → Seed → Upgrade → Rollback/Forward Recovery → Repository/Service → API/OpenAPI → Frontend/Batch/ADM → Test/Drift/Evidence 순서로 영향 범위를 처리한다.

## 10. Fresh Install

1. Empty Schema와 계정 권한 확인
2. Install 적용
3. Object·Column·Index·Constraint·Seed Verify
4. Application Readiness
5. Read/Write Smoke
6. Drift Scan
7. Schema Version·Checksum 보존

## 11. Upgrade

1. 현재 Version·Object Count·Checksum 기록
2. Backup Manifest
3. Migration 적용
4. Verify와 실행계획 확인
5. Mixed Version Smoke
6. Consumer Test
7. Drift 0 확인

## 12. Rollback과 Forward Recovery

Rollback 가능 여부를 Migration별로 정의한다. 데이터 손실 위험이 있거나 비가역이면 Forward Recovery를 사용한다. Rollback 후 이전 Artifact·Config와 Schema 호환을 확인한다.

## 13. Backup·Restore

Manifest에는 DB Backup, Schema Version, Migration Checksum, Artifact, Config Hash, Secret/Certificate Reference, Queue/Topic 정책을 포함한다.

Restore 후 Row Count, Identity/Sequence, Scheduler Lock, Outbox/Inbox/DLQ, 진행 중 Batch, Audit와 Readiness를 확인한다.

## 14. Drift

기대 Manifest와 실제 Object·Column·Index·Constraint·Checksum 차이를 Drift로 정의한다. 미승인 Drift가 있으면 배포를 중단하고 원인 Commit·Owner·영향·복구 Script를 기록한다.

## 15. 성능·용량

대표 정상·최대·경계 건수에서 실행계획을 비교한다. Outbox·Audit·DLQ·Batch Metadata의 보존·Partition·Purge를 정의한다. Commit Interval은 Lock 시간과 재처리 비용으로 결정한다.

## 16. 보안

DB 계정은 Owner별 최소 권한을 사용한다. Credential은 Secret Provider로 공급한다. 개인정보 Column은 암호화·Masking·접근 Audit와 Retention을 적용한다. 운영 Dump·Backup 접근을 통제한다.
