## 1. 공식 Vendor

```text
mariadb
postgresql
oracle
```

H2·MySQL·MSSQL 등은 공식 Vendor Evidence로 사용하지 않는다. Keycloak 같은 외부 제품의 내부 DB도 CPF 업무 DB 검증에 포함하지 않는다.

## 2. 변경 순서

```text
Requirement·Data Model
→ Canonical Schema·Metadata·Runtime Query
→ Generator·Golden Template
→ Vendor Source
→ Install·Migration·Recovery Pack
→ Mapper·Repository
→ Service·API·UI
→ Test·Runtime·Evidence
```

Vendor SQL부터 직접 수정하지 않는다.

## 3. DB Ownership

| 데이터 | Owner | 금지 |
|---|---|---|
| 업무 원장 | 해당 Domain | ADM/BZA/Gateway 직접 갱신 |
| Idempotency Ledger | 업무 또는 Reliability Owner | 공통 전역 테이블에 무분별 통합 |
| Outbox/Inbox/Dedup | Messaging Reliability Owner | Provider별 중복 Schema |
| Batch Execution·Checkpoint | Batch Owner | 업무 Domain이 Batch 메타 직접 수정 |
| Gateway Route·Attempt | Gateway Owner | Core 또는 Domain DB에 혼합 |
| BZA 조직·권한·결재 | BZA Owner | 업무 상태를 BZA에 저장 |
| ADM 운영 작업 | ADM Owner | 업무 원장을 ADM DB에 복제해 정본화 |

## 4. Naming

- Table·Column·Index·Constraint 이름은 중앙 Naming Rule을 따른다.
- 예약어와 Vendor별 길이 제한을 검사한다.
- 업무 키와 기술 키를 구분한다.
- Timestamp는 의미와 Time Zone을 명시한다.
- 상태는 임의 문자열보다 승인된 Code와 Check Constraint를 사용한다.

## 5. 최소 업무 테이블 계약

- PK와 업무 Unique Key
- 생성·수정 시각과 주체
- Version
- 상태와 상태 변경 사유
- Transaction ID 또는 Operation ID
- Logical Delete 사용 시 삭제 상태·시각·주체
- 조회·대사에 필요한 Index
- 금액·건수·Checksum 등 업무 검증 값

## 6. Idempotency Ledger

필수 컬럼:

```text
idempotency_key
request_hash
operation_id
state
result_code
result_reference
created_at
expires_at
version
```

규칙:

1. 같은 Key와 같은 Request Hash는 기존 결과를 반환한다.
2. 같은 Key와 다른 Hash는 Conflict다.
3. 처리 중 Lease를 사용하면 Fencing Token을 저장한다.
4. `UNKNOWN_RESULT`는 Reconcile Key와 마지막 확인 시각을 남긴다.
5. Logical Delete 후 재사용 정책을 명시한다.

## 7. Outbox·Inbox·DLQ

### Outbox

- 업무 Commit과 같은 Transaction에서 기록한다.
- Claim Owner, Lease Until, Fencing Token, Attempt를 가진다.
- Publish Receipt와 Payload Hash를 기록한다.

### Inbox/Dedup

- Message ID·Consumer·Effect Key를 Unique로 보호한다.
- 업무 효과와 같은 Transaction에서 처리 완료를 기록한다.

### DLQ/Replay

- Failure Class·Reason·Attempt·First/Last Failure를 기록한다.
- Replay는 승인·Reason·대상 범위·Dry Run 결과를 남긴다.

## 8. Migration Pack

각 Version은 다음을 포함한다.

```text
install
upgrade
rollback 또는 forward-recovery
verify
reapply 검증
checksum
manifest
```

빈 Rollback 파일은 허용하지 않는다. 역변경이 불가능하면 데이터 손실 가능성, 중단 시간, Forward Recovery 단계를 명시한다.

## 9. Fresh Provision

각 Vendor 검증 전 조건:

```text
Dedicated QA Database/Schema
CPF Object count = 0
기존 사용자 DB 사용 금지
사용자 DB Reset/Drop 금지
```

절차:

1. 전용 QA Database/Schema를 생성한다.
2. CPF Object 수가 0인지 확인한다.
3. Install Pack을 적용한다.
4. Mandatory Metadata·Seed를 검증한다.
5. 임의 Generated Domain을 생성해 Migration을 적용한다.
6. Runtime Query를 실행한다.
7. Reapply가 무변경인지 확인한다.
8. 다른 Hash가 같은 Version으로 들어오면 실패하는지 확인한다.

## 10. Upgrade·Recovery

| 단계 | 확인 |
|---|---|
| Pre-check | 현재 Version·Checksum·Drift·Backup |
| Upgrade | 단계별 Transaction·Lock·Timeout |
| Runtime | Mapper·Query·Index·Constraint |
| Failure | 중간 종료 후 Resume/Forward Recovery |
| Rollback | Schema·Data·Artifact 호환 |
| Mixed Version | Rolling 구간의 Old/New App 호환 |

## 11. Vendor 차이

### MariaDB

- Charset·Collation을 명시한다.
- Online DDL 가능 여부와 Lock을 검증한다.
- `AUTO_INCREMENT`와 Sequence 호환 전략을 문서화한다.

### PostgreSQL

- Schema Search Path를 명시한다.
- Sequence·Identity·JSON/Index 사용 범위를 통제한다.
- Transactional DDL과 Extension 의존성을 확인한다.

### Oracle

- User와 Schema 경계를 명시한다.
- Identifier 길이, Sequence, Tablespace, LOB를 검증한다.
- DDL Auto-commit과 복구 전략을 반영한다.

논리 모델을 Vendor 기능에 맞춰 세 갈래로 분기하지 않는다. 불가피한 차이는 Capability Manifest에 기록한다.

## 12. Transaction·Lock

- Isolation Level은 업무 불변조건에 맞춘다.
- Long Transaction에서 외부 호출을 수행하지 않는다.
- Batch Chunk Size와 Commit Interval을 대사 기준과 함께 정한다.
- Pessimistic Lock은 Timeout과 Deadlock Retry를 정의한다.
- Optimistic Lock은 Expected Version과 현 상태를 응답한다.

## 13. Data Security

- 계정은 Admin·Migration·Runtime·ReadOnly를 분리한다.
- Runtime 계정에 DDL 권한을 주지 않는다.
- Sensitive Column은 암호화·Tokenization·Masking 정책을 연결한다.
- SQL Log와 Evidence에 개인정보·Secret을 남기지 않는다.
- Export는 Permission·Data Scope·Reason·Approval·Audit를 적용한다.

## 14. Backup·Restore

Backup만 성공으로 판정하지 않는다.

1. Backup ID·시각·DB Version·Schema Version을 기록한다.
2. 격리된 Restore 대상에 복원한다.
3. Object·Row Count·Checksum을 비교한다.
4. Application Runtime Query와 주요 업무 대사를 수행한다.
5. 복원 후 Secret·Endpoint·Sequence·Scheduler를 재설정한다.
6. RPO/RTO 결과와 미충족 원인을 기록한다.

## 15. Drift

- Canonical Manifest와 실제 Object를 비교한다.
- 누락·추가·형식·Default·Constraint·Index·Privilege 차이를 분류한다.
- 임의 수정은 자동 덮어쓰지 않고 Owner 승인 후 Repair Pack을 적용한다.

## 16. 검증 Matrix

각 Vendor는 다음을 독립 실행한다.

```text
Fresh Provision
Install
Mandatory Seed
Generated Domain
Runtime Query
Upgrade
Rollback/Forward Recovery
Reapply
Different-hash Conflict
Optional Pack On/Off
Drift

```

기준 Commit에서는 위 전체 Runtime Evidence를 확인하지 않았으므로 검증 상태는 `미검증`이다.
