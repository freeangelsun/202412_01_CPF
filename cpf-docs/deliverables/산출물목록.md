## 3. QA38 목표와 문서 반영 원칙

QA38는 다음 방향을 요구한다.

1. `cpf-core`는 기술 중립 Public API·SPI와 순수 Java 최소 구현만 유지한다.
2. `cpf-common`은 Code·Calendar·Message·Template·업무 Validation 같은 업무 공통만 유지한다.
3. 선택 Runtime은 `cpf-starter-<capability>-<provider>`로 분리한다.
4. Generator는 Versioned Capability Profile을 승인된 Leaf Starter 목록으로 해석하고 `resolvedStarters`와 Version Lock을 남긴다.
5. Kafka 외 RabbitMQ·Jakarta JMS·IBM MQ·TCP·SFTP·Notification을 실제 Consumer·장애·운영·시험까지 닫는다.
6. DB는 MariaDB·PostgreSQL·Oracle 각각 Empty 환경에서 Install·Upgrade·Rollback/Forward Recovery·Reapply·Drift·Backup/Restore를 검증한다.
7. 문서에는 목표와 현재 구현을 혼합하지 않는다.

## 5. 추적성 규칙

각 기능은 최소 다음 연결을 가져야 한다.

```text
Canonical Requirement
→ QA38 Requirement ID
→ Owner Module·Package
→ Public API/SPI/Internal
→ 실제 Consumer
→ Config·SQL·Migration
→ Unit·Contract·Integration·Negative Test
→ Runtime·Fault·Reconcile Evidence
→ 산출물 설명
→ 대상 역할별 매뉴얼 절차
```

Interface, Dependency, Marker, Sample, Swagger 노출만으로 개발 상태를 `완료`로 표시하지 않는다.

## 7. 완료 판정

문서 현행화는 다음 조건을 모두 만족해야 완료로 판정한다.

- 최신 exact SHA가 기록돼 있다.
- Source·SQL·API·Config·Frontend·Script·Test와 문서의 양방향 대조가 끝났다.
- 대상 독자가 다른 사람의 설명 없이 자신의 작업을 수행할 수 있다.
- 정상·오류·부분 실패·응답 유실·재시도·대사·Rollback이 설명돼 있다.
- 실행하지 않은 Runtime·DB·Browser·다중 인스턴스·장애 시험은 `미검증`으로 남아 있다.
- 공식 문서 수와 경로를 위반하지 않는다.
- ZIP은 Repository Root 상대경로를 유지하며 관리 범위 밖 파일을 포함하지 않는다.

## 8. 공식 사용자 매뉴얼 1차 구조

사용자 승인에 따라 사용자 매뉴얼의 목표 구조를 다음과 같이 적용한다.

```text
README.md
cpf-docs/guides/00_프레임워크안내.md
cpf-docs/guides/01_개발자매뉴얼.md
cpf-docs/guides/02_배치개발매뉴얼.md
cpf-docs/guides/03_ADM매뉴얼.md
cpf-docs/guides/05_플랫폼운영매뉴얼.md
cpf-docs/guides/90_CPF_Starters_매뉴얼.md
cpf-docs/guides/91_CPF_Tools_매뉴얼.md
cpf-docs/guides/92_CPF_Gateway_매뉴얼.md
cpf-docs/guides/95_CPF_BZA_매뉴얼.md
```

ADM은 새 제품을 개발하는 문서가 아니라 업무 연동 담당자와 권한별 사용자가 같은 운영 제품을 이용하는 문서로 통합한다. `CPF Starters`와 `CPF Tools`는 처음 사용하는 개발자가 선택·설정·실행·오류 대응까지 수행할 수 있도록 별도 매뉴얼로 관리한다.

현재 `cpf-docs/specification/CPF_DOCUMENTATION_STANDARD.md`의 과거 9개 문서 목록과 차이가 있으므로 해당 정본의 목록·문서 수 Gate·링크 검사는 담당 Owner가 사용자 승인 구조로 현행화해야 한다. 이 작업에서는 읽기 전용 정본을 수정하지 않는다.
