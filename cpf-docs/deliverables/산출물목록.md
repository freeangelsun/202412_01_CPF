## 이 문서 세트를 처음 보는 분께

### 30초 설명

**CPF는 어떤 제품인가?**

**CPF(코어 플랫폼 프레임워크, Core Platform Framework)는 회사의 업무 시스템을 만들고 운영할 때 매번 반복되는 기술 기반을
하나의 제품으로 제공하는 프레임워크입니다.**

예를 들어 회원·계약·심사·결제·정산 같은 업무 시스템을 새로 만들 때는 업무 화면과 규칙만 필요한
것이 아닙니다. 로그인과 권한, 요청 추적, 오류 처리, 중복 방지, 다른 시스템과의 연결, 대량 배치,
운영 화면, 장애 확인, 감사 기록, DB 변경과 복구도 함께 필요합니다.

CPF는 이런 공통 영역을 프로젝트마다 처음부터 다시 만들지 않도록 제품 구조와 개발 규칙, 실행
기능, 운영 화면, 복구 절차와 검증 기준을 함께 제공합니다. 고객은 CPF 위에 자기 회사만의 업무
규칙과 화면을 구현합니다.

### 쉬운 비유

회사가 새로운 업무 시스템을 하나의 건물이라고 보면, 고객 업무는 그 건물 안에서 실제로 수행할
일입니다. CPF는 건물마다 반복해서 필요한 출입 통제, 전기·통신, 안전 설비, 관리실, 점검 기록과
복구 절차에 해당합니다.

CPF가 고객의 업무 자체를 대신 결정하지는 않습니다. 대신 고객 업무가 **같은 기준으로 만들어지고,
서로 연결되며, 운영되고, 장애 후 복구될 수 있는 기반**을 제공합니다.

### 왜 필요한가

시스템이 한두 개일 때는 프로젝트마다 공통 기능을 별도로 만들어도 운영할 수 있습니다. 그러나
시스템과 개발팀이 늘어나면 다음 문제가 반복됩니다.

- 같은 인증·오류·배치·운영 기능을 여러 프로젝트가 다시 만듭니다.
- 시스템마다 상태 이름, 로그 형식과 장애 대응 방법이 달라집니다.
- 응답을 받지 못했을 때 실제 처리가 됐는지 판단하기 어렵습니다.
- 운영자가 소스코드와 DB를 직접 분석해야 다음 조치를 결정할 수 있습니다.
- 공통 기능을 변경할 때 여러 업무 시스템에 예상하지 못한 영향이 생깁니다.
- API·DB·시험·문서와 실제 배포 산출물이 서로 다른 시점을 가리킵니다.

CPF는 이 문제를 조직이 함께 사용하는 제품 기준으로 바꾸려는 프레임워크입니다.

### CPF는 무엇이고 무엇이 아닌가

| 구분 | 설명 |
|---|---|
| CPF가 제공하는 것 | 업무 시스템 공통 개발 기반, 온라인·메시지·파일·대량·정기 처리, API 출입구, 운영 화면, 조직·권한·결재 기반, 보안·감사, DB 변경·복구, 빌드·검증 기준 |
| 고객이 만드는 것 | 고객 고유의 상품·계약·심사·결제·정산 규칙, 업무 화면, 승인 정책과 데이터 의미 |
| CPF가 아닌 것 | 특정 산업의 완성 업무 패키지, 화면만 조립하는 무코드(No-code) 도구, API 출입구 하나만을 의미하는 Middleware |
| 도입 방식 | 필요한 기본 기능과 선택 제품을 정하고 작은 대표 업무에서 검증한 뒤 조직 범위로 확장 |
| 성공 조건 | 고객 업무 책임 주체, 운영 조직, 보안·DB 정책과 검증 기준을 CPF 계약에 맞춰 함께 정함 |

### CPF 제품 구성

CPF는 하나의 라이브러리가 아니라 업무 시스템의 생명주기를 연결하는 여러 제품과 도구의 집합입니다.

<p align="center">
  <img src="png/CPF제품구성쉬운지도.png" width="96%" alt="비전문가도 이해할 수 있는 CPF 제품 구성 지도" />
</p>

| 구성 | 쉬운 설명 | 고객이 얻는 결과 |
|---|---|---|
| 업무 개발 기반 | 새 업무의 기본 구조와 공통 기술 기능 | 개발팀이 공통 기반보다 업무 규칙에 집중 |
| 스타터 제품군 관리 | 정식 루트 프로젝트 `cpf-stater`가 선택 기능 모듈의 등록·목록·통합 검증 기준을 관리 | 선택 기능 누락과 전체 의존성 전파를 방지하고 프로젝트 구조를 명확히 유지 |
| 대량·정기 처리 플랫폼(배치 플랫폼) | 정기·대량·분할 처리를 개발하고 운영하는 제품 | 중지·재시작·재처리·대사까지 같은 절차로 수행 |
| 운영관리 화면(ADM) | 시스템 상태를 조회하고 권한에 따라 조치하는 운영 화면 | 소스코드를 처음부터 분석하지 않고 상태와 조치 이력을 확인 |
| 업무관리 기반(BZA) | 조직·사용자·권한·결재를 제공하는 선택 제품 | 업무 시스템마다 관리 기반을 다시 만드는 범위를 줄임 |
| API 출입구(게이트웨이) | API 요청이 들어오는 공통 출입구 역할의 선택 제품 | 인증·라우팅·제한·게시와 장애 상태를 공통 관리 |
| DB·빌드·검증 도구 | DB 설치·변경·복구와 배포 결과를 관리 | 어떤 소스코드의 어떤 버전이 설치됐는지 확인 |

### 스타터는 무엇인가

스타터는 **특정 공통 기능을 업무 프로젝트에 선택해서 연결하는 설치 단위**입니다. 모든 업무가 모든
스타터를 사용할 필요는 없습니다. 필요한 기능만 선택해야 의존성·설정·장애 영향·보안 검토 범위가
불필요하게 커지지 않습니다.

- `cpf-stater`: 스타터 제품군의 루트 등록·목록·통합 검증을 관리하는 정식 프로젝트
- `cpf-starters/`: 기능별 스타터의 실제 소스코드가 있는 상위 폴더
- `:cpf-starter-*`: 고객 업무가 필요한 기능만 선택해 연결하는 개별 Gradle 프로젝트

#### 어떤 기능이 필요할 때 어떤 스타터를 선택하는가

| 필요한 기능 | 선택 스타터 | 사용하는 때 | 함께 확인할 것 | 사용하지 않는 경우 |
|---|---|---|---|---|
| ADM·BZA 관리자 로그인과 세션 보호 | `:cpf-starter-security` | `/adm/**`, `/bza/**`, `/api/bza/**`의 브라우저 세션·CSRF·자격 증명 보호가 필요할 때 | JDBC `DataSource`, Spring Session, `CPF_BFF_CREDENTIAL_VAULT`, 암호화 키, 허용 출처(Origin), 쿠키 정책 | 일반 고객 API가 무상태 토큰 인증만 사용하고 관리자 세션 기능이 필요하지 않을 때 |
| Kafka 이벤트 발행·수신 | `:cpf-starter-messaging-kafka` | 업무 상태 변경을 이벤트로 전달하거나 `CpfBrokerClient`·`CpfBrokerBridgePort`가 필요할 때 | `KafkaTemplate`, Topic, `cpf.broker.type=KAFKA`, 확인 시간, 페이로드 제한, 멱등성 | 같은 애플리케이션 내부 호출만 있고 Kafka를 사용하지 않을 때 |
| 반복 조회 결과·참조 데이터 캐시 | `:cpf-starter-cache` | 로컬·Caffeine·Redis 캐시와 무효화가 필요할 때 | `cpf.cache.provider`, 크기·페이로드 제한, Redis 연결·비밀값, 원본 조회·무효화·장애 정책 | 업무 원장을 캐시에만 저장하거나 조회량이 작아 운영 비용이 더 큰 경우 |
| 로그·지표·분산 추적 연결 | `:cpf-starter-observability` | 요청·이벤트·배치·외부 호출을 지표와 추적로 연결할 때 | `ObservationRegistry`, 수집기 연결, 거래 식별자, 민감정보 레이블 금지 | 단위 시험처럼 관측 수집이 필요하지 않은 좁은 실행 범위 |
| 원격 호출 시간초과·회로 차단·격리 | `:cpf-starter-resilience` | 외부기관·원격 서비스 장애가 고객 요청 전체로 확산되지 않게 할 때 | `CircuitBreakerFactory`, 시간초과, 회로 차단, 격리(Bulkhead), 재시도 가능 조건, `UNKNOWN_RESULT` 대사 | 동일 JVM 내부 호출 또는 재실행 시 중복 결과가 생기는 명령을 무조건 재시도할 때 |
| 기능을 사용자·조직·환경별로 단계 적용 | `:cpf-starter-featureflag` | 배포와 기능 공개 시점을 분리하거나 제한된 대상에 먼저 적용할 때 | OpenFeature 제공자, 기본값, 대상 문맥, 변경 승인·감사, 제공자 장애 시 동작 | 권한 판정이나 영구 업무 규칙을 기능 플래그로 대신하려는 경우 |
| 비밀번호·토큰·인증서·암호화 키 조회 | `:cpf-starter-secret` | 고객이 승인한 비밀값 저장소에서 실행 시점에 값을 가져와야 할 때 | 하나 이상의 `CpfSecretProvider`, 제공자 신원·권한, 교체·폐기, 로그·검증 증거 노출 금지 | 비밀값을 소스코드·일반 설정·문서에 직접 저장하려는 경우 |

#### 코어와 스타터를 구성하는 세 가지 방식

업무 영역은 스타터를 반드시 하나씩만 등록할 필요는 없습니다. CPF의 목표 구조는 개별 스타터와
승인된 스타터 프로필을 함께 제공하는 것입니다.

<p align="center">
  <img src="png/CPF스타터등록방식.png" width="96%" alt="개별 스타터 등록과 스타터 프로필 묶음 등록 방식" />
</p>

| 등록 방식 | 사용하는 경우 | 장점 | 주의사항 |
|---|---|---|---|
| 코어 전용 | 실행 기술이 필요 없는 최소 업무 계약·시험 | 가장 가벼운 의존성과 빠른 기동 | 보안·관측·외부 연계가 필요한 실행 환경에는 부족할 수 있음 |
| 개별 등록 | 한두 기능만 필요하거나 업무별 구성이 다른 경우 | 실제 실행 의존성과 설정이 가장 명확함 | 같은 조합을 업무 프로젝트마다 반복 선언할 수 있음 |
| 스타터 프로필 | 여러 업무가 같은 기능 조합을 반복 사용하는 경우 | 승인된 조합을 한 번에 선택하고 누락을 줄임 | 불필요한 필수 기능이 있으면 프로필을 변형하지 말고 개별 등록 사용 |

스타터 프로필은 모든 스타터를 담는 통합 모듈이 아닙니다. `cpf-stater`가 관리하는 빌드 시점 선택
목록이며, 실행 코드·자동 설정·설정값·DB 책임은 각 `:cpf-starter-*`가 계속 소유합니다. 프로필을
선택하면 빌드 결과와 배포 목록에는 최종적으로 확장된 개별 스타터가 표시되어야 합니다.

현재 기준 Git에는 프로필 등록을 구현한 Gradle 문법·프로젝트·플러그인이 없으므로 정확한 좌표나
설정 키는 문서에서 만들지 않습니다. 아래 프로필은 제품 목표이며 구현 상태는 `미구현`입니다.

#### 업무 상황별 스타터 프로필 목표

<p align="center">
  <img src="png/CPF스타터묶음선택지도.png" width="96%" alt="업무 상황별 스타터 프로필의 필수·조건부 구성" />
</p>

| 문서상 프로필 이름 | 필수 포함 | 조건부 포함 | 적용 상황 |
|---|---|---|---|
| 관리자 웹 운영 | 보안, 관측 | 비밀값 | ADM·BZA 세션, 운영 추적, 자격 증명 저장소가 함께 필요한 경우 |
| 외부기관 연계 | 복원력, 관측 | 비밀값 | 시간초과·회로 차단·추적이 필요하고 인증 정보가 있을 수 있는 경우 |
| 이벤트 처리 | Kafka 메시지, 관측 | 비밀값, 복원력 | 이벤트 발행·수신·재처리와 브로커 인증 또는 후속 원격 호출이 있는 경우 |
| 분산 캐시 | 캐시, 관측 | 비밀값 | Redis 캐시·무효화·관측이 필요하고 연결 비밀값이 있는 경우 |
| 단계적 기능 공개 | 기능 플래그, 관측 | 비밀값 | 대상별 공개 결과를 확인하고 외부 제공자 인증이 필요한 경우 |
| 외부 호출 배치 | 관측, 복원력 | 비밀값 | 장시간 배치에서 외부 호출·장애 격리·인증 정보가 필요한 경우 |

표의 프로필 이름은 문서상 명칭이며 아직 Gradle 프로젝트 ID나 배포 좌표가 아닙니다. 필수 포함은
프로필 목적을 성립시키는 스타터이고, 조건부 포함은 실제 제공자·인증·외부 제품·업무 흐름이 있을
때만 추가합니다.

#### 개별 등록과 프로필 선택 절차

1. 필요한 기능·외부 제품·DB 자원·운영·복구 조건을 먼저 적습니다.
2. 스타터가 한두 개이거나 기존 프로필과 구성이 다르면 개별 등록을 사용합니다.
3. 승인된 프로필의 필수 구성과 맞으면 프로필 등록을 사용합니다.
4. 조건부 스타터는 실제 Redis·Kafka 인증·외부 제공자·원격 호출 조건이 있을 때만 포함합니다.
5. 프로필에 필요 없는 필수 스타터가 있으면 임의 제외하지 않고 개별 등록으로 전환합니다.
6. 두 프로필 이상을 사용하면 개별 스타터의 합집합으로 확장하고 중복은 하나로 정규화합니다.
7. 같은 스타터의 버전·제공자·설정 조건이 충돌하면 빌드 또는 통합 검증에서 실패시킵니다.
8. 실행 의존성 목록·배포 목록·SBOM에는 프로필과 확장된 개별 스타터를 함께 기록합니다.

#### 개별 등록에서 자주 사용하는 조합

| 업무 상황 | 기본 검토 조합 | 선택 이유 |
|---|---|---|
| ADM·BZA 운영 화면 | 보안 + 관측 + 비밀값 | 관리자 세션 보호, 운영 추적, 자격 증명·암호화 키 공급 |
| 외부기관 API 연계 | 복원력 + 관측 + 비밀값 | 시간초과·회로 차단, 호출 추적, 인증 정보 공급 |
| 이벤트 기반 업무 | Kafka 메시지 + 관측 | 발행·수신·재처리와 거래 추적 연결 |
| 조회량이 큰 기준정보 | 캐시 + 관측 | 캐시 효과·오류·무효화 상태를 함께 확인 |
| 단계적 기능 공개 | 기능 플래그 + 관측 | 대상별 공개 결과와 오류·사용량 확인 |
| 외부 호출이 있는 배치 | 관측 + 복원력 + 비밀값 | 장시간 처리의 추적, 외부 장애 격리, 자격 증명 공급 |

아래 조합은 프로필 구현을 사용하지 않거나 업무별 구성이 다른 경우의 개별 등록 출발점입니다. 실제 의존성은 업무 요구와 실행 환경을 기준으로 선택합니다. 예를 들어 Redis
캐시가 고객 관리 비밀값을 사용하면 캐시와 비밀값이 함께 필요할 수 있지만, 로컬 캐시에는 비밀값을
자동으로 추가하지 않습니다.

### 일반 공통 라이브러리와 무엇이 다른가

일반적인 공통 라이브러리는 개발할 때 필요한 코드를 재사용하는 데 초점을 둡니다. CPF는 코드 재사용에
더해 실행, 운영, 장애 복구, DB 변경, 배포와 검증까지 제품 범위로 연결합니다.

| 비교 항목 | 일반 공통 라이브러리 | CPF |
|---|---|---|
| 주 목적 | 반복 코드와 Utility 재사용 | 업무 시스템의 개발·실행·운영·복구 기준을 제품으로 제공 |
| 제공 범위 | 개발 시 참조하는 클래스와 함수 중심 | 라이브러리, 실행 프로그램, 운영 화면, DB 패키지, 빌드·검증 도구 |
| 업무 확장 | 공통 소스코드를 직접 수정하거나 프로젝트별 구조 사용 | 생성기와 모듈 책임 경계로 새 업무 추가 |
| 운영 | 별도 운영 화면과 절차를 프로젝트가 구축 | 운영관리 화면(ADM)·업무관리 기반(BZA)·API 게이트웨이·배치 운영 경로 제공 |
| 장애 대응 | 로그 확인과 개별 재시도 구현에 의존 | 거래 식별자·시도 이력·결과 대사·재처리·복구 계약 |
| 데이터 변경 | SQL과 업그레이드 절차를 프로젝트별 관리 | 공통 기준·DB 제품별 패키지·DB 변경·복원 생명주기 |
| 공급·버전 | 파일이나 의존성 버전 중심 | BOM·플러그인·배포 산출물·목록 파일·검사값·소스코드 SHA 연결 |
| 검증·문서 | 프로젝트별 시험과 문서 방식 | 소스코드·API·SQL·시험·문서·검증 증거의 연결 기준 |

따라서 CPF 도입은 라이브러리 하나를 추가하는 작업보다 넓습니다. 고객의 개발 표준, 운영 역할, 보안,
DB와 배포 절차를 CPF 제품 계약과 어떻게 연결할지 함께 결정해야 합니다.

### 가벼운 코어와 선택 스타터 구조

CPF의 목표 구조는 `cpf-core`에 모든 기능을 모으는 방식이 아닙니다. 모든 업무가 반드시 공유해야 하는
최소 계약만 코어에 남기고, 실행 기술과 선택 기능은 스타터로 분리해 각 업무 영역이 필요한 것만
사용하도록 관리합니다.

<p align="center">
  <img src="png/CPF경량코어스타터분리.png" width="96%" alt="cpf-core를 최소 계약으로 가볍게 하고 선택 기능을 스타터로 분리하는 목표 구조" />
</p>

| 코어에 남길 책임 | 스타터로 분리할 책임 |
|---|---|
| 거래·작업 식별자와 요청 문맥의 최소 자료형 | DB 접근 구현과 Mapper 자동 설정 |
| 공통 오류·결과·멱등성·처리 기한·결과 미확정 계약 | Web 필터·API 문서 UI·원격 호출 Client |
| 공개 API·SPI와 구현 중립적인 확장 지점 | Kafka·캐시·관측·복원력·보안·비밀값·기능 플래그 |
| 업무 영역이 공통으로 사용하는 최소 애너테이션·자료형 | 파일 압축·대용량 처리·배치 실행 기술 |
| 스타터 구현이 지켜야 할 계약과 호환성 기준 | 특정 OSS의 실행 환경·자동 설정·설정값 |

현재 기준 커밋의 `cpf-core/build.gradle`에는 MyBatis, AspectJ, Springdoc UI, 압축 라이브러리, 검증
구현과 여러 컴파일 경계가 함께 존재합니다. 이 항목들은 **분리 후보**이며 아직 새 스타터 이름이나
완료 상태로 확정하지 않습니다. 실제 분리는 소스코드·실제 사용처·BOM·DB·시험을 함께 이관한 경우에만
완료로 판정합니다.

### CPF로 만들 수 있는 업무

<p align="center">
  <img src="png/CPF업무예시지도.png" width="96%" alt="CPF로 구현할 수 있는 대표 고객 업무 유형" />
</p>

CPF는 다음과 같은 고객 업무 결과를 만드는 데 사용할 수 있습니다.

- 조건 검색·목록·상세·등록·수정·상태 변경 API와 화면
- 승인·거절·취소·재개처럼 상태가 바뀌는 업무
- 중복 요청과 동시에 발생한 수정 충돌을 통제하는 업무
- Kafka 이벤트를 발행·소비하고 실패 메시지를 재처리하는 업무
- 외부 REST·전문·파일 연계와 응답 유실 이후 결과를 확인하는 업무
- 정기·대량·분할·원격 배치와 중단 후 재시작·재처리 업무
- 운영자가 상태를 조회하고 사유·승인과 함께 조치하는 ADM 연동
- 조직·사용자·권한·결재·첨부·알림이 필요한 BZA 기반 업무
- 여러 API를 공통 인증·라우팅·제한 정책으로 공개하는 게이트웨이 업무

### 하나의 업무가 처리되는 과정

처음 보는 분은 CPF를 모듈 이름으로 외우기보다, 고객 요청이 들어와 결과가 확정될 때까지의
과정으로 이해하는 편이 쉽습니다.

<p align="center">
  <img src="png/CPF업무전체여정.png" width="96%" alt="고객 요청부터 정상 결과와 장애 복구까지 이어지는 CPF 업무 전체 여정" />
</p>

1. 고객이나 외부기관이 업무 요청을 보냅니다.
2. CPF는 사용자의 신원과 권한, 입력값을 확인하고 요청을 추적할 식별자를 부여합니다.
3. 고객이 만든 업무 규칙이 실행되고 상태와 데이터가 저장됩니다.
4. 필요하면 이벤트·파일·배치나 다른 시스템 연계가 이어집니다.
5. 운영자는 ADM에서 상태·로그·처리 경로와 감사 기록을 확인합니다.
6. 정상 결과를 확정하거나, 응답 유실·부분 실패가 있으면 대사 후 재처리·복구합니다.

특히 요청을 보낸 뒤 응답을 받지 못한 경우, CPF는 이를 바로 실패로 단정하고 다시 실행하지 않는
원칙을 사용합니다. 같은 거래 식별자와 요청 내용, 처리 시도 이력을 이용해 실제 결과를 확인한 뒤
맞는 복구 방법을 선택합니다.

### 대표 업무 사례: 계약 변경 신청

고객이 계약 내용을 변경하는 간단한 업무를 CPF 관점으로 보면 다음과 같습니다.

| 단계 | 고객에게 보이는 일 | CPF와 고객 업무가 수행하는 일 | 확인 결과 |
|---:|---|---|---|
| 1 | 사용자가 변경 내용을 입력하고 신청 | API 출입구가 사용자와 요청 권한을 확인 | 요청이 허용되거나 권한 오류로 거절 |
| 2 | 신청이 접수됨 | 거래 식별자를 만들고 필수값·형식을 검사 | 같은 요청을 끝까지 추적할 기준 생성 |
| 3 | 계약 상태가 변경됨 | 고객 업무가 현재 버전과 변경 가능 조건을 확인하고 저장 | 변경 전·후 상태와 처리 버전 기록 |
| 4 | 관련 부서나 시스템에 전달됨 | 이벤트 또는 업무 API로 후속 처리를 요청 | 발행·수신·실패·재처리 이력 확인 |
| 5 | 운영자가 진행 상태를 확인 | ADM에서 거래·로그·추적·감사 기록 조회 | 어느 단계까지 처리됐는지 판단 |
| 6 | 응답 유실이나 일부 실패 발생 | 실제 계약 상태와 후속 처리 결과를 대사 | 재처리·보상·운영 확정 중 맞는 조치 선택 |

예를 들어 사용자가 완료 화면을 받지 못했다고 해서 같은 변경을 바로 다시 실행하면 중복 처리될 수
있습니다. CPF는 거래 식별자와 중복 방지 키, 저장된 계약 상태와 후속 처리 이력을 먼저 확인하도록
합니다. 실제 변경이 완료됐다면 결과만 다시 안내하고, 처리되지 않았다면 안전한 조건에서 재처리합니다.

이 사례에서 **계약을 어떤 조건으로 변경할 수 있는지**는 고객 업무가 결정합니다. CPF는 요청 추적,
권한, 중복 방지, 오류, 이벤트, 운영 조회와 복구 절차의 공통 기반을 제공합니다.

### CPF와 고객의 책임 경계

<p align="center">
  <img src="png/CPF고객책임경계.png" width="96%" alt="CPF가 제공하는 영역과 고객이 결정하는 영역" />
</p>

CPF는 고객 업무를 대신 소유하지 않습니다. 다음 경계를 먼저 합의해야 도입 이후 업그레이드와 장애
대응 책임이 명확해집니다.

| CPF가 공통으로 제공·관리 | 고객이 결정·소유 |
|---|---|
| 거래 식별자, 오류 의미, 중복 방지와 결과 대사 계약 | 업무 상태, 계산 규칙, 승인·취소·보상 기준 |
| 보안·감사·마스킹 적용 구조 | 사용자 역할, 데이터 접근 범위와 승인 조직 |
| 온라인·메시지·파일·배치 실행 기반 | 어떤 처리 방식을 어느 업무에 사용할지 |
| ADM·BZA·게이트웨이 공통 제품 기능 | 고객 전용 메뉴·업무 연계와 운영 역할 |
| 빌드·버전·배포 산출물·검증 증거 규칙 | 배포본 일정과 고객 인수 기준 |
| DB 변경·복구 생명주기 기준 | 고객 DB·백업·RPO/RTO와 운영 정책 |

확장하는 방식이 적합합니다.

### 도입 검토 질문

다음 질문에 여러 항목이 해당하면 CPF의 제품 기반 접근을 검토할 가치가 있습니다.

- 비슷한 공통 기능을 여러 프로젝트가 각각 만들고 있는가
- 온라인·메시지·파일·대량 처리가 한 업무 흐름에서 함께 사용되는가
- 장애 후 실제 처리 결과를 확인하거나 재처리·대사해야 하는가
- 운영·보안·감사 기준을 여러 시스템에서 같은 방식으로 적용해야 하는가
- 신규 업무를 추가할 때 기존 공통 소스코드 변경 위험이 큰가
- DB 설치·업그레이드·백업·복원 절차가 시스템마다 다른가
- 개발 결과와 문서·시험·배포 파일의 기준 버전을 맞추기 어려운가

이 질문은 도입을 자동 결정하는 점수표가 아닙니다. 현행 아키텍처와 운영 문제를 확인하고 첫
적용 범위를 정하기 위한 대화의 시작점입니다.

### 어떤 조직에 적합한가

CPF는 다음 조건이 있는 조직에서 가치가 큽니다.

- 여러 업무 시스템을 반복 구축하거나 장기간 확장해야 하는 조직
- 온라인·메시지·파일·배치·외부기관 연계가 함께 있는 조직
- 운영·보안·감사·장애 복구 기준을 시스템별이 아니라 조직 기준으로 맞추려는 조직
- Modular Monolith와 분리 서비스를 상황에 따라 선택해야 하는 조직
- 장애 결과 확인, 재처리와 업무 대사가 중요한 조직
- 프로젝트 결과를 다음 시스템에도 이어지는 제품 기반으로 전환하려는 조직

수명이 짧은 단일 기능 서비스이거나 운영·보안·복구 요구가 작고, 공통 제품을 유지할 조직적 책임이
없는 경우에는 CPF 전체 적용보다 필요한 구성요소만 검토하는 편이 적절할 수 있습니다.

R16은 R15의 개별 스타터 선택과 권장 조합을 다음 수준으로 보완했습니다.

도메인은 기능별 스타터를 하나씩 등록할 수 있고, 반복되는 승인 조합은 향후 프로필 하나로 선택할

### 2.2 R15 경량 코어·스타터 선택 가이드

R15는 `cpf-stater`의 정식 등록 설명에 다음 내용을 추가했습니다.

스타터 세분화 계획은 제품 방향으로 기록하되, 실제 소스코드와 배포 산출물이 없는 기능은 `미구현`으로
유지합니다. 기존 기능이 어느 스타터로 이동하는지와 호환성 정책이 확정된 뒤 문서의 현재 구현 표를
갱신합니다.

### 2.3 R14 `cpf-stater` 정식 프로젝트 합류

사용자 승인에 따라 저장소 루트의 `cpf-stater`를 제거 대상이나 임시 폴더로 보지 않고,
**CPF 스타터 제품군을 관리하는 정식 루트 프로젝트**로 합류시킵니다.

현재 원격 `master`의 기준 커밋 `1eda8e12fe123281748a4388938c62f11819da1e`에는 `cpf-stater` 등록이 아직 없으므로,
이 문서의 반영 상태와 Git 소스코드 상태를 다음과 같이 구분합니다.

| 항목 | 기준 커밋 상태 | 동일 푸시 목표 |
|---|---|---|
| 저장소 루트 경로 | `cpf-stater/` 미등록 | 정식 프로젝트 루트 경로로 추적 |
| Gradle 프로젝트 | `:cpf-stater` 미등록 | `settings.gradle`의 루트 프로젝트 항목으로 등록 |
| 기존 스타터 구현 | `cpf-starters/*`의 7개 선택 기능 모듈 등록 | 기존 경로와 개별 프로젝트 ID 유지 |
| 프로젝트 책임 | 별도 정본 없음 | 스타터 제품군 목록·등록·통합 검증·문서 연결 책임 |
| 실행 의존성 | 개별 `:cpf-starter-*`를 선택 사용 | `cpf-stater`가 모든 스타터를 실행 의존성으로 강제하지 않음 |
| 배포 산출물 | 기준 소스 없음 | 실제 `build.gradle`이 선언한 경우에만 BOM·게시·목록 파일에 포함 |

#### 이름과 경로를 혼동하지 않는 기준

| 구분 | 정확한 이름 | 역할 |
|---|---|---|
| 정식 루트 프로젝트 | `cpf-stater/`, `:cpf-stater` | 스타터 제품군 관리·등록·통합 검증 |
| 기존 구현 상위 폴더 | `cpf-starters/` | 7개 기능별 스타터 소스코드의 물리 경로 |
| 기능별 Gradle 프로젝트 | `:cpf-starter-security` 등 | 보안·Kafka·캐시·관측·복원력·기능 플래그·비밀값 구현 |

`cpf-stater`, `cpf-starters`, `cpf-starter-*`는 서로 다른 식별자입니다. 정식 이름 변경은
`settings.gradle`, 빌드, BOM, 배포 목록, 문서와 실제 사용처를 함께 이관하는 별도 변경으로 처리합니다.

## 8. 적용·변경 관리

### 8.1 적용 전

1. 저장소 루트에서 `git fetch origin master`를 실행합니다.
2. `HEAD`, `origin/master`, Working Tree 변경과 미추적 파일을 확인합니다.
3. 기존 `cpf-docs/deliverables/` 대상 59개 파일을 별도 경로에 백업합니다.
4. ZIP의 SHA-256과 파일 목록을 확인합니다.
5. ZIP을 저장소 루트에 풀어 동일 상대경로로 덮어씁니다.

### 8.2 적용 후

```powershell
git -c core.quotepath=false status --short -- cpf-docs/deliverables
git diff --name-status -- cpf-docs/deliverables
git diff --stat -- cpf-docs/deliverables
git diff --check -- cpf-docs/deliverables
```

### 8.3 되돌리기

적용 전에 만든 백업의 5개 Markdown과 54개 PNG를 동일 경로에 다시 복사합니다.
다른 작업자의 변경을 보호하기 위해 전체 디렉터리 삭제나 `git clean`을 사용하지 않습니다.

## 9. 독립 재검수 결과

R9 구조 검사는 통과했지만, 최신 소스코드와 다시 대조한 결과 다음 항목은 보완 없이 완료로 판정할 수 없습니다.

### 9.1 현재 사용 가능 범위

- 아키텍처·기술 규칙·복구 개념·빌드 방식의 설계 검토에는 사용할 수 있습니다.
- 현재 실행 환경 배포본 API의 전체 DTO·오류·보안 계약을 확정하는 근거로 사용하지 않습니다.
- QA37 검증표와 EDU 목록의 `완료` 표기를 최신 커밋의 실행 환경 성공으로 해석하지 않습니다.
- DB 3종 설치·업그레이드·되돌리기 결과를 이 문서만으로 성공 판정하지 않습니다.
- BOM 로컬·검증 저장소 게시와 배치 `execution-runtime` 공급 경계는 소스코드 수정 또는 실행 확인 전 재확인 필요입니다.

### 9.2 산출물 완료 판정 조건

다음 조건이 모두 충족되기 전에는 산출물 세트를 전체 완료로 표시하지 않습니다.

1. 최신 SHA에서 루트 소스코드 정합성 확인와 빌드 수용 기준가 성공합니다.
2. ADM/BZA 실행 환경 OpenAPI가 `BACKEND_RUNTIME`, `release-eligible=true`로 내보내기되고 생성 클라이언트와 일치합니다.
3. ADM 298개와 BZA 84개 작업의 실제 DTO·보안·표준 오류가 배포 명세에서 확인됩니다.
4. BOM 로컬·검증 저장소·내부 공급 작업와 독립 실제 사용처 검증이 성공합니다.
5. 배치 9개 단위 중 배포 대상과 내부 대상이 확정되고 루트 검증·게시 작업가 그 결정을 반영합니다.
6. QA37 검증표·목록·검증 증거가 `1eda8e12fe123281748a4388938c62f11819da1e` 또는 그 이후 적용 커밋으로 갱신됩니다.
7. MariaDB·PostgreSQL·Oracle의 설치·업그레이드·복구 검증 증거가 같은 배포본 기준으로 연결됩니다.
8. 브라우저·다중 인스턴스·처리 강제 종료·네트워크 장애·DR 결과가 미검증에서 해제됩니다.
9. `cpf-stater/`와 `:cpf-stater`가 같은 커밋의 `settings.gradle`, 루트 프로젝트 목록, 빌드·검증 경로에 등록됩니다.
10. `cpf-stater`가 기능별 스타터 전체를 고객 실행 의존성으로 강제하지 않으며 개별 선택 사용이 검증됩니다.
11. 스타터가 없는 최소 업무 영역이 `cpf-core`의 최소 계약만으로 컴파일·시험됩니다.
12. 하나의 스타터를 선택한 업무 영역에 다른 스타터의 실행 의존성이 불필요하게 전파되지 않습니다.
13. 코어에서 스타터로 이동한 기능의 소스코드·실제 사용처·설정·BOM·DB·시험·문서가 같은 변경에서 갱신됩니다.
14. 프로필을 선택한 업무의 실행 의존성 목록에 확장된 개별 스타터가 표시됩니다.
15. 복수 프로필의 중복 스타터는 하나로 정규화되고 버전·제공자·설정 충돌은 실패합니다.
16. 같은 스타터 구성의 개별 등록과 프로필 등록 결과가 동등함이 검증됩니다.
