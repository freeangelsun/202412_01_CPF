## 1. 설계 목표

CPF는 온라인·비동기·파일·외부 연계·배치·운영 Control Plane·업무 관리·Gateway를 하나의 공통 계약과 복구 모델로 제공한다. 장기 제품 구조, 확장성, 운영성, 보안성, 복구·검증 가능성과 Source·SQL·API·Test·문서 일치를 우선한다.

## 2. Architecture 원칙

1. `cpf-core`는 Topology 독립 Public API/SPI와 표준 식별자·Context·Error만 소유한다.
2. 선택 Runtime은 `cpf-starters/**`가 소유한다.
3. 고객 공개 선택면은 6개 Profile이다.
4. 내부 Provider는 7개 Capability Group과 Resolved Lock으로 해석한다.
5. Domain은 다른 Domain DB와 Internal Package를 참조하지 않는다.
6. ADM/BZA는 Owner 계약으로 조회·조치한다.
7. 결과 불명은 `UNKNOWN`으로 보존하고 대사 전 확정하지 않는다.
8. 다중 인스턴스 상태 변경은 Lease·Fencing·Version을 사용한다.
9. Source·SQL·API·Config·Frontend·Test·문서를 함께 변경한다.

| Profile | Use Case | Artifact |

| minimal-domain | 최소 업무 Domain | cpf-starter-profile-minimal-domain |

| browser-bff | 브라우저 Session과 BFF | cpf-starter-profile-browser-bff |
| event-service | 메시지 기반 업무 | cpf-starter-profile-event-service |

| Capability Group | 내부 기능 |
|---|---|
| data | JDBC·MyBatis·Caffeine·Valkey |
| messaging | Kafka·RabbitMQ·JMS·IBM MQ·Outbox/Inbox/DLQ |

Profile은 전이 Dependency와 선택 정책을 제공하고, 내부 Provider는 하나의 Owner와 AutoConfiguration을 가진다. `all/full/everything` 형식의 Mega Starter를 두지 않는다.

## 5. 의존 방향

```text
Generated/Business Domain → cpf-common → cpf-core
Business Runtime → 공개 Profile → 내부 Capability Provider
cpf-admin → Owner Query/Command Contract
cpf-biz-admin → Business Public Contract
cpf-batch → cpf-core Public Contract + Business Contract
cpf-gateway → cpf-core Public Contract + 선택 Capability
Customer Adapter → cpf-common/core SPI
```

Core의 Admin·Batch·업무 역참조, 업무 Domain 간 DB 접근, Internal Package Compile, Profile과 내부 Leaf 중복 선언을 차단한다.

## 6. Topology

| Topology | 실행 단위 | 계약 보존 |
|---|---|---|
| Embedded Boot JAR | 독립 Process | 표준 Context·Health·Config |
| External WAS WAR | Servlet Container | Servlet 6.1 Lifecycle |
| Modular Monolith | 단일 Runtime | Local Facade·공유 Transaction |
| Microservice | Domain별 Runtime | Remote Facade·Timeout·Service Identity |
| ADM/BZA | Backend + Static Frontend | OpenAPI Generated Client |
| Batch | Control·Scheduler·Worker·Runner·Agent | Metadata·Lease·Restart |
| Gateway | 독립 Runtime | 인증·Route·Attempt·LKG |
| Multi-zone | 다중 Instance/Zone | Fencing·Failover·Drift·DR |

## 7. 온라인 흐름

Request Validation → Authentication/Authorization → Application Transaction → Domain State Transition → Persistence → Audit/Outbox → Response 순서다.

DB Commit 후 Response 유실 시 Idempotency 원장과 Resource Version으로 기존 결과를 반환한다.

## 8. 비동기 흐름

Business Transaction + Outbox → Worker Claim/Lease → Provider Publish → ACK/UNKNOWN → Inbox/Consumer → Audit/Reconcile 순서다.

Provider ACK 유실은 Tracking ID와 Broker·업무 상태를 대사한다.

## 9. 배치 흐름

Job Definition/Version → Schedule/Manual Request → Preview/Approval → JobInstance/Execution → Step/Partition/Worker → Checkpoint → Stop/Restart/Reprocess → Business Reconciliation.

## 10. Runtime Control 흐름

Preview Hash → Request → Approval → Target Apply → ACK/NACK → Observed State → Retry/LKG/Rollback → Audit.

Owner별 Applier가 실제 상태를 변경한다. 공통 Runtime Control은 Owner 구현을 직접 포함하지 않는다.

## 11. 보안 Architecture

- Trust Boundary별 인증과 Service Identity
- Permission·Data Scope·Resource Condition
- Secret Provider와 Certificate Lifecycle
- API·Log·Trace·Audit·Export Masking
- HMAC·Nonce·Body Hash와 SSRF 방어
- 위험 조치 Reason·Approval·Expected Version
- Break-glass Scope·Expiry·Review

## 12. 데이터·동시성

- 상태 변경: 낙관적 Version
- 중복 요청: Idempotency Key와 Request Hash
- Worker: Lease·Owner·Fencing Token
- Scheduler: Unique Trigger/Execution
- Outbox/Inbox: 상태·Attempt·Next Retry·Last Error
- UNKNOWN: Resolution History와 Evidence
- Audit: Append 중심 이력

## 13. 실패·복구 Matrix

| 실패 | 보존 상태 | 복구 |
|---|---|---|
| Validation/Permission | 미실행 | 요청·권한 수정 |
| DB Conflict | 기존 상태 | 최신 Version 재조회 |
| DB Commit 전 실패 | Rollback | 동일 Key 재시도 |
| Commit 후 Response Loss | UNKNOWN 가능 | Resource/Idempotency 조회 |
| Broker ACK Loss | UNKNOWN | Provider Probe·Outbox 대사 |
| Worker Crash | Claimed/In-flight | Lease 만료·Reclaim |
| Partial Apply | ACK/NACK | 실패 Target 재시도·LKG |
| File Transfer 중단 | Offset/Checksum | Resume·새 Transfer |
| DB Migration 실패 | Partial/Failed | Rollback·Forward Recovery |

## 14. Artifact와 Supply Chain

Artifact Catalog가 Owner, Producer, Output Pattern, Consumer와 Attestation을 정의한다. 각 배포 Artifact는 SHA-256, SBOM, License Review와 필요한 Migration/Browser/Runtime 기록을 연결한다.

## 15. 주요 설계 결정

| 영역 | 결정 | 이유 |
|---|---|---|
| 공개 Starter | 6 Profile | 고객 Use Case 중심 선택 |
| 내부 Runtime | 7 Capability Group | Provider·Owner 경계 |
| Batch | Spring Batch Primary | Metadata·Restart 정본 |
| Scheduler | cpf-batch 소유 | 실행 Ownership 통합 |
| Gateway | Spring Cloud Gateway MVC | CPF Route·Trust·Ledger 확장 |
| Feature Flag | OpenFeature + CPF 계약 | 평가·감사·Override |
| Resilience | CPF 계약 + Resilience4j | Timeout·Retry·UNKNOWN 연계 |
| DB | Oracle·PostgreSQL·MariaDB | 고객 Vendor 동등 Lifecycle |

## 16. 변경 영향 분석

Public API/SPI 변경은 Consumer, OpenAPI, Generated Client, JavaDoc, Version과 Compatibility Test를 함께 변경한다. DB 변경은 Canonical Model, 3 Vendor SQL, Generator, Consumer, Migration, Rollback, Drift를 함께 처리한다. Route 변경은 Backend Operation, OpenAPI, Client, Permission, Browser Test와 문서를 함께 변경한다.
