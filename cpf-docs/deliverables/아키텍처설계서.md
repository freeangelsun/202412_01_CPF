## 1. 설계 목표

CPF는 업무 기능을 빠르게 시작하는 공통 Library에 머물지 않고, 업무 시스템의 개발·운영·감사·복구·배포를 같은 계약으로 연결한다.

| 품질 속성 | 설계 수단 | 판정 Evidence |
|---|---|---|
| 변경 용이성 | Owner·Public API/SPI·Adapter | 영향 Matrix·Contract Test |
| 일관성 | Version·Idempotency·Transaction·Outbox | Ledger·Audit·Reconcile |
| 복구 가능성 | Attempt·UNKNOWN_RESULT·Checkpoint·LKG | Fault Test·Runbook |
| 보안 | Identity·Permission·Scope·Masking·Approval | Decision·Audit·Negative Test |
| 운영성 | Health·Log·Metric·Trace·ADM | Dashboard·Incident·교대 기록 |
| 이식성 | Profile·Capability·3 DB Vendor | Resolved Lock·Vendor Verify |
| 추적성 | Source SHA·Operation ID·Manifest | Evidence Matrix·Checksum |

## 2. System Context

```text
고객 사용자·외부 Client·운영자·Scheduler
            │
      Browser / Gateway / API
            │
  Business Domain · Common · Batch
            │
 DB · Broker · Object Store · External Institution
            │
        ADM · BZA · Operations
```

Trust Boundary:

- Browser ↔ BFF.
- 외부 Client ↔ Gateway.
- Service ↔ Service.
- Runtime ↔ DB·Broker·Secret Provider.
- 운영자 ↔ ADM/BZA 위험 조치.

## 4. 의존 방향

```text
Generated/Business Domain → cpf-common → cpf-core
cpf-batch → cpf-core + Business Public Contract
cpf-admin → Owner Query/Command Contract
cpf-biz-admin → Business Public Contract
cpf-gateway → cpf-core Public Contract + 선택 Starter
Customer Adapter → cpf-common/core SPI
```

금지:

- Core의 Starter·Admin·Batch 역참조.
- 업무 Domain 간 DB 직접 접근.
- ADM/BZA의 Owner DB 직접 갱신.
- 내부 호출의 Gateway 재경유.
- Public API에 Provider SDK Type 노출.
- Consumer 없는 Interface·Starter.

## 5. Public API·SPI·Internal

```text
com.cpf.<owner>.api
com.cpf.<owner>.spi
com.cpf.<owner>.internal
```

Public API는 호환성 대상이며 SPI는 Capability·Lifecycle·Failure·Thread-safety를 문서화한다. Internal Package는 다른 Module에서 Compile되지 않게 ArchUnit·Module Metadata·Publication Gate로 차단한다.

## 6. Profile·Capability Architecture

Profile은 고객 서비스의 공개 실행 형태다. Capability는 선택 기술이다. Profile 해석 결과는 Leaf Starter 목록과 Version으로 Manifest에 고정한다.

- `minimal-domain`
- `web-api`
- `secure-api`
- `browser-bff`
- `event-service`
- `batch-service`

Mega Starter는 두지 않는다. 선택하지 않은 Provider의 JAR·Bean·SQL·Config·Secret 요구가 없어야 한다.

## 7. 온라인 Transaction Flow

```text
Client
  → Authentication·Context
  → Validation·Permission·Data Scope
  → Idempotency Key·Request Hash
  → Domain State·Expected Version
  → Business Row + History + Audit + Outbox
  → Commit
  → Result Snapshot
  → Outbox Publisher·External Attempt
```

Dispatch 전 실패는 `FAILED`로 확정할 수 있다. 외부 부작용 뒤 응답 Evidence가 부족하면 `UNKNOWN_RESULT`다.

## 8. 비동기 Flow

Producer는 업무 Commit과 Outbox를 같은 Transaction에 저장한다. Publisher는 Lease와 Attempt로 Broker에 전송한다. Consumer는 Inbox를 확보하고 업무 Commit 뒤 ACK한다. Poison은 DLQ와 승인 Replay로 분리한다.

Multi-instance에서 Lease·Fencing Token으로 오래된 Publisher·Worker의 Write를 차단한다.

## 9. Batch Architecture

Spring Batch Metadata가 JobInstance·Execution·StepExecution·Checkpoint 정본이다. CPF Control Plane은 Scheduler·Runner·Worker·Agent·Center-Cut·Deployment·Recovery를 연결한다.

업무 성공 판정은 Metadata와 업무 건수·금액·Hash·외부 Attempt를 함께 사용한다.

## 10. ADM Control Plane

ADM Frontend는 Route Registry와 Generated Client를 사용한다. Backend는 Owner Port 또는 Remote API를 호출한다. 위험 조치는 Reason·Version·Approval·Idempotency를 사용한다.

`/integrationClosure`는 `06_07`의 Data Quality 정정 승인과 Crypto·Time·Webhook 운영을 연결한다. 승인 요청에서 정정 Snapshot을 고정하고 실행은 Approval ID로 수행한다.

## 11. BZA Control Plane

BZA는 조직·사용자·Role·Permission·Data Scope·결재를 기준일과 Version으로 제공한다. 업무 Domain은 BZA Effective 결과를 소비하지만 최종 업무 상태를 직접 소유한다.

## 12. Gateway Data·Control Plane

Data Plane은 Listener·Predicate·Rewrite·Security·Target Dispatch·Attempt를 실행한다. Control Plane은 Draft·Validate·Approve·Publish·ACK/NACK·LKG·Rollback을 수행한다.

Route Config와 Target Applied Version은 Desired·Observed로 비교한다.

## 13. Data Architecture

모든 상태 변경은 다음 중 필요한 원장을 갖는다.

- Current Row.
- History.
- Idempotency Result.
- Attempt.
- Outbox·Inbox·DLQ.
- Approval Snapshot.
- Audit.
- Reconciliation Decision.

Owner가 다른 원장을 하나의 Local Transaction으로 가장하지 않는다. Cross-resource 결과는 Attempt와 대사로 연결한다.

## 14. Error Taxonomy

| 분류 | 예 | 복구 |
|---|---|---|
| Validation | 형식·범위·교차 Field | 입력 수정 |
| Authentication | Token·Session·Audience | 재인증·Credential 교체 |
| Authorization | Permission·Scope·Masking | 권한·대상 보정 |
| Conflict | Version·Idempotency Hash | 최신 상태 비교 |
| Dependency | DB·Broker·Target | Health·Circuit·Retry 정책 |
| Unknown | 응답 유실·ACK 유실 | Target·Owner 대사 |
| Partial | 일부 Target 성공 | 성공 Target 보존 |
| Drift | Desired·Observed 불일치 | Reconcile·Rollback |

## 15. Security Architecture

- 사용자 Identity와 Service Identity 분리.
- Browser Session·CSRF·MFA.
- Gateway HMAC·Audience·Nonce·Body Hash.
- Menu·Button·API·Data Scope·Masking.
- Secret Provider·Key Version·Rotation.
- Reason·Approval·Break-glass·Immutable Audit.
- Log·Trace·Support Bundle Masking.

## 16. Deployment Architecture

지원 형태:

- Embedded JAR.
- External WAS WAR.
- Modular Monolith.
- Microservice.
- Static Frontend.
- Gateway Runtime.
- Agent·Runner·Worker Process.
- Multi-instance·Multi-zone.
- Rolling·Canary·Blue-Green.

Topology가 달라도 DTO·Validation·Error·Idempotency·Audit·Timeout 의미를 유지한다.

## 17. Failure Architecture

| 실패 | 보호 수단 | 정상화 |
|---|---|---|
| Process Kill | Transaction·Checkpoint·Lease | Restart·Reclaim·대사 |
| Network partition | Timeout·Circuit·Fencing | Target·Owner Reconcile |
| Response loss | Attempt·Operation 조회 | 결과 확정·Compensation |
| Partial apply | Target별 ACK·Observed | 실패 Target 복구·LKG |
| DB migration partial | Backup·Version·Verify | Forward Recovery·Restore |
| Secret rotation partial | Grace Version·Consumer 상태 | 실패 Consumer 재적용 |
