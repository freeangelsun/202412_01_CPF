## 1. 설계 목적

Core Platform Framework(CPF)는 업무 시스템을 온라인, 비동기, 파일, 외부 연계, 배치, 운영 Control Plane, Gateway 형태로 구축할 때 공통 계약과 복구 모델을 제공한다. 이 문서는 Module Ownership, 의존 방향, 배포 Topology, 데이터 흐름, 실패·복구 흐름과 변경 원칙을 정본화한다.

## 2. Architecture 원칙

1. `cpf-core`는 topology-independent Public API/SPI, 표준 식별자, 오류, 문맥만 소유한다.
2. 선택 기술 Runtime은 `cpf-starters/**`가 소유하며 선택하지 않은 JAR·Bean·SQL·Secret을 강제하지 않는다.
3. 개발자가 직접 선택하는 공개면은 6개 Use-case Profile이다.
4. 7개 Capability Group의 Provider·Codec·Exporter는 Generator binding과 `resolved-starter-lock.json`으로 해석한다.
5. 업무 Domain은 `cpf-core`/`cpf-common` Public Contract만 사용하고 다른 Domain DB나 Internal Package를 직접 참조하지 않는다.
6. ADM/BZA는 Owner API로 조회·조치하며 Owner DB를 직접 갱신하지 않는다.
7. 결과 불명(`UNKNOWN`)은 성공이나 실패로 임의 확정하지 않고 대사·승인·재처리 대상으로 유지한다.

## 3. 제품 Module Ownership

| 역할 | Module | 주요 책임 | 대표 Consumer |
|---|---|---|---|
| 기술 계약 | `cpf-core` | Public API/SPI, 표준 결과·오류·문맥·식별자 | 모든 Runtime과 Generated Domain |
| 고객 공통 | `cpf-common` | 고객 공통 코드·메시지·달력·정책 확장 | Generated Domain, ADM/BZA |
| 운영 Control Plane | `cpf-admin` | 플랫폼 조회·조치·승인·감사 | 운영자·승인자 |
| 업무 관리 | `cpf-biz-admin` | 조직·사용자·권한·결재·업무 관리 | 업무 관리자 |
| 배치 | `cpf-batch` | Spring Batch, Scheduler, Center-Cut, Worker, Agent | 배치 개발·운영 조직 |
| Gateway | `cpf-gateway` | Trust Boundary, Route, 정책, Attempt Ledger | 외부 API Consumer |
| Golden Domain | `cpf-member` | Generator 산출물의 실제 Consumer 기준 | 신규 업무 개발자 |
| 교육·참조 | `cpf-reference` | Public API 사용·오류·복구 예제 | 교육·PoC |
| 생성·검증 Tool | `cpf-tools` | Generator, DB Pack, Verification, Build Plugin | 플랫폼 개발·운영 조직 |

## 4. 공개 Profile

| Profile | 사용 목적 | Owner Path | Artifact |
|---|---|---|---|
| `minimal-domain` | 최소 업무 Domain | `cpf-starters/profiles/minimal-domain` | `cpf-starter-profile-minimal-domain` |
| `web-api` | REST API와 OpenAPI | `cpf-starters/profiles/web-api` | `cpf-starter-profile-web-api` |
| `secure-api` | 인증·인가 API | `cpf-starters/profiles/secure-api` | `cpf-starter-profile-secure-api` |
| `browser-bff` | 브라우저 세션·BFF | `cpf-starters/profiles/browser-bff` | `cpf-starter-profile-browser-bff` |
| `event-service` | 메시지 기반 서비스 | `cpf-starters/profiles/event-service` | `cpf-starter-profile-event-service` |
| `batch-service` | 배치·Worker·Scheduler | `cpf-starters/profiles/batch-service` | `cpf-starter-profile-batch-service` |

Profile은 내부 Provider를 숨기는 공개 선택면이다. Provider를 변경할 때 업무 Source를 바꾸지 않고 binding, 환경 설정과 resolved lock을 갱신한다.

## 5. Capability Group

| Group | 포함 기능 | Owner Path |
|---|---|---|
| `data` | JDBC, MyBatis, Caffeine, Valkey | `cpf-starters/data` |
| `messaging` | Kafka, RabbitMQ, JMS, IBM MQ, Outbox/Inbox/DLQ | `cpf-starters/messaging` |
| `integration` | HTTP, Resilience, TCP, Fixed-length, ISO8583 | `cpf-starters/integration` |
| `file` | Attachment, Archive, Tabular, SFTP | `cpf-starters/file` |
| `notification` | Email, SMS, Outbox, Receipt | `cpf-starters/notification` |
| `security` | Resource Server, Session, Service Identity, Secret | `cpf-starters/security` |
| `platform-operations` | Observability, Runtime Control, Channel Registry, Feature Flag | `cpf-starters/platform-operations` |

`cpf-starters/foundation/base`는 내부 Foundation이며 고객이 개별 기능으로 선택하지 않는다.

## 6. 의존 방향

```text
Generated/Business Domain
        │
        ├──> cpf-common ──> cpf-core
        ├──> Public Profile
        └──> Capability Public API

Provider/Internal Starter ──> cpf-core SPI
cpf-admin ──> Owner Query/Command Contract
cpf-gateway ──> cpf-core Public Contract + 선택 Capability
cpf-batch ──> cpf-core Public Contract + batch-service
```

금지되는 방향은 Core의 Admin/Batch/업무 역참조, Consumer의 `internal` package import, Profile과 내부 Leaf의 중복 직접 의존, 업무 Domain 간 DB 직접 접근이다.

## 7. 배포 Topology

| Topology | 배포 단위 | 통신 | 상태·복구 기준 |
|---|---|---|---|
| Modular Monolith | 하나의 Boot Runtime | 동일 JVM Local Facade | 동일 Transaction 경계와 표준 오류 유지 |
| Microservice | Domain별 Boot Runtime | Remote Facade/HTTP·Messaging | Timeout Budget, Idempotency, UNKNOWN, Reconcile |
| External WAS | WAR | Servlet 6.1 | Container Lifecycle과 Health 분리 |
| ADM/BZA | Backend Runtime + Static Frontend | OpenAPI Generated Client | 권한·Reason·Approval·Audit |
| Batch | Control/Scheduler/Worker/Runner/Agent | DB·Messaging·Owner Contract | JobRepository, Lease, Fencing, Restart |
| Gateway | 독립 Runtime | 외부 ↔ 내부 Route | 인증, HMAC, Retry, Attempt Ledger, LKG |

## 8. 핵심 데이터 흐름

### 8.1 온라인 요청

1. Gateway 또는 업무 API가 표준 Header와 인증 정보를 검증한다.
2. Application Service가 업무 의도와 멱등성 Key를 확인한다.
3. Domain 규칙을 수행하고 Data Capability로 저장한다.
4. 외부 부작용이 필요하면 Outbox를 같은 Transaction에 기록한다.
5. 응답에는 거래 식별자, 상태, Version과 추적 정보를 반환한다.

### 8.2 비동기 메시지

1. 업무는 `CpfBrokerClient` 계열 Public API로 발행 요청을 만든다.
2. Reliability Runtime이 Outbox 상태, Claim, Lease, Attempt를 관리한다.
3. Kafka/RabbitMQ/JMS/IBM MQ Provider가 전송한다.
4. ACK 유실이나 Timeout은 `UNKNOWN`으로 기록한다.
5. `CpfBrokerUnknownResultPort`와 Reconciler가 Broker 조회·업무 대사로 확정한다.

### 8.3 Notification

`CpfNotificationOperations`가 요청을 Outbox에 기록하고 Worker가 Provider SPI를 호출한다. Email/SMS 전송 결과가 불명확하면 `CpfNotificationReceipt`와 `CpfNotificationReconciler`를 통해 대사한다.

### 8.4 Runtime Control

ADM이 Preview → Change Request → Approval → Apply → ACK/NACK → Verify → Rollback 순서로 진행한다. 실제 Applier는 각 Owner Starter에 존재하며 `runtime-control-client`는 공통 계약과 Payload 해석만 담당한다.

## 9. 실패와 복구 흐름

| 실패 | 보존 상태 | 자동/수동 조치 | 완료 판정 |
|---|---|---|---|
| DB Commit 전 실패 | 미반영 | 동일 멱등성 Key로 재시도 | 업무 Row·Audit 없음 |
| DB Commit 후 응답 유실 | 결과 불명 | 거래 ID/멱등성 Key 조회 | 기존 결과 반환 또는 Reconcile |
| Broker ACK 유실 | `UNKNOWN` | Provider Probe와 Outbox 대사 | 중복 발행 없이 확정 |
| Worker 종료 | `CLAIMED/IN_FLIGHT` | Lease 만료 후 reclaim | Fencing Token이 최신 Worker와 일치 |
| Partial Apply | Target별 ACK/NACK | 실패 Target 격리, LKG 또는 Rollback | Desired/Applied/Observed 일치 |
| 파일 전송 중단 | 전송 Ledger 유지 | Checksum·Offset 기반 Restart | 원격/로컬 Checksum 일치 |

## 10. 보안·감사 Architecture

- 인증: Resource Server, Browser Session, Service Identity를 Topology에 맞게 선택한다.
- 권한: Permission과 Data Scope를 분리하고 조치마다 Reason·Approval을 요구한다.
- Secret: `CpfSecretProvider` 계열 SPI로 해석하며 운영 Profile의 평문 비밀번호를 허용하지 않는다.
- Masking: 로그·API·Export에 동일 정책을 적용한다.
- Audit: 요청자, 승인자, 대상, Before/After, Reason, Version, 결과와 Correlation ID를 남긴다.

## 11. 품질 속성

- 확장성: Provider SPI와 Conformance Testkit으로 고객 Provider를 추가한다.
- 운영성: Health, Metric, Trace, Runtime Control, Recovery Center에서 상태와 조치를 연결한다.
- 복구 가능성: UNKNOWN, Retry, Restart, Reprocess, Reconcile, Compensation, Rollback을 상태 모델에 포함한다.
- 재현성: Generator 입력, Domain Manifest, `resolved-starter-lock.json`, Artifact Hash를 보존한다.
- 호환성: Public API/SPI는 Version Contract를 적용하고 Internal은 외부 Compile을 차단한다.
