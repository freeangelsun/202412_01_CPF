## 1. 제품 범위

| 업무 유형 | 만들 수 있는 결과 | 주 선택 |
|---|---|---|
| 온라인 업무 | 조건 검색·상세·등록·상태 변경·승인·대사 API와 화면 | web-api 또는 secure-api |
| 브라우저 업무 | Session·CSRF·BFF가 적용된 화면 업무 | browser-bff |
| 비동기 업무 | 이벤트 발행·소비·Outbox·Inbox·DLQ·재처리 | event-service |
| 정기·대량 업무 | Tasklet·Chunk·Partition·Center-Cut·Scheduler·Worker | batch-service |
| 외부 연계 | HTTP·TCP·Fixed-length·ISO8583·SFTP | integration Capability |
| 파일 업무 | Attachment·압축·표 파일·전송 Ledger | file Capability |
| 운영 통제 | ADM 조회·조치·승인·감사·복구 | cpf-admin |
| 업무 관리 | 조직·사용자·권한·결재 | cpf-biz-admin |
| API 진입 | 인증·라우팅·제한·Attempt Ledger·적용 상태 | cpf-gateway |

CPF는 고객 업무 규칙과 데이터를 대신 결정하지 않는다. 고객은 업무 상태, 권한, Data Scope, 보존 기간, SLA, 대사 기준과 승인 정책을 정하고 CPF는 공통 계약·실행 기능·복구 상태·운영 인터페이스를 제공한다.

## 2. 비범위와 금지되는 적용

- 단순 Utility 모음이나 Sample 복사본으로 사용하지 않는다.
- 다른 Domain DB를 직접 조회하거나 갱신하지 않는다.
- ADM/BZA가 Owner DB를 직접 수정하지 않는다.
- 내부 동일 JVM 호출을 Gateway로 우회시키지 않는다.
- Provider SDK Type을 Public API에 노출하지 않는다.
- 응답 유실을 성공 또는 실패로 추정하지 않는다.
- 선택하지 않은 Provider의 JAR·Bean·SQL·Secret 요구를 끌어오지 않는다.

## 3. Module Ownership

| Owner | 책임 | 대표 Consumer |
|---|---|---|
| cpf-core | 기술 중립 Public API·SPI, Context·Error·식별자 | 모든 Runtime과 Domain |
| cpf-common | 고객 공통 정책·코드·메시지·달력 | Generated Domain·ADM/BZA |
| cpf-starters | 선택 기술 Runtime·AutoConfiguration | Profile을 선택한 Runtime |
| cpf-batch | Spring Batch·Scheduler·Center-Cut·Worker·Agent | 배치 Runtime과 ADM |
| cpf-admin | 플랫폼 운영 Query·Command·승인·감사 | 운영자·승인자 |
| cpf-biz-admin | 조직·사용자·권한·결재 | 업무 관리자 |
| cpf-gateway | 외부 진입·Trust Boundary·Route·Attempt | 외부 Client |
| cpf-member | Generator 기준 Golden Domain | 신규 업무 개발자 |
| cpf-reference | 교육·정상/오류/복구 예제 | 교육·PoC |
| cpf-tools | Generator·BOM·Build·DB·검증·환경 | 개발·운영 조직 |

의존 방향은 `업무 Domain → cpf-common → cpf-core`다. Starter와 Provider는 Core SPI를 구현하며 Core가 Starter·Admin·Batch·업무 Module을 역참조하지 않는다.

## 4. 공개 Profile 선택

| Profile | 선택 상황 | Artifact |
|---|---|---|
| minimal-domain | 최소 업무 Domain | cpf-starter-profile-minimal-domain |
| web-api | REST API와 OpenAPI | cpf-starter-profile-web-api |
| secure-api | 인증·인가 API | cpf-starter-profile-secure-api |
| browser-bff | 브라우저 Session과 BFF | cpf-starter-profile-browser-bff |
| event-service | 메시지 기반 업무 | cpf-starter-profile-event-service |
| batch-service | 배치·Scheduler·Worker | cpf-starter-profile-batch-service |

선택 순서:

1. 가장 가까운 업무 결과를 제공하는 Profile 하나를 선택한다.
2. Data·Messaging·Integration·File·Notification·Security·Platform Operations의 Provider Binding을 결정한다.
3. Generator Dry Run으로 실제 해석된 Starter와 충돌을 확인한다.
4. `resolved-starter-lock.json`에서 Version과 내부 Artifact를 고정한다.
5. 선택하지 않은 Provider가 Runtime Classpath·Config·Health에 나타나지 않는지 확인한다.

## 5. Capability Group

| Group | 기능 |
|---|---|
| data | JDBC·MyBatis·Caffeine·Valkey |
| messaging | Kafka·RabbitMQ·JMS·IBM MQ·Outbox/Inbox/DLQ |
| integration | HTTP·Resilience·TCP·Fixed-length·ISO8583 |
| file | Attachment·Archive·Tabular·SFTP |
| notification | Email·SMS·Receipt·Reconcile |
| security | Resource Server·Session·Service Identity·Secret |
| platform-operations | Observability·Runtime Control·Feature Flag |

Provider 교체는 업무 Java Source가 아니라 Binding·Config·Secret Reference·Resolved Lock을 바꾸는 작업이다. 교체 전후 Contract Test, Runtime 연결, Outbox/Inbox/DLQ 호환, ADM 관측과 Rollback Lock을 확인한다.

## 6. Topology 선택

| Topology | 배포 단위 | 계약 | 선택 기준 |
|---|---|---|---|
| Modular Monolith | 하나의 Boot Runtime | Local Facade·공유 Transaction | 단일 배포와 빠른 내부 호출이 우선 |
| Microservice | Domain별 독립 Runtime | Remote Facade·HTTP·Messaging | 독립 배포·확장·장애 격리가 우선 |
| External WAS | WAR + Servlet Container | Servlet 6.1 Lifecycle | 고객 표준 WAS가 배포 정본 |
| ADM/BZA | Backend + Static Frontend | OpenAPI Generated Client | 운영·업무관리 화면 분리 |
| Batch | Control·Scheduler·Worker·Runner·Agent | DB·Messaging·Owner Contract | 정기·대량·분산 실행 |
| Gateway | 독립 Runtime | 외부 ↔ 내부 Route | 외부 Trust Boundary 필요 |

Local과 Remote는 DTO·Validation·Error·Permission·Audit 의미가 같다. Remote에서는 Service Identity, Timeout Budget, Trace Propagation과 결과 불명 대사를 추가한다.

## 7. 핵심 실행 흐름

### 7.1 온라인 상태 변경

1. 요청자는 Resource ID, 목표 상태, `expectedVersion`, `idempotencyKey`, `reason`을 전달한다.
2. Application Service가 Permission·Data Scope·현재 상태·Version을 확인한다.
3. 업무 Row와 Audit·Outbox를 하나의 Transaction으로 반영한다.
4. 응답에는 Transaction ID, Resource Version, Result Code를 반환한다.
5. 응답이 유실되면 같은 Key로 결과를 조회하고 새 부작용을 만들지 않는다.

### 7.2 비동기 처리

1. 업무 Transaction에서 Outbox를 기록한다.
2. Worker가 Lease와 Fencing Token으로 Claim한다.
3. Provider가 Broker에 전송하고 Tracking ID를 기록한다.
4. ACK 유실은 `UNKNOWN`으로 보존한다.
5. Provider Probe·업무 원장·Broker 상태를 대사한 후 결과를 확정한다.

### 7.3 배치

대상 Preview → 승인 → Job Instance/Execution 생성 → Step/Partition 실행 → Checkpoint → Stop/Restart/Reprocess → 업무 합계 대사 순서다.

### 7.4 운영 변경

Preview → Reason·Approval → Apply → Target별 ACK/NACK → Observed 상태 확인 → 실패 Target 재시도 또는 LKG Rollback 순서다.

## 8. 보안·감사 기준

- 인증: JWT Resource Server, Browser Session, Service Identity를 Topology에 맞게 선택한다.
- 인가: Permission과 Data Scope를 분리한다.
- 위험 조치: Reason, Approval, Expected Version과 Idempotency를 요구한다.
- Secret: Repository 밖 Provider Reference로 공급한다.
- Masking: API·화면·Log·Audit·Export에 같은 정책을 적용한다.
- Audit: Actor·Approver·대상·Before/After·Reason·Version·결과·Correlation ID를 기록한다.

## 9. 도입 단계

1. 업무 기능과 비기능 요구를 표로 작성한다.
2. Owner Module과 실제 Consumer를 확정한다.
3. Profile·Capability·Provider·DB Vendor·Topology를 결정한다.
4. Generator로 Domain을 생성하고 Manifest·Lock을 검토한다.
5. API·DB·Messaging·File·Security·ADM 계약을 구현한다.
6. 정상·오류·동시성·Timeout·UNKNOWN·복구 Test를 수행한다.
7. Artifact·Migration·Config·Permission·Runbook을 운영팀에 인계한다.
8. 운영 환경에서 Health·Metric·Trace·Audit와 Backup·Rollback을 확인한다.

## 11. 도입 완료 판정

- 선택한 기능의 Owner와 Consumer가 연결돼 있다.
- Local/Remote, DB Vendor, Provider 선택이 Manifest와 Artifact에 반영돼 있다.
- 정상·오류·중복·동시성·Timeout·UNKNOWN·부분 실패·복구 절차가 준비돼 있다.
- 운영자가 ADM·로그·지표·추적·감사에서 같은 식별자를 찾을 수 있다.
- Upgrade·Rollback·Backup·Restore·DR 책임자와 승인 절차가 정해져 있다.
