## 3. Generator로 신규 Domain 생성

1. Repository Root에서 `cpf-tools/generator/create-domain.ps1`을 Dry Run으로 실행한다.
2. Domain Name, System Code, Package, Profile, Provider Binding, DB Vendor를 입력한다.
3. 생성·수정·충돌 경로와 Port·Schema·Identifier를 검토한다.
4. Apply 후 `domain-manifest.json`과 `resolved-starter-lock.json`을 검토한다.
5. Source·Config·Migration·Test Skeleton과 Manifest가 일치하는지 확인한다.
6. Fresh Build와 생성 정책 Verifier를 실행한다.
7. 신규 업무 파일만 수정하고 Generator·Core·Starter 정본을 직접 바꾸지 않는다.

기존 Domain은 `upgrade-domain.ps1`의 Dry Run으로 Profile·Provider·Config·SQL 이동을 확인한 뒤 적용한다. 업무 Source 덮어쓰기가 감지되면 중단하고 수동 병합한다.

## 5. 조회 기능

### 결정값

검색 Field, 기본 기간, Page Size, 최대 건수, 정렬 Key, Data Scope, Masking, Export 허용 여부를 정한다.

### 구현 절차

1. API DTO에 입력 Type·길이·형식·기본값을 선언한다.
2. Application에서 Permission과 Data Scope를 적용한다.
3. 안정적인 정렬과 Cursor 또는 Page 조건으로 Query한다.
4. 민감정보를 Masking한 응답 DTO를 반환한다.
5. Empty Result, Invalid Cursor, 초과 Page Size, 권한 없음, DB Timeout을 Test한다.
6. Transaction ID와 Query ID를 Log·Metric·Trace에 기록한다.

### 정상 결과

HTTP 상태와 Result Code가 성공이고, 반환 건수·정렬·마스킹이 계약과 일치한다. ADM의 거래 로그와 Trace에서 같은 Transaction ID를 조회할 수 있다.

### 실패와 복구

입력 오류는 요청자가 수정한다. 권한 오류는 재시도하지 않는다. DB Timeout은 전체 Timeout Budget과 Dependency 상태를 확인한 뒤 정책에 따라 재시도한다. Export가 길어지면 비동기 Job으로 전환한다.

## 6. 상태 변경 기능

요청에는 적용 가능한 `resourceId`, `targetStatus`, `expectedVersion`, `idempotencyKey`, `reason`, `actor`를 포함한다.

1. 현재 상태와 Version을 조회한다.
2. Permission·Data Scope·상태 전이·업무 불변식을 검증한다.
3. `WHERE id=? AND version_no=?` 조건으로 갱신한다.
4. 영향 건수가 0이면 최신 상태를 재조회해 Conflict와 Not Found를 구분한다.
5. 업무 Row, Audit, Outbox를 같은 Transaction으로 기록한다.
6. 응답에 새 상태·Version·Transaction ID를 반환한다.

같은 멱등성 Key의 병렬 요청은 한 건만 부작용을 수행하고 나머지는 기존 결과를 반환한다. 응답 유실 후에는 같은 Key나 Operation ID로 결과를 조회한다.

## 7. Transaction·Outbox·Inbox

- DB Transaction 내부에서 외부 Broker·HTTP 응답을 장시간 기다리지 않는다.
- 업무 변경과 Outbox Insert를 같은 Transaction에 둔다.
- Outbox Worker는 Claim Owner, Lease Until, Fencing Token, Attempt, Next Retry Time을 기록한다.
- Consumer는 Inbox 또는 업무 멱등성 원장으로 중복 Message를 차단한다.
- Poison Message는 무한 Retry하지 않고 DLQ와 Incident로 전환한다.

## 8. Messaging

대표 계약은 `CpfBrokerClient`, Publish Request/Result, Provider SPI, Result Probe와 Unknown Result Port다.

1. `bindingName`, Message Key, Payload Type/Version, Idempotency Key를 지정한다.
2. Generator Binding으로 Kafka·RabbitMQ·JMS·IBM MQ 중 Provider를 선택한다.
3. 정상 Publish/Consume Contract Test를 실행한다.
4. Duplicate, Schema 오류, Broker Down, ACK 유실, Consumer Crash, DLQ를 재현한다.
5. ACK 유실은 `UNKNOWN`으로 보존하고 Provider Tracking ID와 Broker 상태를 대사한다.
6. 재처리는 원 Message ID와 새 Operation ID를 연결한다.

Provider 변경 시 Java 업무 Class diff가 없어야 하며 Config·Secret·Resolved Lock·운영 Runbook을 함께 변경한다.

## 9. Notification

`CpfNotificationOperations`에 Template ID, Recipient, Channel, Variables, Idempotency Key를 전달한다.

- Email/SMS 주소와 본문은 Log·Audit에서 Masking한다.
- Provider Timeout 후 Receipt를 조회하기 전 동일 알림을 재전송하지 않는다.
- 취소는 아직 Provider에 전달되지 않은 상태에서만 허용한다.
- 재처리는 원 Delivery ID와 Attempt를 보존한다.

## 10. HTTP 외부 연계

1. Target ID, Method, Path, 인증, Timeout Budget, Retry Class를 선언한다.
2. Endpoint URL은 Allowlist와 Secret Reference에서 해석한다.
3. 표준 Header와 Service Identity를 적용한다.
4. 4xx/5xx/Timeout/Connection Reset/응답 파싱 오류를 분류한다.
5. 비멱등 요청은 Attempt Ledger나 상대 거래 조회 없이 Retry하지 않는다.
6. Write 후 Response 유실은 `UNKNOWN`으로 보존하고 상대 시스템의 거래 조회 API로 대사한다.

## 11. TCP·Fixed-length·ISO8583

- TCP: Framing, Charset, TLS, Correlation, Connect/Write/Read Timeout
- Fixed-length: Layout Version, Field Length, Padding, Encoding, Truncation 금지
- ISO8583: MTI, Bitmap, Field Spec, STAN/RRN, MAC, Reversal

Write 완료 후 응답 유실이 발생하면 원 거래 조회 또는 Reversal 정책으로 확정한 뒤 재전송 여부를 결정한다.

## 12. File·Attachment·Archive·Tabular·SFTP

1. File Size, Count, Extension, MIME, Checksum과 악성 검사 결과를 검증한다.
2. 저장 Key와 원본 File Name을 분리한다.
3. Archive는 Path Traversal, Entry Count, Expanded Size와 중첩 깊이를 제한한다.
4. Tabular는 Sheet·Row·Column·Cell Size와 수식 처리 정책을 제한한다.
5. SFTP는 Host Key Pinning, Path Allowlist, Temp Name, Atomic Rename을 적용한다.
6. 전송 Ledger에 Offset·Checksum·Remote Path·Attempt·Result를 기록한다.
7. 중단 후 Resume 또는 새 전송 정책을 명시한다.

## 14. Feature Flag와 Resilience

Feature Flag는 대상 Context, 기본값, Override 기간, Reason, Approval과 Evaluation Audit를 관리한다. Kill Switch는 위험도가 높은 조치로 처리한다.

Resilience 정책은 Timeout, Retry Count/Backoff, Circuit Threshold, Bulkhead를 정의한다. 비멱등 Operation에 Retry를 추가하지 않는다. 정책 변경 후 Latency·Failure·UNKNOWN·Queue 부하를 확인하고 필요하면 이전 Version으로 되돌린다.

## 15. Local·Remote 전환

- Local Facade와 Remote Facade는 같은 DTO·Validation·Error 계약을 제공한다.
- Remote 전환은 업무 Source가 아니라 Binding·Endpoint·Service Identity를 변경한다.
- 전체 Timeout Budget을 Gateway·Network·Owner 처리 시간에 배분한다.
- Remote 응답 유실은 Operation ID 조회와 Reconcile을 제공한다.
- Mixed Version 동안 Public Contract 호환 범위를 Test한다.

## 16. DB Migration

모든 변경은 Oracle·PostgreSQL·MariaDB의 Install/Migration/Rollback/Verify/Checksum을 함께 처리한다.

1. Canonical Model과 Query Contract를 변경한다.
2. Generator·Template과 Generated SQL을 갱신한다.
3. Fresh Install과 Upgrade Migration을 준비한다.
4. Seed·Sequence/Identity·Index·Constraint를 검증한다.
5. Repository·Service·API·Frontend·Batch Consumer를 갱신한다.
6. Backup Manifest와 Rollback 또는 Forward Recovery를 준비한다.
7. 세 Vendor Drift와 Read/Write Smoke를 확인한다.

## 17. OpenAPI·Generated Client·JavaDoc

Backend OpenAPI를 생성하고 Operation ID·Schema·Error를 검토한다. Frontend Generated Client를 재생성하고 Route의 `expectedOperationIds`와 일치시킨다. Generated Output을 수동 편집하지 않는다.

Public API/SPI, 중요한 상태·동시성·복구·보안 로직에는 계약과 실패 의미를 설명하는 JavaDoc을 작성한다.

## 19. EDU — 멱등 상태 변경

### Source와 설정

- 기준 Domain: `cpf-member/**`
- 실행 Runtime: `cpf-tools/runtime/cpf-local-runtime/**`
- DB Vendor: 선택한 Vendor Pack
- ADM 확인: 거래 로그·통합 Trace·감사 로그

### 정상 실습

1. 상태 변경 요청에 Resource ID, Expected Version, Idempotency Key를 넣는다.
2. 응답의 새 Version과 Transaction ID를 기록한다.
3. 같은 Key로 재요청한다.
4. DB 갱신과 Audit가 한 건인지 확인한다.

### 오류 재현

오래된 Version으로 요청해 Conflict를 확인하고 최신 상태를 재조회한다. 응답을 Toxiproxy로 차단해 같은 Key 조회로 기존 결과를 확인한다.

### 고객 업무 전환

Entity·상태·Permission·Data Scope·대사 기준만 고객 업무로 교체한다. CPF Context·Error·Idempotency·Audit·Reconcile 계약은 유지한다.
