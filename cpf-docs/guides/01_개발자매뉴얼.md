## 3. Generator Golden Journey

Generator Parameter는 기준 Commit의 `cpf-tools/generator/create-domain.ps1` 선언을 정본으로 한다. 작업 순서는 다음과 같다.

1. `-DryRun` 또는 동등 기능으로 **생성하지 않고** 계획을 본다.
2. Module/Package/System Code/Profile/Capability/Provider/DB Vendor를 확인한다.
3. 기존 파일 충돌과 예약 경로를 확인한다.
4. 생성될 Migration·OpenAPI·Test·Manifest를 확인한다.
5. 승인된 입력으로 Apply한다.
6. 생성 후 Manifest와 resolved starter lock을 Diff한다.
7. Generated 영역과 고객 편집 영역을 구분한다.

정상 결과:

- 생성 대상 경로가 의도한 Domain 아래에만 존재한다.
- 선택하지 않은 Provider/Starter가 들어오지 않는다.
- DB Vendor Pack과 Profile이 일치한다.
- 충돌 파일은 덮어쓰지 않는다.
- Manifest에 Source 기준과 선택 결과가 남는다.

실패 예:

| 실패 | 원인 | 행동 |
|---|---|---|
| 기존 Module 이름 충돌 | 이미 존재 | 이름/경로 재결정 |
| 지원하지 않는 Vendor | Contract 불일치 | 지원 Vendor 선택 |
| Profile/Capability 모순 | Browser인데 Session 미선택 등 | 선택표 재검토 |

| Apply 중 부분 생성 | I/O/권한 | 생성 Manifest와 실제 파일 비교 후 정확 경로만 정리 |

## 4. 업무 Source 구조

```text
<domain>/
├─ src/main/java/<base>/
│  ├─ api/             # HTTP/메시지 진입·DTO
│  ├─ application/     # Use Case·Transaction·Permission·Idempotency
│  ├─ domain/          # 상태·불변식·정책
│  ├─ persistence/     # Repository·Query·Ledger
│  ├─ messaging/       # Outbox/Inbox/Event Adapter
│  └─ integration/     # HTTP/TCP/SFTP 등 Adapter
├─ src/main/resources/
│  ├─ db/<vendor>/     # Migration
│  └─ <sql-root>/      # SQL/Mapper
└─ src/test/           # Unit·Contract·Integration·Fault
```

| 계층 | 책임 | 금지 |
|---|---|---|
| API | HTTP/JSON/Validation/Authentication Context | DB Query·상태 전이 |
| Application | Use Case·Transaction·Permission·Idempotency | Provider SDK 타입 노출 |
| Domain | 상태·금액·정책 불변식 | HTTP/DB/Kafka 세부 구현 |
| Persistence | Query·Version·Ledger·Migration | 화면 권한 판정 |
| Adapter | Provider 연결·오류 매핑 | 업무 최종 상태 소유 |

## 5. Query 개발

### 5.1 요구 계약

Query는 부작용이 없고 다음을 명시한다.

- 검색 Field·기본값·허용 범위.
- Paging·Sort 안정성.
- Data Scope와 Masking.
- 기준시각(`asOf`)과 Owner.
- 최신 `version` 또는 변경 탐지 정보.
- 0건/1건/다건/대량 조회 한도.

### 5.2 단계

1. Criteria DTO를 정의한다.
2. 입력 범위를 검증한다.
3. Actor의 Data Scope를 Query 조건에 포함한다.
4. 안정된 Sort Key를 지정한다.
5. Repository/Mapper가 필요한 Column만 조회한다.
6. Masking은 권한 결과에 따라 적용한다.
7. API 응답에 기준시각·페이지 정보·Owner를 포함한다.
8. Unit/Repository/Contract Test를 작성한다.

### 5.3 실패·경계

- 허용되지 않은 Sort Field → 400.
- Page Size 초과 → 제한 또는 400.
- Scope 밖 Row → 403 또는 결과 제외 정책 명시.
- DB Timeout → Dependency Error, 재시도 여부 분리.
- Snapshot이 오래됨 → 최신 재조회 안내.

## 6. Versioned Command 개발

상태 변경 Command의 최소 입력:

```json
{
  "expectedVersion": 7,
  "reason": "업무 사유",
  "idempotencyKey": "<uuid>",
  "approvalRequestId": "<optional>"
}
```

처리 순서:

1. Authentication Context 확인.
2. Permission + Data Scope 확인.
3. Request Validation.
4. Idempotency Key와 Request Hash 확보.
5. 기존 동일 Key 결과 확인.
6. Owner Row 최신 Version 확인.
7. Domain 전이 규칙 적용.
8. Current Row + History + Audit + Outbox/Attempt를 Transaction으로 저장.
9. Commit 후 결과 Snapshot 저장/반환.
10. 외부 부작용은 Attempt와 후속 처리로 분리한다.

### 6.1 동시성

- `expectedVersion == currentVersion`만 변경.
- 다른 경우 409/Conflict.
- Client/ADM은 최신 상세를 다시 읽고 사용자가 다시 판단한다.
- Version 값만 바꾼 재시도는 수행하지 않는다.

### 6.2 Idempotency

| 상황 | 판정 | 행동 |
|---|---|---|
| 동일 Key·동일 Hash·완료 | 기존 결과 | 재실행 금지 |
| 동일 Key·동일 Hash·진행 | 기존 Operation | 상태 조회 |
| 동일 Key·다른 Hash | Conflict | 새 의도면 새 Key |
| 저장 전 실패 | 실행되지 않음 | 정책에 따라 재요청 |
| Commit 뒤 응답 유실 | UNKNOWN_RESULT 가능 | Operation/Owner 대사 |

## 7. Transaction과 일관성

Transaction은 **한 Owner가 원자적으로 보장할 수 있는 범위**까지만 묶는다.

같은 Transaction에 두기 좋은 것:

- 업무 Current Row.
- History.
- Idempotency Result.
- Audit.
- Outbox.

같은 Local Transaction으로 가장하면 안 되는 것:

- 외부기관 HTTP 성공.
- Broker ACK.
- 다른 Service의 DB 갱신.
- Object Store의 최종 처리.

이들은 Attempt·State·Reconcile 계약으로 연결한다.

## 8. Outbox·Inbox·Kafka

### 8.1 Producer

1. 업무 변경과 Outbox를 같은 Transaction에 저장한다.
2. Event ID·Aggregate ID·Schema Version·Payload Hash를 기록한다.
3. Publisher가 Lease/Claim으로 전송 대상을 확보한다.
4. Broker 결과와 Attempt를 기록한다.

### 8.2 Consumer

1. Event ID/Key를 읽는다.
2. Inbox 중복 여부를 확인한다.
3. 업무 Transaction을 수행한다.
4. Inbox 완료와 업무 Commit을 일치시킨다.
5. Commit 이후 ACK한다.

### 8.3 오류 재현

- Publish 직전 Process Kill.
- Publish 성공 후 상태 저장 전 Kill.
- Consumer 업무 Commit 뒤 ACK 유실.
- 동일 Event 중복 Delivery.
- Poison Payload.

복구:

- Outbox/Inbox/Attempt Ledger를 기준으로 재개.
- Blind Publish/Blind Consumer 재실행 금지.
- DLQ Replay는 원본 Event와 승인·Reason을 보존.

## 9. 외부기관 HTTP/TCP/전문 연계

### 9.1 호출 전 기록

- `operationId`.
- `attemptId`.
- Target ID.
- Request Hash.
- Deadline/Timeout Budget.
- Idempotency 또는 기관 업무 Key.

### 9.2 Timeout 분류

| 시점 | 판정 | 행동 |
|---|---|---|
| Dispatch 전 | FAILED 가능 | 정책상 재시도 |
| Connect 실패 | Target 미도달 | 다른 Target/Retry 정책 |
| Write 이후 응답 전 | UNKNOWN_RESULT | Status Query/대사 |
| 명시적 4xx | 결정적 실패 | 입력/권한 보정 |
| 명시적 5xx | Provider 상태 확인 | 멱등성·Budget 내 재시도 |

### 9.3 대사

Target Tracking ID 또는 업무 Key로 기관 상태를 조회하고 Owner 원장과 비교한다. 기관 성공/Owner 미반영이면 보상 또는 Owner 확정 정책을 수행하고, 기관 실패/Owner 성공이면 보상·재전송 정책에 따라 종결한다.

## 18. 실제 Build와 생성 검증 절차

Generator와 Build 명령은 기준 Commit의 현재 Script Parameter와 exact match를 유지한다. 현재 기준의 핵심 흐름은 다음과 같다.

```powershell
$repo='D:\WORK_CPF\202412_01_CPF'
& (Join-Path $repo 'gradlew.bat') clean test --no-daemon --stacktrace

pwsh -NoProfile -ExecutionPolicy Bypass -File (Join-Path $repo 'cpf-tools\generator\create-domain.ps1') `
  -DomainName payment `
  -SystemCode PAY `
  -BasePackage com.customer.pay `
  -CapabilityProfile secure-api `
  -DatabaseVendor postgresql `
  -DryRun
```

Dry Run이 정상이라면 생성 대상·충돌·Profile/Provider/DB Vendor를 검토한 뒤 **동일 입력에 `-Apply`를 사용한다.** `create-domain.ps1`의 현재 계약은 `-DryRun`, `-GeneratePatch`, `-Apply`를 서로 다른 실행 의도로 구분한다. Dry Run 결과를 검토하지 않은 채 Apply로 바로 넘어가지 않는다.

**정상 결과를 기록할 Evidence**

- Gradle exit code.
- 생성 Manifest와 resolved starter list.
- 신규/변경 파일 목록.
- Migration 목록.
- OpenAPI/Generated Client 결과.
- Unit/Contract/Fault Test 결과.

- Error/Retry 의미.
- Idempotency/Version.
- Timeout/Unknown-result.
- Security/Audit.
- Example과 금지 사용법.

Internal 구현 상세를 Public JavaDoc에 노출하지 않는다.

## 20. Saga·Compensation

여러 Owner가 참여하는 업무는 각 Step을 독립 Transaction으로 처리하고 Saga 상태를 Durable하게 기록한다.

```text
REQUESTED -> STEP_A_DONE -> STEP_B_PENDING -> COMPLETED
                                                   -> STEP_B_UNKNOWN -> RECONCILING
```

필수:

- sagaId/stepId/operationId/attemptId.
- Step version/idempotency.
- Step timeout.
- Compensation eligibility와 역순.
- Partial compensation.
- Unknown Step의 대사.
- 자동 복구 불가 시 Manual Decision + Approval/Audit.

## 21. Data Quality·Lineage·Retention

업무 데이터는 입력 Source, Transformation, 저장 Table/Field, 외부 전달, Quality Rule, Reconcile Rule, Owner를 연결한다. 개인정보/업무 데이터 유형별 retention, purge, archive, legal hold, deletion을 정의하고 Backup Restore 뒤 보존 정책을 재적용한다.

## 22. ADM 확인 절차

개발 종료 전 ADM에서 다음을 확인한다.

1. Route/Menu가 노출되는가.
2. Query가 기준시각/Version/Masking을 보여 주는가.
3. Command Button Permission/Scope가 맞는가.
4. 409 Conflict가 최신 상태 재조회로 연결되는가.
5. 응답 유실이 UNKNOWN_RESULT로 표시되는가.
6. Operation/Attempt/Trace/Audit로 대사할 수 있는가.
7. Reprocess/Compensation/Rollback가 필요한 경우 별도 권한과 Reason이 있는가.

## 26. Starter 선택 — 개발자 관점

`minimal-domain`, `web-api`, `secure-api`, `browser-bff`, `event-service`, `batch-service` 중 하나를 시작점으로 고르고, Data/Messaging/Integration/File/Notification/Security/Platform Operations Capability를 업무 필요에 따라 추가한다. Provider Slot은 00 매뉴얼 21~23장의 39개 Catalog를 따른다.

개발자가 확인할 산출물:

- Domain Manifest와 `resolvedStarters`/Profile Version.
- 선택하지 않은 Capability의 Dependency/Bean/Config/SQL 부재.
- Provider Binding의 단일성.
- Public API에 Provider SDK type이 노출되지 않음.
- Customer-owned Source와 Generator-owned Source의 경계/Hash.

### 27.1 예제를 고객 업무로 전환하는 규칙

1. ID의 `requiredFields`를 고객 DTO/JobParameter에 대응시킨다.
2. `businessStates`를 고객 상태기계로 치환하되 UNKNOWN_RESULT/RECONCILED 같은 복구 의미를 삭제하지 않는다.
3. `exceptionScenarios`를 Fault Test에 유지한다.
4. `requiredVerification`을 Unit/Integration/Failure/Recovery/Concurrency Test와 ADM 확인으로 연결한다.
5. Reference DB/Table/Handler를 고객 Owner로 바꾸되 Idempotency·Version·Lease·Attempt·Audit 계약은 유지한다.
6. Reference 전용 Sandbox/Seed는 고객 Runtime에 복사하지 않는다.
