## 4. 계층 구현

### API

- 기술 Vendor Type, Entity, 내부 Exception을 노출하지 않는다.
- Null, Enum, Timezone, Paging, Sort, Error, Permission, Idempotency, Timeout을 계약화한다.

### Application

- Use Case Transaction과 상태 전이를 소유한다.

### Persistence

- Query ID·Table·Index·Constraint Owner를 명확히 한다.
- Vendor SQL·Migration·Rollback·Drift를 함께 변경한다.
- Optimistic Version과 Unique Constraint를 Application 재검증과 결합한다.

## 6. Transaction·동시성

### Local Transaction

```text
Controller → Application Service @Transactional
→ Domain Validation → Repository
→ Outbox 저장 → Commit
```

### 원격 변경

```text
Local 상태/Intent 저장 → Remote Command
→ 응답 수신: Success/Failure
→ 응답 유실: UNKNOWN_RESULT → Status Query/Reconcile
```

### Idempotency

Key만 비교하지 않고 Scope·Principal·Target·Canonical Request Hash·TTL을 비교한다. 같은 Key에 다른 Hash가 오면 `Conflict`로 거부한다.

### Expected Version

- UI 조회 Version을 Command에 전달한다.
- Update 조건에 Version을 포함한다.
- 0건 Update는 최신 상태 재조회 후 충돌로 반환한다.
- Blind Retry로 덮어쓰지 않는다.

## 7. Local·Remote Adapter

| 항목 | Local | Remote |
|---|---|---|
| Contract | 같은 Public API | 같은 Public API·OpenAPI |
| Transaction | 같은 JVM 경계 | 원격 Transaction 분리 |
| Timeout | Deadline 확인 | Connect·Send·Response·Read |
| Security | 내부 Principal 재검증 | Service Identity·Audience·Signature |
| Error | 표준 Error | Transport Mapping 후 표준 Error |
| Unknown | 대개 Commit 결과 확인 가능 | Response loss 시 상태 조회 필요 |

Parity Test는 같은 Scenario를 두 Adapter에 실행하고 결과·오류·Audit·Trace를 비교한다.

## 8. Kafka·Outbox·Inbox

확인된 Starter Property:

| Key | Type | Default | 범위·오류 |
|---|---|---:|---|
| `cpf.messaging.kafka.acknowledgement-timeout` | Duration | `10s` | 0 이하 거부 |

구현 절차:

1. 업무 데이터와 Outbox를 같은 Transaction에 저장한다.
2. Publisher는 Claim·Lease·Attempt를 기록한다.
3. Kafka ACK 전후 중단을 구분한다.
4. Consumer는 Inbox 또는 업무 Idempotency로 중복 차단한다.
5. Retry Topic·DLT·Replay Permission·Reason·Audit을 연결한다.
6. Broker outage, Rebalance, Duplicate, Late reply, Poison을 시험한다.

## 9. File·Attachment·Archive

기준 Commit에는 Archive·Attachment Public API와 Local Adapter가 존재한다. 적용 시 다음을 확인한다.

- bounded streaming, payload 상한
- Temp→fsync/checksum→atomic publish
- canonical path·symlink·hardlink·device·FIFO 차단
- zip slip, duplicate canonical entry, entry/total/ratio budget
- client cancel, timeout, disk full, process kill, stale temp cleanup
- metadata·Permission·Data Scope·download audit

메모리 전체 적재 API를 새 경로에 추가하지 않는다.

## 10. 외부 REST·전문 연계

- Endpoint는 Config/Registry가 소유하고 업무 코드에 하드코딩하지 않는다.
- TLS·SNI·Certificate·Hostname·Redirect·CIDR·DNS 정책을 검증한다.
- Connect·Send·Response·Read Timeout을 분리한다.
- Mutation Retry는 상대 Idempotency와 Request Hash가 있을 때만 허용한다.
- 고정길이 전문은 byte length·encoding·padding·offset·version·masking을 시험한다.

## 부록 C. 변경 명령 상태 기계

업무 변경 명령은 최소한 다음 상태를 구분한다.

```text
RECEIVED
→ VALIDATED
→ RESERVED
→ EXECUTING
→ SUCCEEDED | FAILED | UNKNOWN_RESULT
UNKNOWN_RESULT → RECONCILING → SUCCEEDED | FAILED | MANUAL_REVIEW
```

| 단계 | 저장할 항목 | 실패 시 조치 |
|---|---|---|
| 수신 | operationId, principal, idempotencyKey, requestHash | 같은 Key·다른 Hash는 Conflict |
| 예약 | target, expectedVersion, timeoutBudget | Unique 충돌 시 기존 결과 조회 |
| 실행 | attemptId, targetInstance, 시작 시각 | 전송 전 실패와 전송 후 실패 분리 |
| 응답 | status, remoteOperationId, protocolStatus | 응답 유실은 성공/실패로 추정하지 않음 |
| 대사 | 상태 조회 시각·결과·담당자 | 기한 초과 시 Manual Review |

Blind Retry 금지 조건:

- 상대 Side Effect 발생 가능성이 있음
- Idempotency 계약 또는 상태 조회 API가 없음
- Request Hash가 기존 요청과 일치하는지 확인하지 못함
- 승인·Expected Version 유효성이 만료됨

## 부록 D. API·Application·Domain·Persistence 구현 체크

### D.1 Controller

- DTO Validation 실패를 표준 Field Error로 반환한다.
- Principal·Permission·Data Scope를 Application 진입 전에 잃지 않는다.
- `operationId`, `idempotencyKey`, `expectedVersion`, `reason`, `approvalId`를 Command에 전달한다.
- Entity·Repository·Vendor Exception을 Response에 노출하지 않는다.

### D.2 Application Service

- Local Transaction 시작·종료를 소유한다.
- 허용 상태 전이와 Expected Version을 검증한다.
- 업무 데이터와 Outbox·Audit Intent의 동일 Transaction 여부를 결정한다.
- Remote Side Effect 이후 응답 유실을 `UNKNOWN_RESULT`로 기록한다.

### D.3 Domain

- 상태 전이 Method에 현재 상태·입력·권한 조건을 둔다.
- 금액·수량·일시·코드·식별자를 Value Object 또는 명시 Validation으로 보호한다.
- `setStatus()` 같은 무제한 변경 경로를 두지 않는다.

### D.4 Persistence

- Unique Constraint와 Application Idempotency 검증을 함께 둔다.
- Version Column을 Update 조건에 포함한다.
- Paging·Sort Column은 Allowlist로 제한한다.
- Query Owner와 Vendor SQL Resource를 일치시킨다.

## 21. 표준 API·Application·Domain·Persistence 구현

### 21.1 API

1. 업무 Endpoint의 Owner Domain과 Consumer를 먼저 기록한다.
2. 표준 Header·거래 식별자·Channel·Authentication Context를 공통 Filter/Argument Resolver에서 받는다.
3. Request DTO는 길이·형식·Enum·상호 의존 Validation을 선언한다.
4. 상태 변경 Request에는 `operationId`/`idempotencyKey`, 필요한 경우 `expectedVersion`, `reason`, `approvalId`를 포함한다.
5. Error는 공통 Error Contract로 Mapping하고 내부 Stack/Secret/SQL을 외부 Message에 넣지 않는다.
6. Paging은 Page Size 상한, Sort Allowlist, Stable Sort Key를 둔다.
7. OpenAPI에는 Permission, Error, Example, Idempotency, Version 충돌을 적는다.

### 21.2 Application

- Command와 Query를 분리한다.
- Transaction Owner를 한 Use Case에 고정한다.
- Remote Call을 DB Transaction 안에서 장시간 기다리지 않는다.
- Side Effect 전 실행 원장/Outbox를 기록한다.
- 응답 유실이 가능한 명령은 조회 가능한 식별자를 먼저 만든다.
- Audit 저장 실패를 업무 성공과 어떻게 분리할지 명시한다.

### 21.3 Domain

- 상태 전이는 허용 상태와 명령 조합으로 제한한다.
- Domain Event에는 재처리 가능한 업무 식별자와 Version을 포함한다.
- 현재 시각·외부 ID·Random을 주입해 Test 가능하게 한다.
- Aggregate Version을 Persistence와 API `expectedVersion`에 연결한다.

### 21.4 Persistence·SQL

- Runtime Query는 Vendor-neutral Contract와 Vendor별 SQL을 함께 관리한다.
- Migration은 신규 설치·Upgrade·Rollback·Drift 경로를 모두 준비한다.
- Unique Key는 멱등 Scope와 Request Hash 충돌을 표현해야 한다.
- Index는 조회·Claim·Reconciliation의 실제 Predicate 순서를 기준으로 검토한다.
- PII/Secret은 암호화·마스킹·원문 조회 Permission과 Audit 경로를 분리한다.

## 22. Transaction·동시성·결과 불명

### 22.1 Local Transaction

- Controller가 아니라 Application Service가 Transaction Owner다.
- `readOnly`, Propagation, Isolation, Rollback Exception을 명시한다.
- Self Invocation으로 `@Transactional`이 우회되지 않는지 Test한다.
- Deadlock Retry는 같은 업무 명령 전체를 무조건 반복하지 않고 멱등 원장과 결합한다.

### 22.2 Remote Command

```text
Operation/Idempotency 식별자 생성
→ 요청 Hash 저장
→ 대상 호출
→ 응답 수신: 상태 확정
→ Timeout/연결 단절: UNKNOWN_RESULT
→ 동일 식별자로 대상·원장 조회
→ 결과 확정 후 Retry 또는 Compensation
```

같은 Key와 다른 Request Hash는 `409` 성격의 충돌로 중단한다. 같은 Key와 같은 Hash는 기존 결과를 반환하거나 조회 위치를 알려야 한다.

### 22.3 Expected Version

- Version 불일치 시 사용자 입력을 최신 상태에 자동 합치지 않는다.
- 최신 상태를 다시 읽고 변경 의도를 재확인한다.
- 운영 UI는 409를 일반 오류가 아니라 동시 변경으로 표시한다.

## 23. Local·Remote Service Call

| 항목 | Local Adapter | Remote Adapter | 동등성 Acceptance |
|---|---|---|---|
| 계약 | 같은 Public Port | 같은 Public Port | Request/Response/Error 동일 |
| 인증 문맥 | JVM Context | 신뢰 Header/Token | Principal·Data Scope 동일 |
| Transaction | 호출자/Owner 설계에 따라 | 분리 | 원격 Side Effect를 Local Rollback으로 가정하지 않음 |
| Timeout | 내부 Budget | Connect/Response/Overall | Budget 초과 분류 동일 |
| Retry | Exception 기준 제한 | Network·Status 기준 제한 | 비멱등 명령 Retry 금지 |
| Trace | Context 전달 | `traceparent` 등 전달 | 동일 Transaction/Trace 연결 |

Contract Test는 같은 Scenario를 Local·Remote Adapter에 반복해 결과·오류·권한·Timeout 의미를 비교한다.

## 24. Kafka·Outbox·Inbox

### Producer

1. 업무 DB Transaction에서 Outbox를 기록한다.
2. Message ID, Aggregate ID·Version, Event Type, Payload Schema Version, Trace, 생성 시각을 고정한다.
3. Broker ACK 전 Outbox를 Published로 확정하지 않는다.
4. ACK 유실 시 Broker/Outbox 상태를 대사한다.

### Consumer

1. Inbox 또는 처리 원장으로 중복을 차단한다.
2. Payload Size·Schema·Signature·권한 Context를 검증한다.
3. Side Effect와 Inbox 완료 상태의 Transaction 경계를 명시한다.
4. Retry 가능 오류와 DLT 대상 오류를 구분한다.
5. Replay 시 원 Message ID와 Replay Operation ID를 보존한다.

현재 Kafka Runtime, Process Kill, Late Reply, DLT Replay는 환경에서 확인하므로 운영 반영 전에 `05`의 Runtime Matrix를 실행한다.

## 25. File·Attachment·Archive·외부 연계

- Upload: Size·Extension·MIME·Checksum·Virus Scan·Temporary/Committed 상태를 분리한다.
- 대량 File Job: Dry Run → Validation → Approval → Apply → Row별 결과 → Partial/Unknown → Reconcile/Rollback 순서다.
- Download: Data Scope·Masking·건수 상한·Reason·Audit를 적용한다.
- Archive: Source Stream을 전체 메모리에 적재하지 않고 Streaming·Checksum·Retention을 확인한다.
- 외부 REST/전문: Scheme·TLS·Host/CIDR Allowlist, Redirect, DNS Rebinding, Timeout, Response Size를 검증한다.
- Shell/Process: 실행 파일 Allowlist, Argument 분리, Working Directory, Timeout, Output Size, Exit Code를 제한한다.

## 26. Security·Permission·Audit

1. Authentication과 Authorization Owner를 구분한다.
2. Controller Route가 열린 것과 Method Permission이 허용된 것을 혼동하지 않는다.
3. Data Scope는 Query Predicate에 적용하고 UI 필터로만 제한하지 않는다.
4. Masked List와 PII Raw 조회 API를 분리한다.
5. Raw 조회·위험 조치·Export는 구체적 Reason과 별도 Permission이 필요하다.
6. Approval Snapshot은 마스킹 Payload와 Hash를 고정한다.
7. Break-glass는 좁은 Scope·짧은 TTL·Owner Command의 명시적 소비·사후검토를 요구한다.
8. Audit에는 Actor, Action, Target, Before/After Hash, Reason, Approval, Operation ID, Result를 남긴다.

현재 BFF FilterChain Authorization은 배포 전에 확인한다. 모든 Privileged Endpoint의 401/403 Negative Test가 통과하기 전에는 UI Menu 숨김만으로 보호됐다고 판정하지 않는다.

## 27. DB Migration·Upgrade·Rollback

### 변경 순서

```text
Canonical Schema 수정
→ 3 Vendor Migration 생성
→ Checksum 갱신
→ Runtime Query/Metadata 갱신
→ 신규 설치 Test
→ 기존 Version Upgrade Test
→ Rollback 또는 Forward Recovery Test
→ Drift 검사
→ Application 호환 Test
```

현재 V86 BFF Credential Vault, V87 Batch Remote Message Ledger, V88 Scheduler Durable Launch Outbox, V89 Batch Execution Idempotency, V90 Deployment Request Hash/Reconciliation, V91 BZA Bootstrap Claim Recovery가 3 Vendor 경로에 추가됐다. 실제 Oracle·PostgreSQL·MariaDB 실행은 환경에서 확인하므로 Script 존재만으로 적용 성공을 기록하지 않는다.

## 28. OpenAPI·Generated Client·Frontend 연결

- Backend 실행 결과에서 전체 Public API·DTO·Validation·Error Contract를 Export한다.
- Snapshot의 `x-cpf-source-sha`가 기준 Commit과 같아야 한다.
- Generated Marker는 OpenAPI Hash, Generated File Hash, Generator Hash, Source SHA를 포함한다.
- `CPF_SOURCE_SHA`를 생략했을 때 현재 Git HEAD 비교를 건너뛰는 Gate는 허용하지 않는다.
- ADM/BZA 현재 Snapshot은 일부 인증 API와 자유 Schema 중심이므로 기능 제공이다. Raw `fetch`와 Generated Client 혼재를 구현 충족으로 판정하지 않는다.

## 56. API·Application·Domain·Persistence 구현 절차

### API

- Entity·Vendor Type·내부 Exception을 노출하지 않는다.
- Validation 오류는 Field와 허용 범위를 반환한다.
- Time은 Timezone·정밀도·포맷을 명시한다.
- Paging·Sort Allowlist와 최대 Size를 둔다.
- 변경 API는 Idempotency Key, Expected Version, Reason, 필요 시 Approval ID를 받는다.

### Application

```text
Controller
→ Authentication·Permission·Data Scope
→ Request Validation
→ Idempotency Reservation
→ @Transactional Use Case
→ Domain State Transition
→ Repository + Outbox
→ Commit
→ Remote Dispatch 또는 Result Projection
```

응답이 유실될 수 있는 변경은 Operation ID 조회와 Reconcile Use Case를 함께 제공한다.

### Domain

- 현재 상태를 무시하는 Setter 대신 명시적 전이 Method를 사용한다.
- 중복·기간 겹침·금액·수량·상태 Invariant를 Aggregate 내부에서 검증한다.
- 외부 I/O·Clock·Random은 Port로 분리해 Test 가능하게 만든다.

### Persistence

- Query와 Command Repository를 필요에 따라 분리한다.
- Unique Constraint와 Application 검증을 함께 둔다.
- Optimistic Version을 Update 조건에 포함한다.
- 대량 조회는 정렬 Key·Paging·Index를 고정한다.
- Vendor별 Type·Sequence·Identity·Lock 차이를 Migration과 Test로 확인한다.

## 57. 멱등 변경 기능 구현 예시

```text
POST /api/<resources>
Idempotency-Key: <operation-id>
If-Match: <expected-version>
X-Operation-Reason: <reason>
```

처리 순서:

1. Principal·Target·Operation Scope를 정규화한다.
2. Request Body를 Canonical JSON으로 변환하고 SHA-256 Hash를 계산한다.
3. Scope+Key가 없으면 Reservation을 생성한다.
4. 같은 Scope+Key·같은 Hash면 기존 결과를 반환하거나 상태 조회 위치를 반환한다.
5. 같은 Scope+Key·다른 Hash면 충돌로 거부한다.
6. Version 조건을 포함해 업무 상태를 변경한다.
7. 응답 전에 Operation 결과와 Audit를 저장한다.
8. 응답 유실 시 Operation 조회로 결과를 확정한다.

## 58. Kafka·Outbox·Inbox 구현 워크북

### Outbox Record

- Message ID, Aggregate Type·ID·Version
- Event Type·Schema Version
- Payload Hash·Created At
- Transaction·Trace·Attempt
- Publish Status·Lease·Attempt·Last Error

### Producer

1. 업무 상태와 Outbox를 같은 DB Transaction에 저장한다.
2. Publisher가 Lease로 Claim한다.
3. Kafka ACK가 확인되면 Published 상태를 저장한다.
4. ACK 응답 유실은 Broker Key와 Outbox 상태를 대사한다.
5. Payload Size·Header·Schema·PII를 검증한다.

### Consumer

1. Producer ID·Tenant·Environment·Schema·TTL을 검증한다.
2. Inbox 또는 업무 Idempotency로 중복을 차단한다.
3. Side Effect와 Inbox 완료 Transaction을 정의한다.
4. Retry 가능 오류, DLT 대상, 수동 Replay 대상과 최대 Attempt를 구분한다.
5. Replay는 원 Message ID와 Replay Operation ID를 모두 보존한다.

## 59. File·Attachment·외부 연계 구현 워크북

- Upload는 Stream으로 읽고 Size·MIME·Extension·Checksum을 검증한다.
- Temp 저장 후 fsync·검사·Checksum을 확인하고 Commit 위치로 이동한다.
- Path Traversal·Symlink·Hardlink·Device·FIFO·Zip Slip을 차단한다.
- Download는 Data Scope·Masking·건수·Byte 상한·Reason·Audit를 적용한다.
- 외부 REST는 Scheme·Host·Port·CIDR·DNS Pin·TLS/SNI·Redirect·Timeout·Response Size를 검증한다.
- 변경 요청 Retry는 상대 Idempotency와 Request Hash가 있을 때만 허용한다.
- Timeout·Client Cancel·Disk Full·Process Kill 후 Temp·Ledger·업무 상태를 대사한다.

## 61. 3DB Migration 절차

1. MariaDB·PostgreSQL·Oracle의 신규 설치 Script를 작성한다.
2. 기존 Version Upgrade Script와 Checksum을 작성한다.
