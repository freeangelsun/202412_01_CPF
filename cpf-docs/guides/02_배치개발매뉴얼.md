## 4. Tasklet·Chunk

### Tasklet

외부 Process·단일 업무 조치에 사용한다. Side Effect 전후 Checkpoint와 Unknown 판정 방법을 기록한다.

### Chunk

```text
Read N → Process N → Write N → Commit
```

- Reader 재시작 위치와 정렬 Key 고정
- Processor 순수성 또는 중복 영향
- Writer Upsert·Unique·Version 정책
- Chunk 재시도 시 중복 안전성
- Skip Item의 별도 원장과 재처리 기준

확인된 Default:

| Property | Default | 제한 |
|---|---:|---|
| `cpf.batch.execution.default-chunk-size` | 100 | 0은 Default, 범위 1~10,000 |
| `cpf.batch.execution.max-partition-count` | 256 | 0은 Default, 범위 1~10,000 |
| `cpf.batch.execution.remote-poll-interval-ms` | 1000 | 0은 Default, 범위 10~60,000 |
| `cpf.batch.execution.remote-timeout-ms` | 3600000 | 0은 Default, 범위 1,000~86,400,000 |
| `cpf.batch.execution.remote-chunk-max-wait-timeouts` | 40 | 0은 Default, 범위 1~10,000 |
| `cpf.batch.execution.remote-chunk-throttle-limit` | 256 | 0은 Default, 범위 1~10,000 |

운영 환경은 Default 사용 여부와 용량 근거를 기록한다.

## 7. Idempotency 구현과 검증 기준

현재 Adapter는 `idempotency_scope + idempotency_key`로 Reservation을 조회하고 Canonical `request_hash`, Job/Definition/Approval, Plan Checksum을 비교한다. 같은 Scope·Key와 다른 불변 요청은 `CpfBatchIdempotencyConflictException`으로 거부한다. Duplicate Insert 경합에서도 Winner Reservation의 Hash를 다시 검증한다.

남은 검증은 3 Vendor Unique Constraint, 동시 Start, RESERVED 뒤 Process Kill, Terminal Result Replay, Reconcile Retry다.

## 8. Lease·Claim·Fencing

현재 구현은 `CPF_BATCH_EXECUTION_EPOCH`의 Job별 최신 Fencing Token을 단조 증가시키고, 낮은 Token을 거부하며, Bind Transaction에서 Epoch Row를 잠가 Token 교체와 상태 갱신 경합을 차단한다. 다중 인스턴스·DB 장애·Clock/Lease 경계는 실행 검증이 필요하다.

필수 Scenario:

1. Manager A가 Lease Epoch 10 획득.
2. A 중단 후 B가 Epoch 11 획득.
3. A의 늦은 Write·Completion은 거부.
4. B 결과만 Current로 확정.
5. Lease DB 장애·Clock Skew·Heartbeat 지연을 분류.

## 부록 D. Start·Bind 응답 유실과 대사

현재 `CpfSpringBatchExecutionControl.start()` 순서는 다음과 같다.

```text
ledger.reserve
→ fencing.assertCurrent
→ Job materialize
→ JobOperator.start
→ BatchExecutionLink 생성
→ ledger.bind
```

`JobOperator.start` 후 `ledger.bind` 전에 Process가 중단되면 Spring Batch 실행은 존재하지만 CPF Link가 없을 수 있다. 운영 절차:

1. `idempotencyKey`로 CPF Control 행을 조회한다.
2. 동일 Job Parameter의 `cpfExecutionId`로 Spring `JobExecution`을 조회한다.
3. 실행이 존재하면 새 Job을 시작하지 않는다.
4. `reconcile(cpfExecutionId)` 또는 승인된 복구 Command로 Link를 재구성한다.
5. 실행이 없다는 근거가 확인된 경우에만 재실행한다.

## 부록 E. 현재 Idempotency·Fencing 주의사항

### E.1 Idempotency

현재 JDBC Adapter는 `idempotency_key`로 기존 `cpf_execution_id`를 반환한다. Request Hash·Scope·Definition Version·Parameter Hash 충돌을 같은 조회에서 검증하지 않는다. 따라서 같은 Key에 다른 입력이 들어오지 않도록 호출자가 Key Scope를 분리하고, 제품 보강 전에는 기존 Request와 Definition·Parameter·Approval을 운영 대사로 비교한다.

### E.2 Fencing

`assertCurrent`는 Job별 최신 Epoch와 실행의 Fencing Token을 비교한다. Takeover Test에서는 이전 Manager의 늦은 Bind·Write·Completion이 거부되는지 확인한다.

## 부록 F. Scheduler Dispatch 상태 흐름

기준 Commit의 Scheduler는 다음 순서를 사용한다.

```text
runtime policy 확인
→ Leader fencing token 확인
→ due schedule 조회
→ available window·business calendar 확인
→ fenced trigger insert
→ 승인 실행 Request Resolve
→ executionControl.start
→ JobExecution ID 연결
→ next_fire_at fenced advance
```

중요 경계:

- Business Calendar Runtime이 중지된 경우 영업일 의존 Schedule을 소진하지 않는다.
- Trigger Insert는 Duplicate Key를 중복 실행 방지 신호로 사용한다.
- Job Start 후 Trigger mark 전 중단은 Trigger·Execution 대사가 필요하다.
- `scheduleId + scheduledAt`를 Idempotency Key로 사용한다.
- `next_fire_at` Update 0건은 동시 변경 또는 Fencing 거부로 처리한다.

Misfire 정책은 Schedule 정의·SQL·ADM 화면과 함께 확인하며, Source에서 확인하지 않은 상태 이름을 문서에 추가하지 않는다.

| `max-log-archive-bytes` | `1073741824` | 1 GiB |
| `process-timeout-seconds` | `60` | Process 제어 Timeout |
| `max-process-output-bytes` | `1048576` | stdout/stderr 1 MiB 상한 |
| `log-archive-ttl-seconds` | `600` | Log Archive 보존 초 |

Service별 `serviceId`, `artifactId`, `installRoot`, `logRoot`, `systemdUnit`, `windowsStartScript`, `healthUrl`, `runtimeControlUrl`, `runtimeMode`, `environmentCode`, `releaseChannel`을 설정한다. 설치 전 Artifact Hash·Signature·Digest Header·Key 유효기간·Service Identity·경로 권한·Pinned Address를 확인하고, 적용 후 Health·Current Pointer·Artifact State MAC·Build SHA를 대사한다.

## 부록 H. Batch 검증 Scenario

| Scenario | 기대 판정 |
|---|---|
| 같은 Idempotency Key·같은 Request | 기존 Execution 조회 또는 동일 결과 Replay |

## 부록 I. Primary Engine·Job 등록·진행 상태

Spring Batch는 Job·Step·JobRepository·ExecutionContext·Checkpoint·Restart의 **Primary Engine**이다. CPF Job 등록은 Published Definition, Definition Version, Execution Plan Version, SHA-256 Checksum, Owner Domain, Executor Reference를 묶어 수행한다. 같은 Job ID의 새 정의는 기존 Version을 덮어쓰지 않고 새 Version으로 등록하며, 실행 중에는 Definition·Plan·Artifact Version을 고정한다.

진행 상태는 CPF Execution ID와 Spring JobExecution·StepExecution을 연결해 Read·Write·Skip·Error Count, Partition·Worker, Checkpoint, Last Update, Exit Status를 조회한다. ADM 진행률이 Spring Metadata와 다르면 Reconcile 전까지 확정 상태로 표시하지 않는다.

## 20. Job Definition·Plan·Step 계약

### 20.1 승인 실행 요청

`BatchApprovedLaunchRequest`의 필수 입력:

| 입력 | 제약 |
|---|---|
| `definition` | 상태 `PUBLISHED`, Checksum SHA-256 |
| `plan` | Definition의 Job ID·Version과 일치, Integrity 검증 |
| `parameters` | Canonical immutable 값으로 정규화 |
| `approvalId` | 1~120자 |
| `operatorId` | 1~120자 |
| `reason` | 5~500자 |
| `idempotencyKey` | 8~200자, `[A-Za-z0-9._:-]` |
| `fencingToken` | 양수 |

Idempotency Scope는 `jobId:definitionVersion:approvalId`이고 Request Hash는 Definition·Plan·Parameter·승인 범위를 Canonical Digest로 계산한다. 같은 Scope/Key에 다른 Hash가 오면 재실행하지 않고 충돌로 처리한다.

### 20.2 Execution Plan

- `planId`는 Job ID와 일치한다.
- `planVersion`은 Definition Version과 일치한다.
- Step은 1개 이상이며 `stepId`가 중복되면 안 된다.
- Success/Failure Transition Target은 등록된 Step 또는 `END`여야 한다.
- Plan Checksum은 SHA-256이다.
- Plan을 저장·전송한 뒤 실행 시점에 다시 Integrity를 검증한다.

### 20.3 Step Definition

| 항목 | 의미·검증 |
|---|---|
| `stepId` | 1~100자 식별자 |
| `executorType` | Tasklet·Chunk·Remote·Protocol 등 Definition Enum |
| `executorReference` | 실제 Registry/Bean/Handler 식별자 |
| `parameters` | Step 고정 Parameter |
| `partitionCount` | 기본 1, 제품 상한 10,000; 운영 상한은 `maxPartitionCount` |
| `nextOnSuccess`, `nextOnFailure` | Flow Transition |
| `restartable` | 실패 뒤 Restart 허용 여부 |

Definition이 허용하더라도 Runtime Property 상한, Worker Pool Capacity, DB Connection, Kafka Partition 수를 넘으면 실행을 거부하거나 Preview에서 차단한다.

## 21. Tasklet·Chunk·Reader·Processor·Writer

### 21.1 Tasklet

Tasklet은 하나의 명확한 Side Effect 또는 짧은 Control 작업에 사용한다.

1. Input Parameter와 Restart 의미를 정의한다.
2. 외부 Side Effect 전 멱등 원장을 기록한다.
3. ExitStatus와 BatchStatus를 혼동하지 않는다.
4. Process Kill 뒤 재호출 가능한지, 결과 조회가 필요한지 명시한다.
5. Long-running Loop는 Chunk/Partition 또는 별도 Worker로 전환한다.

### 21.2 Chunk

```text
Reader가 Commit 구간만큼 읽음
→ Processor가 업무 Validation/변환
→ Writer가 Side Effect 반영
→ Transaction Commit
→ ExecutionContext Checkpoint 저장
```

- `defaultChunkSize` 기본 100, 범위 1~10,000.
- Item 자체 식별자와 Chunk Sequence를 보존한다.
- Skip은 데이터 오류에만 제한하고 시스템 오류를 무시하는 수단으로 사용하지 않는다.
- Retryable Exception, Retry 횟수, Backoff와 최종 실패 상태를 정의한다.
- Writer가 외부 API를 호출하면 Item별 Idempotency Key와 Result 조회가 필요하다.

### 21.3 Reader·Processor·Writer 선택

| 유형 | Reader | Writer | 핵심 검증 |
|---|---|---|---|
| DB→DB | Paging/Cursor | Batch JDBC/JPA | 정렬 Key, Isolation, 중복·누락 |
| File Import | Streaming CSV/XLSX | Domain Command | Checksum, Row 번호, Dry Run, Partial |
| API Job | DB/Queue | Protocol Adapter | SSRF/TLS/Timeout/Result Unknown |
| Export | DB Paging | Streaming File/Archive | Masking, Disk, Checksum, Retention |
| Center-Cut | Target Provider | Result Ledger | Partition/Chunk/Commit/대사 기준 |

## 22. JobParameter·Identity·Metadata·Checkpoint

### Job Identity

- 식별 Parameter와 비식별 Parameter를 구분한다.
- CPF는 `cpfExecutionId`, `jobId`, `definitionVersion`, `approvalId`, `idempotencyKey`, `fencingToken`, Plan/Definition Checksum을 연결한다.
- Business Date, File Checksum, Schedule ID 등 재실행 의미에 영향을 주는 값은 식별 여부를 명시한다.

### Metadata

- Spring Batch Metadata Schema는 `spring.batch.jdbc.initialize-schema=never`; 운영자가 Vendor별 Migration으로 설치한다.
- CPF Control Ledger는 Spring IDs와 CPF 실행 ID를 연결한다.
- Metadata나 Link Row를 수동 UPDATE해 상태를 맞추지 않는다.

### Checkpoint

- Reader Position과 Writer Side Effect 경계를 함께 검증한다.
- Commit 직후 Process Kill Scenario에서 이미 반영한 Item이 재처리되는지 확인한다.
- ExecutionContext에 Secret·대용량 Payload·직렬화 불가능 객체를 저장하지 않는다.

## 23. 실행 상태·Stop·Restart·Abandon·Recover

CPF Control State:

```text
RESERVED → STARTING → STARTED → COMPLETED
                         ├→ STOPPING → STOPPED
                         ├→ FAILED
                         └→ UNKNOWN_RESULT
FAILED/STOPPED → Restart 조건 검증 → STARTING
복구 불가 실행 → ABANDONED
검증·승인 거부 → REJECTED
```

`UNKNOWN_RESULT`는 Terminal이 아니다. Spring Batch Metadata, CPF Link, Scheduler Outbox, Worker Message Ledger, 외부 Side Effect를 대사해 상태를 갱신한다.

Center-Cut Control API:

| Method·Path | 입력 | 정상 응답 | 실패 처리 |
|---|---|---|---|
| `POST /internal/v1/center-cut/executions` | approvalId, reason, idempotencyKey, fencingToken, parameters | 202 + `BatchExecutionLink` | 응답 유실 시 Key/CPF Execution ID 조회 |
| `POST .../{jobExecutionId}/stop` | reason | 202 accepted | Spring 상태 재조회 |
| `POST .../{jobExecutionId}/restart` | reason, fencingToken | Link | Stale Token 거부 |
| `POST .../{jobExecutionId}/abandon` | reason | 202 | 재시작 불가 영향 확인 |
| `POST .../{cpfExecutionId}/reconcile` | CPF Execution ID | 최신 Link | 미존재·Link 불일치 조사 |

운영 API가 `recover`를 직접 노출하지 않는 경우 내부 Method가 있다는 이유로 화면에서 사용할 수 있다고 설명하지 않는다.

## 24. Idempotency·Request Hash·Reservation

```text
승인 실행 요청 정규화
→ idempotencyScope + key 조회
→ 미존재: requestHash와 RESERVED 기록
→ 같은 Hash: 기존 Reservation/Result 반환
→ 다른 Hash: CpfBatchIdempotencyConflictException
→ STARTING 기록 후 JobOperator.start
→ Spring ID Bind
```

필수 Fault Test:

1. 두 Thread가 같은 Key·Hash로 동시에 Start.
2. 같은 Key·다른 Parameter/Approval/Definition.
3. RESERVED 뒤 Process Kill.
4. JobOperator Start 성공 뒤 Link Bind 실패.
5. Link Bind 성공 뒤 HTTP 응답 유실.
6. Restart와 신규 Start가 동시에 경합.

정상 판정은 실행이 하나라는 사실만이 아니라, 두 호출자가 동일 Reservation/Link를 받거나 명확한 충돌을 받는 것이다.

## 25. Lease·Claim·Fencing

- Scheduler Leader Lease, Trigger Claim, Worker Claim, Deployment Cell Lock은 소유 Resource가 다르다.
- Fencing Token은 Lease 갱신 시 증가하고 모든 상태 변경 SQL Predicate에 포함돼야 한다.
- 기준 Commit은 `CPF_BATCH_EXECUTION_EPOCH`의 Job별 최신 Token을 조회하고 Bind Transaction에서 Epoch Row를 잠근다. Vendor별 `FOR UPDATE`·동시 갱신 의미와 다중 인스턴스 실행은 환경별로 실행해 확인한다.
- Lease 만료 뒤 과거 Worker가 완료 응답을 보내면 `late reply`로 분리하고 현재 상태를 덮어쓰지 않는다.

## 26. Partition·Remote Partition·Remote Chunk

### Local Partition

- Partition Key 범위가 겹치거나 빠지지 않는지 Preview한다.
- `maxPartitionCount` 기본 256, 범위 1~10,000.
- Grid Size와 Executor Core/Max/Queue를 함께 조정한다.

### Remote

기본 Kafka Contract:

| Property | Default·범위 |
|---|---|
| `cpf.batch.remote.kafka.request-topic` | `cpf.batch.remote.requests.v2` |
| `reply-topic-prefix` | `cpf.batch.remote.replies.v2` |
| `consumer-group` | `cpf-batch-remote-workers-v2` |
| `role` | `ALL`; Manager/Worker 별 분리 권장 |
| `send-timeout` | 30초 |
| `message-ttl` | 5분, 최대 1시간 |
| `max-envelope-bytes` | 2 MiB |
| `max-payload-bytes` | 1 MiB, Envelope 이하 |
| `max-headers` | 32 |
| `max-header-value-length` | 512 |
| `max-delivery-attempts` | 5 |
| `max-payload-depth` | 32, 최대 128 |
| `reply-queue-capacity` | 1,000, 최대 100,000 |

`managerInstanceId`는 명시 Property, `CPF_INSTANCE_ID`, `HOSTNAME` 중 하나가 필요하다. 허용 Producer ID, Environment, Tenant, Message TTL·Size·Depth를 Codec과 Ledger 양쪽에서 검증한다.

## 27. Scheduler·Calendar·Misfire·Durable Launch Outbox

### 정상 Dispatch

```text
Leader Lease 확인
→ Due Schedule 조회
→ 영업시간·Calendar 판정
→ Fenced Trigger Claim/Insert
→ Durable Launch Outbox 기록
→ 승인 실행 요청 생성
→ Job Start/Link Bind
→ Trigger Dispatched 표시
→ next_fire_at CAS Advance
```

- 영업일 전용 Schedule에서 Calendar Runtime이 중지되면 `next_fire_at`을 소진하지 않는다.
- `NEXT_BUSINESS_DAY`와 `SKIP` 정책을 구분한다.
- `next_fire_at` CAS 또는 Fencing 실패는 다른 Leader가 처리한 것으로 재조회한다.
- Trigger Claim 뒤 Process Kill이면 Outbox가 재개해야 하며 신규 Trigger를 만들지 않는다.
- Misfire 정책은 각 Schedule 정의의 허용 값, 횟수 상한, 과거 실행 Catch-up 여부를 문서화한다.

## 28. Center-Cut

Center-Cut Definition에는 다음을 명시한다.

- 대상 Provider와 대상 Selection 조건.
- Business Key·Business Date.
- Partition 수와 범위.
- Chunk Size와 Commit 기준.
- Handler Reference.
- Retry Limit과 Retryable Error.
- Result Status, Payload Masking, 대사 기준.
- 중복 Target·이미 처리된 Target 정책.

ADM `batch` 화면에서 Job, Target, Result를 교차 조회한다. Target의 `transactionId`, Parent Segment, Segment ID와 Result ID를 보존한다. 실패 건수만 보고 재수행하지 않고 Row별 Side Effect와 Result Ledger를 확인한다.

## 29. Job Pack·Artifact·Runner·Worker·Agent

### Artifact

1. Artifact ID·Version·SHA-256·Signature·Manifest를 고정한다.
2. Repository URL·TLS·Host/IP Identity를 확인한다.
3. Download Size 상한, Temp Directory, Atomic Install/Current Pointer를 사용한다.
4. 설치 뒤 Health가 실패하면 이전 Version으로 Rollback한다.

### Host Agent 주요 Property

- Repository URL, Allowed Host·Content Type, Proxy, Private Address 허용 정책.
- Legacy Public Key와 Versioned Trust Store의 Key Path·유효기간·폐기 상태.
- Signature, Repository Digest Header, Artifact State MAC Key.
- Artifact/Log/Process Output Size와 Process Timeout.
- Command Ledger Root·Retention과 Client Subject Allowlist.
- Service별 installRoot, logRoot, systemdUnit/Windows Script, healthUrl, runtimeControlUrl, runtimeMode, environment, release channel.

Agent는 검증한 Pinned Address를 실제 Socket 연결에 사용하고 원 Hostname으로 TLS SNI·Hostname Verification을 수행한다. Redirect·Proxy·DNS 변경·혼합 A/AAAA·Metadata Address를 Negative Test한다.

## 30. Deployment·Cell·Partial Failure·Reconciliation

```text
Manifest 검증
→ Plan 생성
→ BAT/DEPLOY_PLAN 승인
→ Cell Lock 획득
→ Instance별 Artifact 설치
→ Process 전환
→ Health Probe
→ 결과 집계
→ SUCCESS / PARTIAL_FAILED / UNKNOWN_RESULT
→ Reconcile 또는 Compensation/Rollback
```

- 같은 Operation ID와 다른 Request Hash는 충돌이다.
- Cell Lock을 잃은 실행은 이후 Side Effect를 중단한다.
- Instance별 단계와 오류를 저장한다.
- 일부 Instance만 변경된 상태에서 전체 성공으로 표시하지 않는다.
- Reconciliation은 실제 Agent State·Artifact Pointer·Health를 다시 읽어 Terminal 상태를 결정한다.
- Rollback은 이전 Artifact/Config/DB 호환성을 확인하고 별도 승인·사유로 실행한다.

## 31. ADM Batch 화면 사용 연결

### `batch`

Job 등록·수동 실행·실패 재수행·중지·Scheduler 1회 실행·Job 상세·Schedule Simulation·Relation·Target·Step·Worker·Lock·Ghost·Operation Log·CSV를 제공한다.

필수 입력: Job ID/명/유형, Execution/Schedule ID, Parameter, Calendar, Business Date, Dispatch Status, Heartbeat Timeout, Lock Key, Ghost Action, Reason.

### Batch Runtime Views

`batch-overview`, `batch-runtime`, `batch-instances`, `batch-scheduler`, `batch-worker-pools`, `batch-center-cut`, `batch-agents`, `batch-job-packs`, `batch-executions`, `batch-recovery`, `batch-leases`, `batch-alerts`, `batch-audit`, `workers`는 Control Server View를 조회한다. 응답의 `stale=true` 또는 `partial=true`를 빈 결과/정상으로 해석하지 않는다.

### Deployment

Manifest JSON과 Reason으로 Plan을 생성한 뒤 Approval 화면에서 `BAT / DEPLOY_PLAN` 또는 `ROLLBACK_PLAN`을 승인한다. Plan 생성은 배포 완료가 아니다.

## 35. Batch 실무 패턴 — Tasklet 외부 Process

### 설계 항목

단일 조치, exit code, timeout, process tree, output budget

| 항목 | 필수 기록 |
|---|---|
| Identity | jobId, definitionVersion, parameters, businessDate, idempotency scope/key/hash |
| Execution | cpfExecutionId, JobInstance/Execution/Step ID, partition/worker ID |
| State | CREATED·READY·RUNNING·STOPPING·COMPLETED·FAILED·UNKNOWN_RESULT 등 실제 상태 |
| Resource | chunk, partition, thread, queue, connection, file, timeout budget |
| Control | stop, restart, abandon, reprocess, reconcile, rollback 허용 조건 |
| Security | operator, permission, reason, approval, artifact trust, outbound allowlist |
| Audit | request hash, plan checksum, fencing token, before/after, result |

### 구현 순서

1. JobParameter 중 식별 Parameter와 비식별 Parameter를 구분한다.
2. JobInstance 중복 기준과 CPF Idempotency Scope·Hash를 일치시킨다.
3. Step의 Restart 가능 여부와 Checkpoint 저장 시점을 정의한다.
4. Reader 정렬과 재시작 위치를 고정한다.
5. Writer의 중복 안전성과 업무 Unique·Version을 정의한다.
6. Skip·Retry·No-Retry Exception을 분류한다.
7. Stop 요청 뒤 실제 Resource 정리 완료 기준을 정의한다.
8. Manager·Worker·Agent의 Lease·Heartbeat·Fencing을 연결한다.
9. ADM 화면에서 실행·진행·오류·복구 상태를 확인한다.
10. Process Kill, Broker outage, DB deadlock, response loss를 주입한다.

### 정상 결과

- CPF Control 상태와 Spring Batch Metadata가 같은 실행을 가리킨다.
- Read·Process·Write·Skip·Error 건수가 업무 대사 결과와 일치한다.
- 모든 Partition·Worker가 Terminal 상태이며 Lease가 정리된다.
- Artifact·Definition·Plan Checksum이 실행 기록과 일치한다.
- Audit와 Metric에서 승인·실행자·사유·복구 이력을 확인할 수 있다.

### 복구

실패 단계에 따라 `restart`, `failed-only reprocess`, `reconcile`, `compensation`, `abandon`, `rollback` 중 하나를 선택한다. 응답 유실 상태에서 새 Execution을 만들지 않고 기존 `cpfExecutionId`와 Idempotency Key로 결과를 찾는다.

2. Dry Run으로 총건수·제외·중복·Invalid·예상 Partition을 산출한다.
3. Partition Key·Range와 Chunk·Commit 단위를 기록한다.
4. Definition·Plan·Artifact Checksum을 고정한다.
5. Permission·Reason·Approval·Idempotency·Fencing으로 실행한다.
6. CPF Execution과 Spring Job/Step ID를 연결한다.
7. 처리 중 Read·Write·Skip·Error·Unknown 건수를 관찰한다.
8. Stop 시 신규 Claim 차단, In-flight 종료, Checkpoint 저장을 확인한다.
9. 실패 건은 failed-only Reprocess 전에 업무 상태와 중복 안전성을 확인한다.
10. 대상 총건수·성공·실패·제외·중복·합계·Hash를 대사한다.
11. Audit와 실행 Evidence를 저장한다.

## 49. Host Agent 설치·제어 절차

- Repository URL·Allowed Host·Pinned Address·CIDR·Port·Content Type를 설정한다.
- Signature Trust Store, Digest Header, Artifact SHA-256, State MAC Key를 확인한다.
- Artifact 크기는 기본 512MiB, Log Archive는 기본 1GiB 상한을 적용한다.
- Command Ledger는 `./data/agent-command-ledger`에 저장하고 Retention을 관리한다.
- Service Definition의 installRoot·logRoot·systemdUnit 또는 Windows Script·Health URL·Runtime Control URL을 등록한다.
- Download→Digest→Signature→Manifest→Staging→Atomic Install→Service Control→Health 순서로 실행한다.
- 실패 시 Staging을 정리하고 현재 서비스 Version을 유지한다.

## 제5부. Spring Batch 기능 전체 구현·실행 워크북

## 50. Job Definition 작성

`BatchExecutionPlan`은 Plan ID·Version·Topology·Step 목록·Checksum을 가지며 `BatchStepDefinition`은 Step ID·Executor Type·Reference·Parameter·Partition Count·Transition·Restartable을 정의한다.

개발자는 다음을 Job Definition에 기록한다.

- `jobId`, `jobName`, `definitionVersion`, Owner Domain
- Definition·Artifact·Plan SHA-256
- JobParameter 식별성·Default·민감정보 제외
- Step 순서, Start Limit, Restartable
- Tasklet/Chunk 선택 근거
- Reader 정렬 Key와 Checkpoint
- Processor 중복 영향
- Writer Upsert·Version·Unique 정책
- Commit Interval·Skip·Retry·Timeout
- Success/Failure Transition과 업무 대사 기준

## 51. Tasklet 구현 절차

Tasklet은 단일 외부 명령·파일 이동·집계·대사 작업에 사용한다.

1. Side Effect 전 입력 Snapshot과 Operation ID를 저장한다.
2. 외부 호출 전후 Checkpoint를 분리한다.
3. Exit Code·응답 상태·Output 상한을 정의한다.
4. Timeout·Process Kill·응답 유실 시 상대 상태 조회 방법을 제공한다.
5. Restart가 같은 Side Effect를 중복 생성하지 않도록 Idempotency를 적용한다.
6. Stop 요청 시 Interrupt·Child Process·Temp File 정리를 수행한다.

## 52. Chunk 구현 절차

```text
Reader → Processor → Writer → Commit
```

- Reader는 재시작 가능한 정렬 Key와 Snapshot 기준을 사용한다.
- Processor는 순수 변환 또는 중복 영향이 명확해야 한다.
- Writer는 Chunk 재시도 시 Upsert·Unique·Version으로 중복을 막는다.
- Skip Item은 별도 Ledger에 Business Key·Error·Attempt를 저장한다.
- Commit Interval은 처리량뿐 아니라 Lock·Rollback·Memory를 기준으로 정한다.
- Restart Test에서 같은 Item이 중복 반영되지 않는지 확인한다.

## 53. 승인 실행 요청

`BatchApprovedLaunchRequest`에는 Published Definition, Plan, Parameter, Approval ID, Operator, Reason, Idempotency Key와 양수 Fencing Token을 전달한다.

실행 순서:

1. Published Definition Version·Checksum을 확인한다.
2. Plan Checksum을 다시 계산한다.
3. Approval의 Target·Expiry·Requester/Approver 분리를 확인한다.
4. Scope+Idempotency Key+Canonical Request Hash를 Reservation에 저장한다.
5. Job별 최신 Epoch를 Claim하고 Fencing Token을 얻는다.
6. Spring Batch Job을 Start한다.
7. CPF Execution ID와 JobInstance·JobExecution·StepExecution ID를 Bind한다.
8. Start 또는 Bind 응답 유실 시 Reservation·Spring Metadata·Link를 대사한다.

## 56. Scheduler 등록·Misfire·Durable Dispatch

Schedule에 다음을 저장한다.

- Schedule ID, Job ID, Definition Version
- Cron 또는 Fixed Delay, Timezone, Business Calendar
- Effective From/To, Enabled, Expected Version
- Misfire 정책: Skip, Fire Once, 제한된 Catch-up
- Parameter Template, Approval 정책, Reason
- Cluster Claim, Durable Launch Outbox, Dispatch Attempt

Trigger Claim 후 Process가 중단되면 Durable Outbox의 상태로 Dispatch를 재개한다. 같은 Trigger 시각의 중복 Start는 Idempotency Scope·Hash로 차단한다.

## 57. Partition·Remote Worker

1. 대상 Snapshot과 Partition Key·Range·Total Count를 고정한다.
2. Partition Count는 Property 상한 이하로 제한한다.
3. Worker Capability·Version·Zone·Heartbeat를 확인한다.
4. Claim·Lease·Fencing으로 한 Partition의 현재 Owner를 결정한다.
5. Stale Worker의 늦은 Write·Completion은 Fencing으로 거부한다.
6. Rebalance·Broker 장애·Late Reply·DLT를 시험한다.
7. 완료 후 Partition별 건수·합계·Hash를 전체 대사한다.

Product Profile 기동 시 `scripts`, `pathAliases`, `trustedSigningKeys`, `outboundHttp`를 이 Class의 검증 규칙으로 확인한다.

## 60. Host Agent 설치·제어

Agent는 Artifact Repository URL·Trust Store·Allowed Host·Pinned Address·CIDR·Port·Digest Header·Signature·State MAC Key를 사용한다. Command Ledger는 영속 Directory에 저장한다.

Service Definition에는 Service ID, Artifact ID, Install/Log Root, systemd Unit 또는 Windows Script, Health/Runtime Control URL, Runtime Mode, Environment, Release Channel을 등록한다.

Agent 조치 순서:

1. Client Subject와 Command Permission을 확인한다.
2. Artifact Manifest·SHA-256·Signature·Key 유효기간·폐기 여부를 확인한다.
3. DNS 검증 주소와 실제 Socket 주소를 고정한다.
4. Download Size·Content Type·Digest Header를 검증한다.
5. Install·Start·Stop·Restart·Log Archive Command를 Ledger에 기록한다.
6. 응답 유실 시 같은 Command ID로 결과를 조회한다.

## 61. Stop·Restart·Abandon·Recover 판정

| 조치 | 허용 기준 | 확인 결과 |
|---|---|---|
| Stop | 실행 중·Stop 가능 Step | 실제 Step 종료·Worker 해제·Resource 정리 |
| Restart | Restart 가능한 종료·Checkpoint·호환 Definition | 새 JobExecution·중복 없는 업무 결과 |
| Abandon | 재시작 금지 결정·Approval | Metadata와 운영 정책 모두 Abandon |
| Recover | Spring Metadata 복구 대상 | 복구 Execution Link와 업무 대사 |
| Reprocess | 실패 Item이 식별되고 중복 안전 | Failed-only 결과와 전체 합계 |
| Reconcile | 응답 유실·Link 누락·Unknown | CPF·Spring·업무·Worker 상태 일치 |

## 62. `UNKNOWN_RESULT` 대사 순서

1. `cpfExecutionId` Reservation·상태·Request Hash를 조회한다.
2. JobInstance·JobExecution·StepExecution을 조회한다.
3. CPF Execution Link 존재 여부를 확인한다.
4. Partition·Worker Message Ledger와 Reply를 조회한다.
5. 업무 Item·Result·Outbox를 대사한다.
6. Success·Failed·Stopped·Unknown을 확정한다.
7. Restart·Reprocess·Compensation·수동 확정 중 하나를 승인한다.
8. Operator·Reason·Approval·대사 근거를 Audit에 남긴다.
