## 3. Tasklet

단일 외부 호출, 파일 이동, 마감 집계처럼 작업 단위가 명확할 때 사용한다.

1. Tasklet의 부작용과 완료 Marker를 정의한다.
2. 재실행 시 이미 끝난 부작용을 식별하는 Key를 저장한다.
3. 외부 호출 전후 상태를 분리해 결과 불명을 판정한다.
4. 완료 후 Exit Status와 업무 원장 결과를 대사한다.

DB Commit 후 상태 보고가 유실되면 업무 원장을 조회해 완료 여부를 확정한다. 단순히 Tasklet을 다시 실행하지 않는다.

## 4. Chunk

1. Reader는 안정적인 정렬 Key와 Restart Cursor를 제공한다.
2. Processor는 가능한 한 순수 변환으로 작성한다.
3. Writer는 Chunk Transaction과 영향 Row Count를 검증한다.
4. Commit Interval은 Lock 시간, 메모리, 실패 시 재처리 비용으로 정한다.
5. Skip·Retry 대상과 한도를 업무 오류와 기술 오류로 구분한다.
6. Step 완료 후 Read/Write/Filter/Skip/Rollback Count를 업무 합계와 비교한다.

## 5. JobParameter·Instance·Execution

업무일자, 대상 범위, 기준 Version과 요청 ID를 식별 Parameter로 사용한다. 매번 변하는 실행 시각을 식별 Parameter에 무조건 포함하지 않는다.

- JobInstance: 같은 업무 정의와 식별 Parameter
- JobExecution: Instance의 한 실행 시도
- StepExecution: Step 단위 결과
- ExecutionContext: Restart에 필요한 상태

재처리는 기존 Execution을 수정하지 않고 새 Operation ID를 만든다.

## 6. Stop·Restart·Abandon·Reprocess

| 조치 | 의미 | 사용 조건 | 완료 판정 |
|---|---|---|---|
| Stop | 안전 지점에서 중지 요청 | 운영 중단 필요 | Step이 중지 상태이고 Checkpoint 보존 |
| Restart | 같은 Instance의 Checkpoint 재개 | Failed/Stopped | 완료 Chunk 중복 처리 없음 |
| Abandon | 더 이상 Restart하지 않음 | 운영 판단·승인 | 상태 종결, 데이터 대사는 별도 |
| Reprocess | 대상 일부/전체를 새 실행 | 업무 재처리 | 새 Manifest와 Operation ID 대사 |

## 7. Partition과 Remote Worker

1. Partition Key와 범위의 중복·누락 방지 규칙을 정의한다.
2. Master가 Partition Manifest와 Snapshot Hash를 만든다.
3. Worker가 Lease·Owner ID·Fencing Token으로 Claim한다.
4. Heartbeat·Progress·Checkpoint를 보고한다.
5. Worker 종료 시 Lease 만료 후 다른 Worker가 Reclaim한다.
6. 이전 Worker의 늦은 Commit은 Fencing Token으로 거부한다.
7. Partition별 성공·실패·UNKNOWN을 합산하고 전체 대상과 대사한다.

## 8. Center-Cut

Center-Cut은 대상 선정, Partition, Chunk, Commit과 대사를 하나의 실행 계약으로 관리한다.

필수 값:

- 대상 Query/조건과 Preview Count
- 조건 Hash와 기준 Snapshot/Version
- Partition Key·Range·Chunk Size·Commit Interval
- 제외·오류·UNKNOWN 정책
- 승인자와 실행 가능 시간대
- 처리 후 원장 대사 Query
- 실패 Partition Reprocess Manifest

실행 후 `대상 = 성공 + 실패 + UNKNOWN + 제외`가 성립해야 하며 UNKNOWN은 성공에 포함하지 않는다.

## 9. Scheduler

등록 값은 Job ID/Version, Calendar, Cron/Interval, Timezone, Misfire, Concurrency, Parameter Template, Effective Time이다.

변경 절차:

1. 다음 실행 시각과 과거 회차를 Preview한다.
2. 영향 Job·Worker·Calendar를 확인한다.
3. Expected Version과 Reason을 입력한다.
4. 위험도에 따라 Approval을 받는다.
5. 적용 후 Scheduler Instance별 Applied Version을 확인한다.
6. 첫 Trigger 결과와 Audit를 확인한다.

Misfire 정책은 Skip, Fire Once, Catch Up, Manual로 구분한다. Catch Up은 최대 Backlog와 동시 실행 제한을 둔다.

## 10. Job Pack·Artifact·Agent

Job Pack에는 Job Definition, Parameter Schema, Migration, Config, Artifact Hash, Permission, Runbook, Test Evidence를 포함한다.

Host Agent는 승인된 Artifact Version과 Checksum만 설치·실행한다. Agent와 Control Server 사이에는 Service Identity, Nonce, Timeout과 Command Result 조회가 필요하다.

## 11. Dry Run과 대상 Preview

운영자는 실행 전에 대상 건수, 조건 Hash, 예상 Partition 수, 예상 처리시간, DB/Worker 용량과 제외 조건을 확인한다. Preview와 실제 실행 사이에 기준 데이터가 바뀌면 Snapshot 또는 Expected Version 정책에 따라 재승인을 요구한다.

## 12. 실행 절차

1. ADM `Batch Overview`에서 Job·Schedule·Worker·Lock Health를 확인한다.
2. 대상 Preview와 조건 Hash를 기록한다.
3. Parameter, Artifact Version, Expected Job Version을 입력한다.
4. Reason과 Approval을 완료한다.
5. Execution ID를 기록하고 실행한다.
6. Step·Partition·Worker·Lease·Throughput·Error를 관찰한다.
7. Timeout이나 화면 응답 유실 시 Execution ID로 상태를 조회한다.
8. 완료 후 업무 원장·Batch Metadata·Audit를 대사한다.

## 13. 장애 분류와 정상화

| 장애 | 상태 | 조치 |
|---|---|---|
| DB Commit 전 Worker 종료 | 미반영 또는 Rollback | Checkpoint에서 Restart |
| Commit 후 보고 유실 | 결과 불명 | 업무 원장과 StepExecution 대사 |
| Broker ACK 유실 | UNKNOWN | Broker Probe·Outbox 대사 |
| Partition 일부 실패 | Partial | 실패 Partition만 Reprocess |
| Lease 만료 후 구 Worker Write | Stale Writer | Fencing 거부·Incident |
| Scheduler Misfire | Missed Trigger | 정책별 Skip/Fire/Catch Up/Manual |
| Artifact 불일치 | 실행 거부 | 승인 Artifact·Checksum 복원 |

## 15. EDU — Chunk Restart

1. 1,000건 대상과 Commit Interval 100을 준비한다.
2. 550건 부근에서 Worker Process를 종료한다.
3. Execution이 Failed 또는 Stopped로 남고 마지막 Checkpoint가 보존되는지 확인한다.
4. Restart 후 완료 Chunk가 중복 갱신되지 않는지 확인한다.
5. 최종 성공·실패·제외·UNKNOWN 합계와 업무 원장을 대사한다.

## 16. EDU — Partition Fencing

Worker A Claim → Heartbeat 차단 → Lease 만료 → Worker B Reclaim → A의 늦은 Write 거부 → B 완료 → Audit와 Fencing Token 확인 순서로 수행한다.
