## 3. 설치 전 점검

1. 기준 Commit과 Artifact Hash를 확인한다.
2. 대상 Topology와 Instance 수를 확인한다.
3. Port·DNS·TLS·Proxy·Firewall을 점검한다.
4. DB 전용 Schema와 계정을 준비한다.
5. Secret 참조를 준비하고 값은 문서에 기록하지 않는다.
6. Migration·Recovery Pack과 Backup을 확인한다.
7. Health·Metric·Trace 수집 경로를 준비한다.
8. Rollback Version과 중단 기준을 합의한다.

## 4. Property 관리

Property Catalog는 다음을 포함해야 한다.

```text
Key / Environment / Type / Default / Required / Range
Consumer / Profile / Restart / Secret
Failure / Verify Command / Expected Result / Rollback
```

변경은 Version·Checksum을 남기고 Target별 ACK를 확인한다. 일부 Target만 적용된 상태는 `PARTIAL_SUCCESS`로 처리하고 신규 변경을 겹치지 않는다.

## 5. Secret·Certificate

- Secret 원문을 Git·Markdown·CSV·JSON Evidence·Log에 저장하지 않는다.
- Provider가 없거나 필수 Secret이 만료되면 Prod 계열 Readiness를 거부한다.
- Rotation은 Old/New 중첩, 적용 Target, Rollback을 정의한다.
- TLS 인증서 만료·Chain·SAN·Revocation을 점검한다.

## 6. DB 설치·Migration

Vendor별 전용 QA 환경에서 Fresh·Upgrade·Recovery를 검증한다. 운영 적용 전 Backup ID와 Restore 검증 결과를 확보한다. Runtime 계정에 DDL 권한을 주지 않는다.

## 7. Messaging

### 현재

Kafka 개발·시험 Runtime과 공개 Starter가 존재한다.

### QA38 목표

RabbitMQ·JMS(Artemis Fixture)·IBM MQ를 Provider별로 검증한다. Docker Runtime이 준비돼도 Product Starter·Consumer·Operations가 없으면 기능을 완료로 판정하지 않는다.

운영 항목:

```text
Broker/Queue Manager Health
Topic/Queue/Subscription
Backlog/Lag
Consumer Instance
Retry/DLQ/DLT
Publisher Receipt
Credential/TLS
Replay Approval/Audit
```

## 8. 기동·종료

### 기동

1. DB·Secret·Broker·Collector를 준비한다.
2. Migration 상태와 Drift를 확인한다.
3. Control Plane → Owner Service → Edge 순으로 기동한다.
4. Health가 아니라 Readiness와 실제 Probe를 확인한다.
5. 신규 Traffic을 열고 오류율·지연·Backlog를 관찰한다.

### 종료

1. 신규 Traffic과 Schedule을 중지한다.
2. Worker 신규 Claim을 중지한다.
3. 진행 Transaction·Outbox·Checkpoint를 Drain한다.
4. Application을 종료한다.
5. DB·Broker는 소유 Runbook에 따라 종료한다.

## 9. 배포 전략

### Rolling

Mixed Version API·DB·Message 호환이 검증된 경우에만 사용한다.

### Blue-Green

DB와 외부 효과가 공유될 때 이중 처리 방지를 검증한다. 전환 후 Old 환경의 Worker·Scheduler를 중지한다.

### Canary

대상 Traffic·사용자·Route를 제한하고 오류·지연·업무 대사를 기준으로 확대한다.

## 10. 관측

### Log

Transaction·Trace·Operation·Attempt·State·Failure Class를 기록한다.

### Metric

Request, Error, Latency, Retry, Backlog, DLQ, Reconcile, Lease Conflict, DB Pool을 수집한다.

### Trace

외부 Provider Attempt와 Timeout Budget을 연결한다. Payload와 Secret은 기록하지 않는다.

## 11. Capacity

- CPU·Memory·Heap·GC
- Thread·Connection Pool
- DB Session·Lock·IO
- Broker Partition/Queue·Consumer·Prefetch
- Batch Chunk·Partition·Worker
- File Size·Transfer Concurrency
- Log/Trace Export Backpressure

부하 시험은 정상 처리량뿐 아니라 장애 중 Queue 증가와 복구 시간을 측정한다.

## 12. Backup·Restore

- DB, Broker Metadata, Config, Certificate, Route/Policy, Artifact Manifest를 범위에 포함한다.
- Restore는 격리 환경에서 실제 Application Query까지 검증한다.
- RPO/RTO 미충족 원인을 기록한다.

## 13. Upgrade·Rollback

1. Compatibility Matrix 확인
2. Backup/Restore 확인
3. DB Pre-check
4. Canary 또는 단계 적용
5. Target ACK·Health·업무 대사
6. 중단 기준 도달 시 Rollback/LKG
7. DB가 역변경 불가하면 Forward Recovery

## 14. 장애 Runbook

### DB

Connection, Lock, Slow Query, Disk, Replication, Drift를 분리한다.

### Broker

Broker Down, Backlog, Poison, Consumer Cancel, Receipt Loss를 분리한다.

### Instance

Crash, OOM, Stuck Thread, Readiness Failure, Lease 잔여를 확인한다.

### Network

DNS, TLS, Reset, Latency, Half-open, Packet Loss를 재현하고 Timeout Budget을 확인한다.

### Disk·Memory

임계 도달 전 신규 작업 수락을 제한하고, 증적 보존 후 대상별 정리를 수행한다. 광역 삭제 명령을 사용하지 않는다.

## 15. Docker 개발·시험 환경

새 문서 경로:

```text

```

현재 환경은 Container 자동 시작을 금지하고 `restart: "no"`를 사용한다. Image·Volume·Secret·사용자 DB를 임의 삭제하지 않는다. QA38 Messaging 증분 환경은 Product 구현 검증을 위한 선택 Fixture로 구분한다.
