지원 DB는 Oracle, PostgreSQL, MariaDB다. Frontend Build와 Browser Test는 Node 22 계열 환경을 사용한다.

## 2. Artifact 수령

1. `cpf-tools/release/cpf-final-artifact-catalog.json`에서 Artifact ID·Owner·Output·Consumer를 확인한다.
2. SHA-256과 Source SHA를 검증한다.
3. CycloneDX SBOM과 License Review를 확인한다.
4. DB Pack은 Vendor·Migration Version·Checksum을 확인한다.
5. Frontend는 Lockfile·Generated Client·Browser Test 기록을 확인한다.
6. 배포 Manifest에 Artifact·Config·DB·Secret Reference·Certificate Version을 기록한다.

## 3. 계정과 Directory

Runtime별 전용 OS 계정을 사용한다. Artifact, Config, Log, Work, Temp, Upload, Backup, Evidence Directory를 분리하고 필요한 Write 권한만 부여한다. Secret과 Private Key는 Repository·Artifact·Log 경로 밖에 둔다.

## 5. Secret·Certificate

1. Secret Provider와 Reference를 배포한다.
2. Runtime 계정이 필요한 Reference만 읽도록 ACL을 설정한다.
3. Log·Actuator·Dump에 실제 값이 노출되지 않는지 확인한다.
4. 인증서 Chain·SAN·Expiry·Key Usage를 확인한다.
5. 교체 시 신·구 Version 동시 신뢰 구간을 둔다.
6. Consumer Reload/Restart 후 Handshake를 확인한다.
7. 구 Version 폐기와 Audit를 완료한다.

## 6. DB 신규 설치

1. Vendor Pack과 Checksum을 확인한다.
2. Empty Schema와 DB 계정 권한을 확인한다.
3. Install을 적용한다.
4. Verify Query로 Object·Column·Index·Constraint·Seed를 확인한다.
5. Application을 기동해 Readiness와 Read/Write Smoke를 수행한다.
6. Drift Scan과 Schema Version을 보존한다.

## 7. DB Upgrade·Rollback

1. 현재 Schema Version과 Backup Manifest를 만든다.
2. Mixed Version 호환 기간과 Lock 영향을 검토한다.
3. Migration을 적용하고 Verify한다.
4. Application Canary 또는 일부 Instance로 Smoke한다.
5. 문제가 있으면 승인된 Rollback 또는 Forward Recovery를 수행한다.
6. Reapply와 Drift 0건을 확인한다.

운영 데이터가 있는 환경에서 파괴적 Rollback을 임의 실행하지 않는다.

## 8. Messaging

| Provider | 확인 항목 |
|---|---|
| Kafka | Bootstrap·TLS/SASL·Topic·ACL·Consumer Group·Lag·Idempotence |
| RabbitMQ | VHost·Exchange·Queue·Binding·Publisher Confirm·Mandatory |
| JMS/Artemis | Broker URL·Destination·Transaction·Acknowledge |
| IBM MQ | Queue Manager·Channel·Queue·CCSID·TLS/CCDT·Reason Code |

업무 Source는 Provider SDK가 아니라 CPF Messaging API를 사용한다. Provider 장애 중 발생한 UNKNOWN은 복구 후 Reconcile한다.

## 9. 개발·시험 Docker 환경

`cpf-tools/environment/docker-development-test/**`는 수동으로 기동한다. RabbitMQ, Artemis, IBM MQ, TCP Simulator, Mailpit, WireMock, Toxiproxy, OTel Collector 등 필요한 Fixture만 선택한다.

- Secret은 Repository 밖에서 공급한다.
- Restart Policy는 `no`를 유지한다.
- 검증 종료 후 Container를 중지한다.
- Container Volume·Log·Temp 정리는 exact path로 수행한다.
- 운영 환경 설치 절차와 Docker 시험 환경을 혼동하지 않는다.

## 10. 기동

Dependency 순서: Secret/Identity → DB → Broker/File/External → CPF Runtime → Gateway → ADM/BZA Frontend.

1. Artifact·Config·Migration Version을 확인한다.
2. Runtime 계정으로 Process를 기동한다.
3. Liveness와 Readiness를 구분해 확인한다.
4. 필수 Dependency Health를 확인한다.
5. ADM Topology와 Capacity에서 Instance·Version·Endpoint를 확인한다.
6. Smoke Transaction과 Audit를 확인한다.

## 11. 종료

1. 신규 Traffic을 차단하고 Drain 상태로 전환한다.
2. In-flight Request와 Worker Claim을 확인한다.
3. Scheduler 신규 Trigger와 Worker 신규 Claim을 중지한다.
4. Checkpoint·Outbox·File Transfer 상태를 보존한다.
5. Process를 종료한다.
6. Lease 만료·Reclaim·미확정 Operation을 확인한다.

## 12. Health 상태

- Liveness: Process 자체 상태
- Readiness: 요청 수락 가능 여부
- Dependency: DB·Broker·SFTP·Secret·OTLP 실제 연결
- Degraded: 일부 기능 제한
- Unknown: 상태 확인 실패

설정값 존재만으로 Readiness를 성공 처리하지 않는다.

## 13. 배포 전략

### Rolling

Instance Drain → 배포 → Migration 호환 확인 → Readiness → Traffic 복귀 순서다. Mixed Version의 API·Message·DB·Config 호환을 확인한다.

### Blue-Green

Green 배포 → Migration 호환 → Smoke → Traffic 전환 → 관찰 → Blue 보존/종료 순서다.

### Canary

Tenant 또는 Traffic 비율을 제한하고 Error·Latency·UNKNOWN·DLQ·DB/Broker 부하를 기준선과 비교한다.

## 14. Config Partial Apply

Preview Hash와 Target Snapshot을 확인하고 적용한다. Target별 ACK/NACK와 Observed Hash를 대조한다. 실패 Target만 재시도하거나 LKG로 되돌린다. 성공 Target을 중복 적용하지 않는다.

## 15. Log·Metric·Trace

필수 관측:

- 요청 성공·실패·UNKNOWN·Latency
- Retry·Circuit·Bulkhead·Timeout
- DB Pool·Lock·Replication·Slow Query
- Broker Lag·Queue Depth·Outbox·Inbox·DLQ
- Batch Throughput·Worker Lease·Scheduler Misfire
- File Transfer·Notification Delivery
- Runtime Change·Approval·Rollback

개인정보·Token·Secret·전문 원문은 기본 Log와 Trace Attribute에 기록하지 않는다.

## 16. Capacity

CPU·Memory·GC·Thread·Connection Pool·Disk·File Descriptor·Network·DB Lock/IO·Broker Lag·Worker Queue를 함께 본다. 단일 지표만으로 Scale 결정을 내리지 않는다.

## 17. Backup·Restore

Backup Manifest에 DB, Artifact, Config Hash, Secret/Certificate Reference, Migration Version, Queue/Topic 정책, Attachment/File Storage를 기록한다.

Restore 후 Schema/Row Count, Sequence/Identity, Scheduler Lock, Outbox/Inbox/DLQ, 진행 중 Batch, Audit 연속성, Readiness와 업무 Smoke를 확인한다.

## 18. DR

RPO/RTO, Replication, Backup 주기, DNS/Route 전환, Broker Offset/Queue, Secret/Certificate, Audit 보존을 정의한다.

Failover 시 Stale Writer와 Split Brain을 차단한다. Failback 전 양쪽 데이터·Outbox·Batch·Audit를 대사한다.

## 19. 장애 Runbook

### DB

Readiness 차단 → Connection·Lock·Replication 확인 → Write 제한 결정 → DB 복구 → Transaction·Outbox·Batch 대사 → Readiness 복귀.

### Broker

Publish/Consume 영향 확인 → ACL·TLS·Queue/Topic·Lag 확인 → UNKNOWN 보존 → Broker 복구 → Outbox/Inbox/DLQ Reconcile.

### Instance

Traffic 제거 → In-flight·Lease 확인 → Process Restart → Readiness → Stale Claim·Reclaim 확인 → Traffic 복귀.

### Disk

신규 대량 작업 제한 → 증가 경로와 Owner 확인 → 승인된 Retention/Cleanup 수행 → Free Space·File Handle·Process 확인. 임의 Log·DB·Queue 파일을 삭제하지 않는다.

### Memory

Heap·Native·Thread·Direct Buffer·GC를 분리해 확인한다. Dump에 Secret·개인정보가 포함될 수 있으므로 접근과 보존을 통제한다.

### Network/TLS

DNS·Route·Firewall·Proxy·Certificate·Handshake를 확인한다. Retry 폭주를 제한하고 Dependency 복구 후 UNKNOWN을 대사한다.

## 20. Upgrade 인계와 Rollback

Artifact Version, DB Version, Config Version, Frontend Version, Route/Profile Lock을 하나의 배포 단위로 관리한다. Rollback 전 이전 Artifact가 현재 Schema와 호환되는지 확인한다. 비가역 Schema 변경은 Forward Recovery를 준비한다.
