## 4. Configuration 문서화 규칙

**운영 Property Reference는 실제 Runtime Source에서 확인한 Leaf Key를 아래 열로 관리한다. Prefix만으로 완료 처리하지 않는다.**

| 필드 | 의미 |
|---|---|
| Key | 실제 Property Key |
| Env | 환경변수 이름 |
| Type | Boolean/Integer/Duration/URI/Enum/... |
| Default | 코드/metadata의 실제 Default |
| Required | 언제 필수인지 |
| Range | 허용 범위·교차 조건 |
| Consumer | 실제 ConfigurationProperties/AutoConfiguration/Runtime |
| Profile | 적용 Profile/Capability |
| Restart | 변경 시 Restart 필요 여부 |
| Secret | Secret 취급 여부 |
| Symptom | 잘못된 값의 증상 |
| Check | 확인 명령/API/ADM 화면 |
| Expected | 정상 결과 |
| Rollback | 이전 값/LKG 복원 |

### 4.1 Configuration 우선순위

환경별 우선순위는 Spring Boot 외부설정 규칙과 CPF dynamic control plane을 구분한다. Boot binding 값은 profile YAML/env/command line 우선순위로 정하고, Runtime Control로 hot-apply되는 정책은 별도 desired/actual version·checksum·ACK/NACK 원장으로 관리한다.

### 4.2 Prefix와 Leaf Key

`cpf.messaging.kafka`처럼 Namespace만 존재하는 항목은 Capability 설명에 두고, 운영 설정표에는 실제 하위 Leaf Key를 전수 기록한다.

## 22. 신규 설치 통합 실습

## 23. Config Partial Apply 통합 실습

## 28. SLI·SLO·Error Budget

서비스별 Availability/Latency/Error/Throughput/Batch SLA/Queue Lag 등 SLI를 정의한다. SLO 숫자는 실제 환경과 고객 승인으로 확정한다. Burn-rate Alert와 Escalation을 연결한다.

## 29. Maintenance·Drain·Quiesce

점검 전 신규 Traffic/Job/Claim을 단계적으로 차단하고 진행 중 작업을 안전 지점까지 처리한다. Drain 완료 조건, 최대 대기시간, 강제 종료 조건, 미종결 Operation/Lease 대사를 기록한다.

## 30. Resource Limits

모든 Queue/Thread/Connection/File/Archive/Download/Batch/Support Bundle은 size/count/time budget을 가진다. 한도를 넘었을 때 reject/throttle/spill/quarantine 정책과 사용자 Error를 정의한다.

## 31. Configuration 정합성 Gate

05의 Configuration 절은 아래 정합성 조건으로 판정한다. Starter Catalog의 선택 Namespace와 Runtime Leaf Prefix가 다른 경우를 분리하고, 직접 설정이 없는 Profile/SPI/Codec에는 가상 Key를 만들지 않는다.

1. `@ConfigurationProperties`/metadata/YAML/env/script의 실제 Leaf Key 전수 수집.
2. Alias/Deprecated/Dynamic key 분리.
3. 동일 Key의 Default 불일치 0건.
4. Secret 원문 예시 0건.
5. Consumer 없는 Key 0건 또는 폐기 근거.
6. 문서 Key와 Source Key 양방향 Missing 0건.
7. 확인 명령과 Rollback이 모든 운영 Key에 존재.

## 32A. cpf-tools 실행 절차와 결과 판정

### 32A.1 작업 Context 확인

```powershell
pwsh -NoProfile -File cpf-tools/scripts/check-work-context.ps1
```

정본 문서·HEAD·Branch·Working Tree를 **읽기 전용**으로 확인한다. Dirty/Ahead/Behind/Diverged를 발견해도 이 Tool의 결과를 근거로 `reset`, `clean`, `restore`, `stash`를 실행하지 않는다. 보호 대상부터 기록한다.

### 32A.2 DB 정본 동기화

```powershell
pwsh -NoProfile -File cpf-tools/scripts/sync-database-artifacts.ps1
```

공식 Vendor Source→Vendor Pack→Install SQL→Batch Sequence→Runtime Query Pack→Query Contract→Nullable/Empty repair→Migration Checksum→Schema Manifest→Drift/Profile Standard 순서로 검증한다. Generated Domain 반영이 필요한 경우에만 승인된 `-ApplyGeneratedDomains` 경로를 사용한다. 중간 단계 실패를 후속 단계 성공으로 덮지 않는다.

### 32A.3 DB 초기화/검증

```powershell
pwsh -NoProfile -File cpf-tools/scripts/initialize-cpf-database.ps1 -ProfilePath cpf-tools/config/database-install.default.json
```

기본 실행은 정적 검증과 sanitised result를 만든다. 실제 DB 실행은 `-RequireRun`을 명시한다. `-All`과 개별 Selector를 혼용하지 않는다. Generated Domain DB는 Platform Pack이 아니라 Domain Manifest가 지시하는 경로로 설치한다.

### 32A.4 Generated Domain 동기화

```powershell
pwsh -NoProfile -File cpf-tools/scripts/sync-generated-domain-artifacts.ps1
# diff/ownership 확인 후 필요할 때만
pwsh -NoProfile -File cpf-tools/scripts/sync-generated-domain-artifacts.ps1 -Apply
```

ownership manifest와 격리 재생성 SHA를 비교한다. Generator-owned 파일이 사용자가 수정한 상태라면 자동 덮어쓰지 않고 fail-closed한다.

### 32A.5 임의 Domain Parity

```powershell
pwsh -NoProfile -File cpf-tools/scripts/check-generator-arbitrary-domain-parity.ps1
```

서로 다른 Domain/SystemCode를 build sandbox에 생성하고 이름 normalize 후 구조·DB3·Starter lock parity를 비교한다. 특정 PAY/MBR 이름에만 맞는 Template 예외를 탐지하는 용도다.

### 32A.6 전체 제품 검증

```powershell
pwsh -NoProfile -File cpf-tools/scripts/verify-full-product.ps1 -StaticOnly
pwsh -NoProfile -File cpf-tools/scripts/verify-full-product.ps1 -WithDatabase -WithGeneratorLifecycle -WithBrowser -RequireAll
```

첫 명령은 정적/계약 점검용, 두 번째는 모든 Group 실행을 요구하는 통합 Gate다. `-RequireAll`에서 `SKIPPED`가 있으면 완료로 기록하지 않는다. 실패 Gate는 해당 Source/Contract를 수정하고 원 명령을 다시 실행한다.

### 32A.7 Convention Plugin / Platform BOM

Generated/고객 Domain은 `cpf-tools/build/gradle-plugin`의 Convention과 `cpf-tools/build/platform-bom`을 사용한다. BOM은 버전 정렬만 하며 Capability를 대신 선택하지 않는다. CPF Source/JAR를 고객 Domain에 수동 복사하지 않는다.

## 33A. Starter 39개 구현 종류별 사용·운영 카드

각 Starter는 “이름이 존재한다”로 끝내지 않고 선택 목적, Provider Slot, 실제 설정면, 실패/복구, EDU 연결을 확인한다. Profile 6개는 고객이 직접 내부 Starter를 임의 조립하는 대신 승인된 시작점으로 사용한다.

### `cpf-starter-data-cache-caffeine`

- **종류/Group:** `provider` / `data`; Provider Slot `cache:caffeine`.
- **목적:** 로컬 저지연 Cache Provider.
- **선택 기준:** 단일 프로세스/인스턴스 로컬 캐시가 충분할 때.
- **Catalog Namespace:** `cpf.data.cache.caffeine`.
- **실제 설정면:** cpf.data.cache.caffeine.provider + cpf.cache.caffeine.* (`DIRECT_LEAF_DIFFERENT_PREFIX`).
- **사용법:** Capability와 Provider Slot을 함께 선택하고 동일 Slot의 다른 Provider와 무승인 동시 활성화를 피한다. 외부 ConnectionFactory/Secret/Endpoint가 필요한 Provider는 고객 인프라 설정과 CPF 정책 Key를 분리한다.
- **대표 EDU:** EDU-DEV-12, EDU-DEV-36.
- **실패/복구:** Startup validation/Health에서 잘못된 Provider·필수값을 차단하고, Side Effect가 있는 기능은 timeout을 곧바로 실패로 단정하지 말고 Attempt/Owner 상태를 대사한다. Config 변경은 이전 snapshot/LKG로 되돌릴 수 있어야 한다.

### `cpf-starter-data-cache-valkey`

- **종류/Group:** `provider` / `data`; Provider Slot `cache:valkey`.
- **목적:** 공유 Cache/무효화 Provider.
- **선택 기준:** 다중 인스턴스에서 공유 캐시·무효화가 필요할 때.

### 34.2 설정 변경 절차

1. 변경 대상 Key가 위 표의 Boot binding인지 Runtime Control hot-apply인지 구분한다.
2. Boot binding이면 기존 값과 Secret reference를 보존하고 변경 전 Config Hash를 기록한다.
3. Startup validation/Health/의존성 연결을 확인한 뒤 업무 Smoke와 관련 EDU fault/recovery를 수행한다.
4. Runtime Control이면 desired version/checksum을 만들고 Target별 ACK/NACK/Timeout을 수집한다.
5. Partial Apply는 성공 Target을 “미적용”으로 간주하지 않는다. 실패 Target만 Reconcile하거나 승인된 LKG로 되돌린다.
6. Rollback 후에는 이전 값 복원만 보지 않고 actual version/config hash/health/transaction 결과를 다시 대사한다.

### 34.3 설정 금지 사례

- Catalog Prefix만 보고 존재하지 않는 leaf를 생성하지 않는다.
- SFTP raw password, Session credential key, Service Identity secret, Runtime agent token을 Git/YAML 평문으로 두지 않는다.
- Profile Starter에 leaf key를 중복 정의하지 않는다. Profile은 resolved Starter 조합을 소유한다.
- `cpf.db.resource-root` 없이 Module-local Vendor SQL로 fallback하지 않는다.
- `UNKNOWN_RESULT`를 timeout 실패와 동일하게 취급해 무조건 재시도하지 않는다.

### 36.1 신규 설치 Gate

Artifact/Checksum → 계정/Directory → Config/Secret/Certificate → DB/Broker → Deploy → Health → Smoke → Backup → 운영 인계 순서를 고정한다. Artifact/Config/Schema/Service Identity가 서로 다른 Version을 가리키면 설치 성공으로 보지 않는다.

### 36.2 Config Partial Apply Gate

Desired Snapshot/Checksum을 만든 뒤 Target별 ACK/NACK/Timeout을 기록한다. 일부만 성공하면 성공 Target을 되돌리지 않고 실패 Target을 Reconcile하거나 승인된 LKG로 Rollback한다.

### 36.3 DR Gate

Primary/Standby lease/epoch/fencing을 사용해 Split-Brain을 막는다. Backup Restore만 성공했다고 DR을 종결하지 않고 Application/DB/Broker/Route/Sequence/Outbox/Inbox/Audit를 함께 대사한다.
