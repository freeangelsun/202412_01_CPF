### 0.1 읽는 순서

1. 책임 경계와 상태 모델을 먼저 확인한다.
2. 정상 절차를 수행하기 전에 권한·설정·데이터베이스·다중 인스턴스 영향을 확인한다.
3. 오류·부분 실패·복구 절차와 완료 점검을 같은 작업 범위로 수행한다.
4. 직접 실행하지 않은 검증은 `완료`로 기록하지 않는다.

## 1. 구조 원칙

CPF 구조는 다음 질문에 항상 답할 수 있어야 한다.

1. 이 기능의 최종 소유 모듈은 어디인가?
2. 외부에서 사용하는 공개 API인가, 고객 확장 SPI인가, 제품 내부 구현인가?
3. 실제 소비자는 누구이며 어느 실행 경로에서 호출하는가?
4. 동일 JVM과 분리 WAS에서 계약의 의미가 같은가?
5. 다중 인스턴스와 부분 실패에 안전한가?
6. 운영자가 상태·원인·조치 결과를 확인할 수 있는가?
7. 데이터베이스, 이관, 생성기와 배포 산출물에 어떤 영향이 있는가?

구조는 패키지 모양이 아니라 **소유권, 의존성, 실패 책임과 운영 책임**을 분리하는 규칙이다.

## 2. 제품 영역

### 2.1 기반 영역

#### `cpf-core`

배포 구조에 독립적인 기술 계약을 소유한다.

- 표준 헤더와 거래 문맥
- 공개 오류·검증·결과 계약
- 로컬·원격 서비스 호출 계약
- 시간 제한, 재시도, 회로 차단과 격리
- 멱등성, 임대, 점유, 세대 토큰과 잠금
- 비동기 봉투, 송신함·수신함 계약
- 파일·전문·외부 연계 기술 계약
- 비밀값 참조, 마스킹, 로그·추적·지표 기반
- 공개 테스트 도구

특정 업무 정책, ADM 화면, BZA 조직 정책, 배치 스케줄러 구현을 넣지 않는다.

#### `cpf-common`

여러 업무영역이 선택적으로 재사용하는 고객 업무 공통을 소유한다.

- 고객 공통 코드·메시지·기준정보
- 영업일 달력과 공통 업무 검증
- 공통 마스킹·감사 정책
- 고객 공통 파사드와 기반 SPI 구현

모든 호출을 `cpf-common`으로 모으는 중앙 경유 계층으로 사용하지 않는다.

### 2.2 업무·운영 애플리케이션 영역

- `cpf-admin`: 플랫폼 운영과 통제
- `cpf-biz-admin`: 고객 업무 관리
- `cpf-member`: 생성기의 기준 업무영역
- `cpf-<domain>`: 생성기로 만드는 독립 업무영역
- `cpf-reference`: 공개 API 교육·참조 구현

각 애플리케이션은 자신의 API, 애플리케이션 서비스, 도메인 규칙, 어댑터와 데이터 소유권을 가진다.

### 2.3 선택 실행 제품

#### `cpf-gateway`

공통 외부 진입 정책이 필요한 경우 선택한다. 내부 업무 호출을 무조건 게이트웨이로 재경유시키지 않는다.

#### `cpf-batch`

업무영역이 제공한 배치 계약을 실행하는 제품군이다. `cpf-batch` 자체는 집합 프로젝트이며 실행 파일은 제어 서버, 스케줄러, 작업자, 대량 실행기와 원격 에이전트 하위 모듈에서 만든다.

### 2.4 도구·공급·검증 영역

`cpf-tools`는 다음을 소유한다.

- 업무영역 생성과 제거
- 데이터베이스 정본 동기화와 공급자별 변환
- 설치·이관·업그레이드·되돌리기·백업·복구
- 로컬·사내 저장소·폐쇄망 산출물 공급
- 구조·보안·SQL·문서·저장소 위생 검사
- 실행 환경 기동·중지·상태와 진단

## 3. 공개 경계

### 3.1 공개 API

고객 개발자와 다른 모듈이 안정적으로 사용하는 계약이다.

- 최소 입력으로 안전한 기본 동작
- 명확한 입력 제약과 오류 분류
- 동시성·멱등성·시간 제한 의미
- 한글 JavaDoc, 사용 예제와 테스트 도구
- 버전 호환 정책

### 3.2 SPI

고객 어댑터나 업무 확장을 위한 포트다.

SPI는 구현 책임, 호출 시점, 스레드·시간 제한, 재시도 여부, 중복 호출, 비밀값과 오류 변환 규칙을 문서화한다. 기본 구현을 제공하거나 미구성 시 명확하게 안전 차단한다.

### 3.3 내부 구현

`internal` 패키지는 제품 내부에서만 사용한다. 외부 모듈의 직접 의존은 구조 검사에서 실패해야 한다.

## 4. 허용 의존성

```text
업무영역 ────────→ cpf-common ───────→ cpf-core
업무영역 ───────────────────────────→ cpf-core
cpf-admin ──────────────────────────→ cpf-core
cpf-biz-admin ─────→ cpf-common ─────→ cpf-core
cpf-gateway ────────────────────────→ cpf-core
cpf-batch 하위 실행 모듈 ───────────→ cpf-core
```

다음 의존성은 금지한다.

```text
cpf-core → cpf-common / admin / batch / 업무영역
업무영역 A → 업무영역 B의 DB 직접 접근
ADM → 다른 소유자의 DB 직접 갱신
외부 모듈 → com.cpf.*.internal
업무영역 간 내부 호출 → 게이트웨이 강제 재경유
생성 산출물 → 특정 예제 업무명에 고정된 계약
```

## 5. 애플리케이션 계층

```text
api
 ├─ controller
 ├─ request / response
 └─ openapi
application
 ├─ service
 ├─ command / query
 └─ port
domain
 ├─ model
 ├─ policy
 └─ state machine
adapter
 ├─ persistence
 ├─ remote
 ├─ messaging
 └─ file
config
test
```

- 컨트롤러는 입력·인증 문맥·권한 진입점·응답 변환을 담당한다.
- 애플리케이션 서비스는 사용 사례와 트랜잭션 경계를 조정한다.
- 도메인은 상태 전이와 업무 불변식을 강제한다.
- 포트는 외부 의존과 저장소 의존을 추상화한다.
- 어댑터는 데이터베이스, 원격 호출, 메시징, 파일 등 기술 구현을 소유한다.

저장소가 업무 규칙을 대신하거나 컨트롤러가 상태 전이를 직접 수행하지 않는다.

## 6. 데이터 소유권

### 6.1 원칙

- 업무 원장은 해당 업무영역이 소유한다.
- 다른 모듈은 공개 API, 이벤트 또는 승인된 조회 계약으로 접근한다.
- ADM은 상태를 조회하고 명령을 요청하지만 다른 소유자의 원장을 직접 수정하지 않는다.
- 운영 편의를 이유로 공용 DB 계정에 모든 권한을 부여하지 않는다.

### 6.2 조회 모델

운영 통합 조회가 필요하면 다음 중 하나를 사용한다.

1. 소유자 공개 조회 API
2. 이벤트 기반 조회 투영
3. 읽기 전용 복제·검색 저장소
4. 승인된 보고용 데이터 제품

투영 데이터는 원장과의 지연·버전·정본 불일치를 표시하고 재구축 절차를 제공한다.

## 7. 배포 구성

### 7.1 동일 JVM

```text
업무 A → 공개 파사드 → 로컬 어댑터 → 업무 B 애플리케이션 서비스
```

- 네트워크 직렬화 비용이 없다.
- 호출 계약과 오류 의미는 원격 호출과 같아야 한다.
- 호출자가 상대 구현 클래스를 직접 주입하지 않는다.
- 순환 의존을 만들지 않는다.

### 7.2 분리 WAS

```text
업무 A → 공개 파사드 → 원격 어댑터 → 서비스 등록부 → 업무 B 공개 API
```

- 전체 시간 예산에서 연결·TLS·처리·재시도 시간을 배분한다.
- 전송 예외를 공개 오류 계약으로 변환한다.
- 인증·권한·거래 문맥과 추적 정보를 전달한다.
- 응답 유실 시 결과 불명으로 분류할 수 있어야 한다.

### 7.3 모듈형 단일체

- 모듈별 공개 경계와 데이터 소유권을 유지한다.
- 내부 호출은 로컬 어댑터를 사용한다.
- 한 프로세스라는 이유로 다른 모듈의 내부 패키지나 테이블에 접근하지 않는다.

### 7.4 마이크로서비스

- 업무영역별 독립 배포와 데이터 소유권을 유지한다.
- 서비스 등록부, 상태 점검, 시간 제한, 재시도와 장애 격리를 적용한다.
- API·이벤트·DB 이관 호환 기간을 관리한다.

### 7.5 혼합 구성

일부 업무영역은 같은 JVM에 두고, 대용량·보안·배포 독립성이 필요한 영역만 분리할 수 있다. 호출자는 로컬·원격 어댑터 선택을 알지 않는다.

## 8. 직접 진입과 게이트웨이

게이트웨이는 다음 조건에서 사용한다.

- 여러 채널에 공통 인증·헤더 정규화가 필요하다.
- 외부 공개 경로와 대상군을 중앙에서 승인·배포해야 한다.
- 호출량 제한, 요청 크기 제한과 장애 격리가 필요하다.
- 연결시험, 인스턴스별 적용 확인과 구성 정본 불일치 관리가 필요하다.

다음 경우에는 직접 진입이 더 적합할 수 있다.

- 내부 전용 서비스이고 공개 진입 정책이 업무영역에 이미 있다.
- 불필요한 중앙 홉이 지연과 장애 범위를 늘린다.
- 도메인 간 내부 호출을 외부 진입 계층으로 우회할 이유가 없다.

## 9. 제어 영역과 실행 영역

### 소유자 원격 제어 계약

ADM과 같은 운영 애플리케이션은 다른 제품의 데이터베이스를 직접 갱신하지 않는다. 조회는 조회 Port, 상태 변경은 Control Port로 분리하고, 분리 실행 환경에서는 소유 제품이 제공하는 내부 제어 API를 원격 어댑터가 호출한다.

```text
ADM 화면
→ ADM Application Service
→ Owner Control Port
→ Local Adapter 또는 Remote Adapter
→ 소유 제품의 상태 전이
→ 결과·감사·운영 원장
```

게이트웨이 제어 요청은 요청 시각, Nonce, Body Hash와 서명을 검증한다. 배치 작업정의 제어도 소유 제어 서버가 상태 전이와 버전을 최종 강제한다. 운영 편의를 이유로 ADM이 게이트웨이 또는 배치 테이블을 직접 수정하지 않는다.


### 9.1 제어 영역

정의, 버전, 승인, 배포, 상태 조회와 명령을 소유한다.

예: ADM, 배치 제어 서버, 게이트웨이 바인딩 원장, 설정 정책 원장

### 9.2 실행 영역

실제 거래, 메시지, 작업과 파일을 처리한다.

예: 업무 애플리케이션, 게이트웨이 인스턴스, 배치 작업자, 원격 에이전트

제어 영역 장애가 정상 업무 거래를 불필요하게 롤백시키지 않도록 트랜잭션과 저장 책임을 분리한다. 실행 환경은 마지막으로 승인된 유효 설정을 유지하되 만료·보안 위험이 있는 경우 안전 차단 정책을 적용한다.

## 10. 표준 거래 문맥

모든 주요 실행 흐름은 다음 식별자를 연결한다.

- `transactionId`: 사용자 또는 업무 요청 전체
- `segmentId`: 개별 호출·이벤트·작업 단계
- `parentSegmentId`: 상위 단계
- `traceId`: 분산 추적 연결
- `operationId`: 멱등 명령 단위
- `systemCode`, `moduleId`, `serverInstanceId`
- 배치 `jobExecutionId`, 메시지 `eventId`, 파일 `transferId`

비동기 전환과 스레드 전환은 문맥을 명시적으로 복사한다. 요청 종료 시 스레드 지역 문맥을 제거한다.

## 11. 시간 제한과 재시도

### 11.1 시간 예산

호출자는 전체 시간 예산을 정하고 하위 호출에 남은 시간을 전달한다.

```text
전체 2,000ms
├─ 연결·TLS 300ms
├─ 대상 처리 1,200ms
├─ 재시도 여유 300ms
└─ 응답 변환·정리 200ms
```

하위 계층의 개별 시간 제한 합이 상위 시간 예산을 초과하지 않도록 한다.

### 11.2 재시도 조건

재시도는 다음 조건을 모두 만족할 때만 수행한다.

- 오류가 일시적이며 재시도 가능하다.
- 요청이 멱등하거나 멱등성 보호가 있다.
- 남은 시간 예산이 있다.
- 최대 시도 횟수와 지수 지연·무작위 분산이 정의돼 있다.
- 호출 계층별 재시도가 중첩돼 폭증하지 않는다.

## 12. 결과 불명

요청을 대상에 전달한 뒤 응답을 받지 못하면 다음을 구분한다.

| 단계 | 분류 | 조치 |
|---|---|---|
| 연결 전 실패 | 미처리 가능성이 높음 | 안전 조건을 확인해 재시도 |
| 요청 전송 중 중단 | 처리 여부 불명 | 상태 조회·대사 |
| 대상 처리 후 응답 유실 | 처리 가능성이 높지만 불명 | 멱등 키로 조회, 대사, 운영 확정 |
| 명시적 실패 응답 | 확정 실패 | 오류 계약에 따라 종료 또는 보상 |

결과 불명을 일반 실패로 바꿔 무조건 재실행하지 않는다.

## 13. 다중 인스턴스

### 13.1 임대와 점유

장시간 작업은 소유자, 만료 시각, 갱신 시각과 세대 토큰을 저장한다.

### 13.2 세대 토큰

새 소유자가 점유를 인계받으면 토큰을 증가시킨다. 이전 소유자의 늦은 완료 요청은 토큰 불일치로 거부한다.

### 13.3 낙관적 잠금

운영 명령과 상태 변경은 기대 버전을 받는다. 영향 행이 0이면 충돌로 처리하고 최신 상태를 다시 보여준다.

### 13.4 시계와 만료

- 서버 기준 시계와 시간대를 명시한다.
- 시계 오차 허용 범위를 정한다.
- 만료 판정과 갱신 실패를 관측한다.
- 장시간 정지 뒤 복귀한 인스턴스가 이전 소유권을 사용하지 못하게 한다.

## 14. 비동기와 메시징

- 업무 원장과 송신함을 같은 트랜잭션에 저장한다.
- 게시자는 점유·세대 토큰으로 중복 전송 경쟁을 제어한다.
- 소비자는 수신함과 멱등 키로 중복 처리를 방지한다.
- 순서가 필요한 이벤트는 업무 키 기준 분할과 버전을 사용한다.
- 독성 메시지는 무한 재시도하지 않고 격리한다.
- 재생은 범위, 사유, 승인, 중복 영향과 결과를 기록한다.

## 15. 배치 구조

```text
작업정의·승인·배포
        ↓
실행용 투영
        ↓
스케줄러 → 작업자 / 원격 에이전트 / 대량 실행기
        ↓
실행·단계·체크포인트·재처리 이력
```

- 작업정의와 실행 인스턴스를 분리한다.
- 스케줄 발생, 수동 실행, 재시작, 재실행과 재처리를 구분한다.
- 일정의 시간대·일광절약시간·오실행 정책을 명시한다.
- 실행 중 버전 변경은 새 실행에만 적용한다.

## 16. 데이터베이스 구조

### 16.1 정본

논리 스키마와 이관 계획을 하나의 정본에서 관리하고 Oracle, PostgreSQL, MariaDB 산출물을 생성·비교한다.

### 16.2 변경 단위

다음은 같은 변경 단위로 검토한다.

- 테이블·열·기본값·제약·인덱스
- 설치·초기 자료·검증 SQL
- 이관·업그레이드·되돌리기
- 매퍼·DTO·조회 조건
- 생성기 템플릿
- 백업·복구와 호환 기간

### 16.3 정본 불일치

예상 테이블이 존재한다는 이유만으로 설치를 건너뛰지 않는다. 열·형식·기본값·제약·인덱스·버전·체크섬을 비교하고 차이는 정본 불일치 또는 이관 문제로 보고한다.

## 17. 보안 경계

- 외부 공개는 기본 거부한다.
- 서버 권한 검증을 화면 표시보다 우선한다.
- 비밀값은 참조로 전달하고 원문 생명주기를 짧게 유지한다.
- 로그·API·감사·검증 증적에 재귀 마스킹을 적용한다.
- 위험 조치는 작성자·승인자 분리, 사유, 범위, 만료와 감사가 필요하다.
- 운영자 기능의 실패가 원 업무 트랜잭션을 오염시키지 않도록 경계를 분리한다.

## 18. 설정과 정책 배포

설정은 코드 기본값, 제품 프로필, 환경 설정, 외부 설정 공급자와 버전 정책의 우선순위를 명시한다.

```text
작성 → 검증 → 승인 요청 → 승인 → 게시 → 인스턴스 적용 → 확인 응답 → 상태 대사
```

각 인스턴스의 예상 버전, 적용 버전, 체크섬과 결과를 저장한다. 일부 적용, 오래된 확인 응답, 정본 불일치와 되돌리기를 운영할 수 있어야 한다.

## 19. 호환성과 업그레이드

### 19.1 API

- 호환 추가는 기본값과 버전 정책을 제공한다.
- 필드 제거·의미 변경은 폐기 기간을 둔다.
- 오류 코드와 상태 의미를 임의로 재사용하지 않는다.

### 19.2 이벤트

- 생산자와 소비자의 혼재 버전을 고려한다.
- 필드 추가는 구 소비자가 무시할 수 있어야 한다.
- 필수 의미 변경은 새 사건 유형 또는 명확한 버전을 사용한다.

### 19.3 데이터베이스

확장 후 축소(확장 후 축소) 방식으로 구·신 애플리케이션이 함께 동작하는 기간을 둔다.

### 19.4 설정

새 설정은 안전한 기본값을 제공하고 구 버전 인스턴스가 알 수 없는 필드를 처리하는 방식을 정의한다.

## 22. 금지 사례

- 편의를 위해 모든 기능을 `cpf-core`에 적치
- 인터페이스만 만들고 기본 구현·소비자·오류·운영 경로 생략
- 업무영역 간 테이블 직접 조인
- ADM이 다른 업무 원장을 직접 수정
- 동일 JVM에서 내부 구현 클래스를 직접 호출하고 원격 구성에서만 공개 API 사용
- 게이트웨이를 모든 내부 호출의 필수 중앙 경유지로 사용
- 임대 없이 여러 스케줄러가 같은 실행을 생성
- 데이터베이스 공급자별 SQL을 수동 복사해 정본으로 관리
- 생성기 소유 영역과 고객 수정 영역을 구분하지 않음
- 과거 실행 결과를 현재 Commit의 검증으로 승계

## 부록 Z. 구현 추적 시작점

문서의 설명을 완료 근거로 사용하지 않는다. 아래 경로에서 실제 Consumer·구현·설정·SQL·Test 연결을 확인한다. 경로가 이동했다면 `git ls-files`와 `git grep -n`으로 최신 Owner를 다시 찾는다.

| 추적 대상 | 대표 경로 또는 명령 | 확인 목적 |
|---|---|---|
| Module 정본 | `settings.gradle` | 공식 Module과 Composite Build |
| 기술 계약 | `cpf-core/src/main/java/com/cpf/core/api`, `cpf-core/src/main/java/com/cpf/core/spi` | Topology-independent API/SPI |
| 업무 공통 | `cpf-common` | 선택형 고객 업무 공통 |
| 실행 제품 | `cpf-gateway`, `cpf-batch/*` | 선택 Edge와 독립 Batch Runtime |
| Architecture Gate | `cpf-tools/scripts/check-architecture-ownership.ps1` | 역방향·Internal 의존·Owner 위반 검출 |

### Z.1 공통 확인 명령

```powershell
git status --short
git diff --check
git grep -n "TODO\|UnsupportedOperationException\|return null" -- ':!cpf-docs/archive/**'
pwsh -File .\cpf-tools\scripts\check-architecture-ownership.ps1
pwsh -File .\cpf-tools\scripts\check-document-links.ps1
pwsh -File .\cpf-tools\scripts\check-repository-hygiene.ps1
```

명령이 현재 Repository에 존재하지 않거나 Parameter가 달라졌다면 해당 Tool Source와 [도구 상세 참조](CPF_TOOL_REFERENCE.md)를 먼저 갱신한다.

### Z.2 완료 상태 사용

- **완료**: 구현·Consumer·운영 경로·검증·Evidence가 현재 Commit에서 확인됨
- **부분 구현**: 일부 계층 또는 실패·복구·운영 경로가 빠짐
- **미구현**: 제품 동작이 없음
- **미검증**: 구현은 있으나 요구된 실행 검증을 수행하지 않음
- **실패**: 검증을 수행했으나 기대 결과를 충족하지 못함
- **재확인 필요**: Source·문서·Evidence 또는 환경이 서로 달라 현재 상태를 확정할 수 없음
